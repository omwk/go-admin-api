## 2. 批次

### S1 · 部门管理（2.5 人日）

| 端 | 内容 |
|---|---|
| 后端 | `POST/PUT/DELETE /admin/depts`；树形校验（不能成环、父必须存在、同级重名）；删除保护（有子部门或有成员 → 409）；成员数统计 |
| 前端 | 部门树管理页：新增子部门、编辑、删除、拖动排序（用 sort 字段） |

### S2 · 配置与字典（6 人日）

| 端 | 内容 |
|---|---|
| 后端 | ① 系统配置 API：按 group 读写、类型校验（string/number/bool/json）、变更审计<br>② 数据字典：`sys_dict` + `sys_dict_item` 新表，类型 + 项 CRUD，前端下拉统一取值<br>③ 错误码字典：`GET /meta/error-codes` 返回 code → message（供前端 i18n） |
| 前端 | 系统配置页（分组表单）、字典管理页（类型 + 项）、错误码查询页 |

### S3 · 通知中心（4.5 人日）

| 端 | 内容 |
|---|---|
| 后端 | 站内信 API：`GET /admin/notifications`（用户维度）、`POST /{id}/read`、`POST /read-all`、未读数；通知偏好（按类型开关） |
| 前端 | 通知中心页（列表 + 已读 + 未读角标）、通知通道配置页（F3 的 8 个接口） |

### S4 · 审计与安全（6 人日）

| 端 | 内容 |
|---|---|
| 后端 | ① 审计查询：`GET /admin/audit-logs`（操作者/资源/时间/结果过滤，只读）<br>② 登录历史：新表 `sys_login_log`，记录成功/失败/来源 IP/UA<br>③ 手动解锁：`POST /admin/users/{id}/unlock`<br>④ 密码策略配置化：长度/复杂度/有效期/历史条数从配置读取 |
| 前端 | 审计日志页、安全设置页（密码策略 + 会话策略）、用户行内「解锁」 |

### S5 · 租户管理（5 人日）

| 端 | 内容 |
|---|---|
| 后端 | 租户 CRUD、停用/启用；**开通流程**：建租户时生成默认角色 + 默认菜单 + 首个管理员邀请 |
| 前端 | 租户列表与详情、开通向导 |

**合计约 24 人日**（后端约 12，前端约 12）。

---

## 3. 顺序与依赖

```
S1 部门  →  S2 配置与字典  →  S3 通知中心  →  S4 审计与安全  →  S5 租户
```

理由：

- S1 最小，且用户管理页已等着它（跨部门编辑目前只能单测）
- S2 的字典是后续所有下拉的基础，越早越省事
- S3 依赖 F3 的后端（已完成），只补收件箱与页面
- S4 的登录历史依赖登录路径改造，放后面避免与安全策略冲突
- S5 依赖前三批（开通流程要建默认角色/菜单/通知偏好）

## 4. 每批的完成标准

1. 后端：OpenAPI 更新 + 集成测试 + `verify` 通过
2. 前端：页面可用 + 真实接口验证 + lint/typecheck/unit/build
3. 文档：`docs/api/inventory.md` 与 `docs/design/admin-framework.md` 同步更新
4. 验收：能在界面上完成该模块的操作，无需 SQL
