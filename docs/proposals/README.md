# proposals · 评审与待办

本目录只放**文档**，不放代码。Codex 在 Gate A 阶段只能写这里。

| 文件 | 何时产生 | 谁写 |
|---|---|---|
| `Mx-review.md` | 每个里程碑开始前的设计评审 | Codex 生成，人裁决 |
| `backlog.md` | 实现过程中发现但不在本卡范围的问题 | Codex 或人追加 |
| `xxx-proposal.md` | 实现中遇到需要改架构/数据模型的问题 | Codex 提议，人裁决后再落 ADR |

---

## Mx-review.md 模板

```markdown
# M3 设计评审

- 日期：2026-11-01
- 评审人：Codex
- 输入：docs/milestones/M3.md、docs/05-platform-sync.md、docs/03-data-model.md §4/§7

## 1. 规格冲突与歧义

| # | 位置 | 问题 | 理解 A | 理解 B | 建议 |
|---|---|---|---|---|---|
| 1 | M3 §7 T3.7 | 「整页成功才推进游标」与「不可重试错误进死信」冲突 | 有死信也算成功，推进 | 有死信就停，不推进 | A（否则一条坏数据卡死全链路） |

## 2. 实现风险

| # | 风险 | 触发条件 | 影响 | 规避 |
|---|---|---|---|---|
| 1 | 映射编译占用 CPU | 每条记录都编译 | run 耗时翻倍 | 按 version_id 缓存 |

## 3. 方案对比

### 争议点 1：漂移检测的时机

- **A 每批一次**：成本低，漏检批内小变化。工作量 0.5d。
- **B 每页一次**：更灵敏，CPU 开销约 +15%。工作量 1d。
- **推荐**：A。理由：漂移是「结构性」变化，批次粒度足够。
- **影响**：无表结构变更。

## 4. 未来 2 个里程碑的坑

- M4：`listing` 归并若自动匹配，会与人工归并冲突。
- M5：订单详情逐条拉取会放大限流风险。

## 5. 待决策清单

- [ ] Q1 游标推进策略按理解 A？
- [ ] Q2 漂移检测是否采用方案 A？
```

**人怎么处理**：逐条勾选/批注 → 有结论的写进 `docs/ADR.md` 或修改任务卡 → 再让 Codex 开始实现。
