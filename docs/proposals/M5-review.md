## 3. 方案对比

### Q1 状态机边界：命令约束与平台事实如何共存

现状依据：M5 §5.1；模型已具 payment_status/fulfillment_status；同步规格 §6.4 的 unknown 与取消示例。以下规则全部在既有来源身份校验通过之后执行，不能使被来源仲裁拒绝的 raw 重新变新。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 严格单状态 | 保留现有七态与单步白名单；非法快照只记录、不更新，冲突人工处理 | 改动少，命令规则直观 | 首次看到已完成单可初始化，但后续跨多步快照仍卡住；部分退款与取消混淆；真实回滚无法自动修复 | order 状态机、历史异常展示；基本沿用模型 | 1–2 人日 |
| B 正交事实 + 兼容投影（推荐） | 生命周期、支付、履约、售后、取消分别校验；status 仍输出原七态；快照跳步与受控纠正有单独规则 | 部分退款不抹掉发货状态；可解释平台纠正；保持现有列表 status 筛选 | 必须定义维度组合、纠正证据和历史结构，新增字段 | sales_order 增 lifecycle_status、after_sales_status、cancel_status；历史补决策元数据；详情增加维度，人工状态接口带版本 | 3–5 人日 |
| C 追加事件并构建投影 | 支付、履约、售后独立事件流驱动所有查询投影 | 历史表达能力强，适合未来复杂售后 | 上游常只有快照，不能凭空补事件；引入事件身份、投影修复与新表，明显超出 M5 | 新事件表、投影器、查询/运维链路 | 7–10 人日 |

**推荐 B 的判定规则：**

1. **身份与来源先决条件**：tenant/shop/platform/订单实例完整匹配，映射版本冻结，来源通过 ADR-018 校验。失败零聚合修改；平台状态字符串未知不能当作 unknown→任意状态的绕行入口。
2. **初始化与合法快进**：首次完整订单快照可直接初始化为已发货/已完成等状态；已有订单的快进允许经过已批准白名单的可达路径，例如 pending_payment→shipped，但只记“观测到跳步”，不捏造中间事件或时间。涉及经济事实时还须金额/支付证据一致；退款不作普通履约快进。
3. **何时信平台回滚**：平台能力配置明确支持该种纠正，且有可比较的更高 revision/更晚且可信的更新时间及完整权威详情；无 revision 时，只能在同一订单串行、无其他在途拉取的条件下，使用平台明确具备一致性保证的详情确认。还须通过支付、履约、退款交叉校验，例如更正发货记录不等于撤销已经成功支付。两次普通缓存读相同并不足以证明更新。
4. **高风险退回**：shipped→pending_payment、completed/closed/refunded 的重开不自动按“最后到达”接受；有明确撤销支付/撤销履约/退款撤销等平台纠正证据才进入单独受控纠正白名单。其余保留本地已接受事实、保存候选与冲突原因并进入人工处理；需有可见待处理项与责任人，不能只打 warn 后永远遗忘。
5. **何时拒收**：旧版本、身份多义、仅 webhook 摘要、未知状态、时间不可信、跨维度矛盾、缺关键详情均不能纠正。可重试详情失败进持久待办；语义冲突持久记录后允许页推进，重试用例必须证明不会无限卡页。对矛盾快照不做“状态留旧、金额换新”的混合更新。
6. **unknown 的边界**：新单可在保留原状态下进入 unknown；已知单遭遇未识别状态时保留已知投影并记冲突。不能先写 unknown 再借其“任意流转”抹掉支付/退款终态约束。
7. **人工操作**：继续走命令白名单和 50301；不允许人工把 paid/refunded 等支付事实改出来。人工纠正需独立授权、原因和当前 version，使用既有 409/10409 处理竞争；若增加入口，先批准契约，不把原 `/status` 暗中变成任意修复接口。

**叠加态建议：** lifecycle_status 保留待付款/待发货/已发货/已完成/已关闭五段，避免退款失败后不知道应回到哪一段；payment_status 沿用四值；fulfillment_status 沿用三值。after_sales_status 区分 none/processing/partial_refunded/refunded，cancel_status 区分 none/requested/rejected/cancelled。枚举及可组合矩阵须裁决后冻结。

- 部分成功退款：payment_status=partial_refund，履约/生命周期保持，兼容 status 继续显示 shipped 或 completed 等基础态；详情明确退款金额。若同时还有另一笔处理中的退款，after_sales_status=processing，已成功部分仍由 payment_status 与金额保留。
- 退款处理中：payment_status 不提前变 refunded；兼容 status=refunding；失败/撤销后从 lifecycle_status 恢复展示，不固定回 completed。全额成功且退款口径完整时才投影 refunded。
- 取消处理中：保留基础 status，cancel_status=requested；未付款确认取消才 closed；已付款取消与退款分开追踪，不能仅凭 IN_CANCEL 推断已经退款。
- 每次接受的维度变化均记历史，即使兼容 status 未变；拒绝候选用 event_kind=reject/correction/snapshot 等元数据区别于真实流转，不画成已经发生的时间线。新增 history 的 reason、维度前后值、证据 RawRef、mapping checksum、可空 occurred_at 与 observed_at/时间可信度；缺平台事件时间时明确“发生时间未知”。重复候选不得重复堆积历史。

**验收门禁**：快进、真实退回、有证据与无证据的终态重开、未知状态、退款撤销、部分退款且仍已发货、人工/同步竞争；重复 raw 不新增历史。B 需要调整 BR-010/任务卡解释，由人落裁决，本文不直接改变规则。

### Q2 幂等与重复到达：重复内容不等于旧版本

现状依据：raw.go 的重复返回原 RawRef；listing_source.go 按 raw ID 仲裁；ADR-018 明确不保证上游真实最新观测。保持这些机制，不另提来源排序算法。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 仅接可靠版本平台 | 必须具备不可变订单 ID 与可比较 revision/可信 updated_at，否则阻止订单同步上线 | 保证边界最清晰，旧版本可判定 | 排除部分平台；相同 revision 异内容仍要报冲突 | 订单能力门禁、fixtures、校验规则；存平台版本证据 | 1–2 人日 |
| B 至少一次到达 + 聚合幂等 + 能力分级（推荐） | 完整快照与稳定订单实例身份；沿用 raw 去重，订单内容相同不改业务；缺版本时以串行权威详情收敛，无法证明的冲突保留 | 适配现实平台；重复不增订单、不重复退款/历史；不虚称 hash 能排序 | 无可靠版本/一致性保证时仍不能自动判定新旧；平台回到相同旧内容存在已知边界 | order 幂等元数据、接入能力声明、详情待办、冲突展示；复用现有隔离原因边界 | 3–5 人日 |
| C webhook 事件 ID 驱动 | 每个事件 ID 作为处理凭据，按平台事件序号归并订单 | 对有可靠事件序号的平台效率高 | 不能统一覆盖回看窗口/分页重叠；事件 ID 无法证明订单版本，漏事件仍需拉详情 | webhook 收件箱、去重约束、事件到快照桥接 | 4–6 人日，仍需 A/B 的轮询兜底 |

**推荐 B 的规则：**

- 分清三层身份：投递 ID（如 webhook event_id）、raw 内容身份、订单实例身份。没有投递 ID 时不编造一个“唯一最新版本”；同一个投递事件可触发拉详情，但不能把 webhook 局部 body 当完整订单直接覆盖。
- raw hash 相同且 checksum 相同：沿用既有来源与幂等判断，订单数、item 集、金额和状态历史均不变。相同 raw 换 checksum 仍可重解释，不能被订单层“hash 相同即跳过”提前拦截。
- raw 不同但业务投影相同：可能只是追踪字段、数组顺序等变化；以规范化的完整聚合内容比较减少无效业务写入，同时保留来源前进及处置结果。投影包括状态维度、金额、按稳定行 ID 排序的 items、地址变化、vanished 标记，排除抓取时间/请求追踪；固定规范化版本。不得将随机加密后的 ciphertext 用作内容指纹，也不建立手机号等低熵明文 SHA 索引；若需持久比较敏感值，使用域隔离的带密钥摘要并标记版本。
- raw/业务投影不同只说明“有变化”，不说明“更新”。可靠 revision 较低拒绝，revision 相同异内容记冲突；时间同值异内容不能强行先后排序。无可靠版本且详情不保证一致性时，保留冲突并展示“最新性未确认”，不能用本地 fetched_at 或更大 raw ID证明平台版本。
- **A→B→A**：raw 去重会返回最初 A 的 RawRef，既有来源仲裁会拒绝倒退。Q1 的平台纠正证据不能绕过这个结果。本轮不更改该裁决；要求自动处理这种回滚的平台，应在订单上线前另卡解决或明确禁用该能力，不能声称 B 已保证最终收敛。
- 并发插入以唯一键作最后防线；冲突后回读并按聚合锁/CAS 重做判断。一次成功应用与历史去重凭据同事务提交；同一变化对应的一次累计退款更新不能在重试时变成重复加款。

**隔年同号的识别与处理：** 优先使用平台不可变内部 ID 作 external_order_id，order_no 仅用于展示/搜索，搜索结果允许同号多单。若平台仅有按月/年分段编号，只有平台明确保证分段不可变时，才能使用版本化、无歧义的“平台分段 + 原编号”作为实例键，且 raw 与规范层必须使用同一实例身份。不能按抓取年份、店铺当前年份或可能被纠正的 placed_at 自动拼键。

同号但不可变 ID/平台保证的分段不同，应形成新订单；同实例 ID 却出现冲突的创建标识，应隔离核实。仅凭金额、买家昵称、地址不同不能认定新单。没有任何可核实区分字段时，平台数据不足以自动识别复用，不能覆盖旧单或私自生成新单，须人工澄清接入契约。明细 external_item_id 也必须稳定，不能用数组下标或当前 SKU 充当身份。

**验收门禁**：回看重叠、webhook 重投、页边界重复、乱序与等时间异内容、同 raw 换映射、A→B→A 受限结果、同展示单号不同实例、两条相同 SKU 不同行、重复退款不累加。

### Q3 PII 加密：保护范围必须覆盖 raw 与查看通道

现状依据：M5 §5.3 与模型 order_address 不一致；Sealer 为 AES-256-GCM 且每次生成独立 nonce；bootstrap/ingestion_raw.go:140 将原 JSONB 直接写入 payload。下面三种粒度都必须同时解决 raw、日志、导出及权限旁路，单换地址表表示并不足够。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 整行订单加密 | 主单和地址/明细整体加密，只留必要查询索引投影 | 敏感字段边界宽，不易漏字段 | 状态/金额/时间筛选需大量明文冗余，统计与更新复杂，扩大改造 | sales_order/order_item/query 大幅调整，仍需安全索引与 raw 保护 | 9–13 人日 |
| B 逐 PII 字段加密（推荐） | 姓名、电话、地址独立密文信封；安全掩码单独投影；raw 完整内容独立加密 | 最贴近现有三列模型；字段 AAD 可阻止互换，查询不需解密 | 三次加解密；新增敏感字段必须登记；多字段更新与版本须原子 | order_address 格式与掩码、raw 存取适配、二次授权与审计、预览/归档保护 | 6–10 人日 |
| C 行内 PII JSON 加密 | 将姓名/电话/地址序列化后加密为一个 bytea 信封，非敏感投影独立存 | 一次加密，PII 字段扩展方便，符合“整体加密”字面意思 | 修改任一字段重加整块，不能字段级授权；与现有三列模型冲突更大 | order_address 改为统一 PII cipher，API 掩码、raw 保护与授权同 B | 6–9 人日 |

**推荐 B 的密码学契约：**

- 每列 bytea 保存版本化信封（格式版本、nonce、ciphertext+tag），key_version 与本行三字段原子更新；或者显式新增每字段 nonce 列，二者须选定，推荐前者。使用现有 Sealer，不复用 nonce；读取只用指定 key version，不试遍旧密钥。
- AAD 编码必须固定、无分隔歧义，至少包含用途域 `order_address`、格式版本、tenant_id、platform_id、shop_id、内部 order_id、字段名；上述 ID 从已经校验的关系链读取，不能信任请求 body。order_id 不随展示单号复用变化；不要绑定 status、手机号、updated_at 等可变数据。
- 仅 tenant/order 已能防跨租户跨订单调包，但不能防同单不同字段互换。加入 field 防 phone/name 调换；绑定地址修订号可防同单旧密文回滚，推荐新增 address_revision 并在完整替换时递增。AAD 认证关系，不提供新旧排序，也不解决数据库整体回滚。
- 行内 JSON 方案的 field 固定为 pii_bundle；整块替换仍绑定订单和修订号。密钥轮换保持业务身份与内容不变，仅替换密文/key_version；幂等 hash 不能因轮换改变。订单层将现有 Sealer 的凭据解密错误统一转换为既有 50401，隐藏密码学细节。

**raw 与衍生路径的最低要求（需 D2 批准）：**

1. 不裁剪原始详情；在可信服务端完成原文规范化与既有 hash 计算，再将订单 raw 的完整原文加密持久化。raw JSONB 可保存带版本的密文信封，读取端恢复原文；这是存储表示扩展，必须补充 ADR-002 的解释并覆盖在线/归档/诊断/重放读取兼容，不能将 ciphertext 当 JSON 原文交给 mapping。不得为绕过去重而在原文中塞采集时间或随机值。
2. raw 密文使用独立用途域，绑定可信 tenant/platform/shop/resource/订单实例身份与完整 RawRef；先分配目录身份后加密，目录与密文仍同事务。规范层地址加密在 raw 提交后的聚合写入阶段完成，符合 raw 先落约束；映射失败也只能保留受保护原文，不能落明文死信。
3. raw 详情默认只返安全元数据或掩码视图；原文查看也必须按订单 PII 权限、二次认证与审计控制，不能凭普通 sync/raw 权限旁路。dry-run、隔离详情、错误详情、请求元数据和 SQL 参数日志都纳入检查；PII 禁止经 ext、note、状态历史、队列 payload 泄漏。
4. region_hint 仅省级；不持久化市区/街道掩码来增加粒度。postal_code 同收货信息保护，不能继续默认明文；buyer_nick/buyer_id 是可关联个人的信息，只保留 PRD 明确需要的授权查询用途，不传播到公开分享或普通导出。

**掩码、二次授权与审计：** 列表/详情默认只用写入时生成的受限掩码投影，不为分页全量解密；须批准 receiver_name_mask、phone_mask 等字段及其残余可识别风险。严格默认用全掩码电话，任务卡“保留末四位”若要保留须单独确认；仅省份可明文筛选。没有安全投影时返回“已隐藏”，不能为满足示例把完整地址混入 DTO。

`trade:pii:read` + 当前订单数据范围 + 最近 5 分钟重新认证作为默认建议；认证后签发绑定 actor/session/tenant/order/用途/到期时间的短期查看凭据，不是一个可修改的 confirmed=true。当前 address GET 需增加凭据要求，另列受保护的申请/认证步骤；不在 URL 放凭据，响应 no-store，不将解密结果写缓存。跨订单、会话撤销、店铺移交均重验，超时重新认证。

每次真正返回完整 PII 都记录一条 order.pii.read 审计，含 actor、订单内部 ID/脱敏单号、字段集合、用途、结果、时间、trace/request 标识与授权凭据 ID；拒绝与解密失败也有安全审计，禁止记录明文或密文。成功审计必须持久提交后才返回明文，审计失败则不泄露数据；重复网络请求可关联相同 request，但多次实际披露不能静默采样。普通掩码列表无需每行解密审计；批量解密另行授权，M5 不默认开放。

**CSV 与搜索侧信道：** M5 普通 CSV 不含完整姓名、手机号、详细地址、邮编、buyer_id、raw/ext 原文，推荐也不导出 buyer_nick，仅保留业务白名单与省级统计；不新增 PII 导出路径。沿用既有导出物化、字段快照、生命周期与防公式注入决策。完整电话/地址、任意后缀/前缀、密文等值与敏感 ext 查询均不开放；订单号/买家昵称按 REQ-ORD-005 仅在已授权店铺范围内查询，避免未经授权 total、自动补全、错误差异泄露存在性；限流并监测枚举，不宣称消除授权范围内的所有推断风险。

**验收门禁**：跨租户/订单/字段调包、旧修订重放、错误 key_version、密钥轮换、二次授权过期/跨单、审计失败不返回、raw/预览旁路、搜索计数越权、普通 CSV 无 PII；测试仅用合成占位标记，不写真实电话或完整地址。

### Q4 金额口径：保存平台事实，显式表达差异

现状依据：模型有 goods/shipping/discount/total/paid 五种金额；工程约定 `*_cents` int64 + currency，PRD BR-001 明确最小货币单位且跨币种不可直接相加；M5 不做账单对账和换汇。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 不平就拒收 | goods+shipping-discount 与 total/paid 不一致即隔离整单 | 表内看似总能对平 | 拒绝未付款/部分支付等正常订单；税/补贴差异造成漏业务数据 | 校验、隔离展示，几乎不增模型 | 1–2 人日 |
| B 平台金额分层保留 + 差异标记（推荐） | 各金额原值保留；已付款现金口径取 paid，退款另列；记录公式差额与可信度，派生分摊明确标识 | 不丢订单，支持解释与后续账单对账 | 必须统一统计口径，业务方需理解“原值/估算” | sales_order 退款额/差异质量信息；order_item 分摊元数据；详情、筛选、stats、CSV | 2–4 人日 |
| C 本地重算覆盖 | 从明细重算 total/paid，并按比例强制分平 | 展示简单，账面守恒 | 篡改平台实付；未知税费/补贴被隐藏，退款再重算会移动历史成本 | 所有金额写入与查询，审计差异 | 3–5 人日，不推荐 |

**推荐 B 的口径：**

- goods=商品小计，shipping=运费，discount=订单定义内的优惠，total=应付，paid=累计已成功支付的毛额；paid 不等于 total，也不能默认等于 goods+shipping-discount。未付款 paid=0 不算不平；分期/部分支付保留平台事实。
- 差异至少分为 `formula_delta = total - (goods + shipping - discount)` 与 `payment_delta = paid - total`；后者只有在平台宣告结清时才按其支付口径判断异常。不用“以实付为准”覆盖 total/goods 或伪造平衡项。税、平台/商家补贴、舍入等有真实来源才作有标签的解释，未知则展示“平台金额未对齐”，不启动账单对账流程。
- 可表示但公式不平的单据接收并标记；缺币种、金额不可精确转换、int64 溢出、数量非法、退款超出平台定义可退款支付额等语义不可信情况隔离核实，不自动截断为零。允许的平台特殊负值需由接入契约证明，不能全平台一刀切或吞成默认值。
- 核心新增 refunded_amount_cents 表示累计成功退款，`net_received = paid - refunded` 为派生现金净额；平台若 paid 已是净额，必须有明确毛/净语义，不加回未获知的退款额来猜毛额，缺失标“未知”。原始订单额不随退款下降，不因部分退货减少原始 qty。
- 商品/运费/优惠口径需按平台 fixture 锁定，尤其 item discount 是否已经包含订单优惠；不能把同一优惠在 item 与订单再扣两次。

**订单优惠分摊：** 优先保留平台明细分摊；平台只给订单额时，以符合优惠条件的 item 的折前金额减已知行优惠为权重，纯整数采用最大余数法，剩余最小单位按稳定 external_item_id 决定，保证行分摊和恰等于目标优惠，且行应付不为负。平台未提供参与范围或优惠性质时，不猜是否含运费；保持订单优惠未分配并标 unknown。全零权重且优惠非零、优惠大于可分配基数等不得硬摊，显示待核实。新增分摊规则版本/来源元数据，区别平台原值与本地估算。

例如两个可参与行金额 1001、1000 最小单位，订单优惠 101，得到 51、50；此为估算分摊，不改变 paid。部分退款后保留这组原始分摊，仅记录实际退款及可确认的 item 归属；若平台不给行退款，订单累计额可知、行退款仍未知，不按比例伪造退款事实。退款撤销须有新证据与对应记录，不能用每次到达的累计额当增量相加。

**币种：** 沿用字段名 *_cents，单位定义为该 currency 的最小货币单位；JPY 为 1、KWD 为 0.001，禁止所有币种一律乘 100。按批准的币种精度表精确转换，未知币种/超精度金额不静默舍入。同一订单与明细使用同币种；跨币种支付或退款不能压入一个 int64，M5 标注不支持并保存 raw，不做折算。stats、CSV 按 currency 分组，不能输出跨币种单一总额。

**验收门禁**：公式差异与未付款单、税补贴、101 单位分摊、相同余数稳定性、零权重、折扣超额、部分/全部退款及撤销、相同累计额重复到达、JPY/KWD、跨币种汇总拒绝、溢出。

### Q5 增量同步与漏单：区分列表覆盖和详情落地

现状依据：M5 §5.2；Orchestrator 新周期将 fetchCursor 置空；sync_page.go 目前按 page_token 建游标并提交 page.Next；FetchRequest 只有 Resource/Cursor/PageSize；sync_runtime.go 一次 Fetch 仅取一个共享限流令牌，外层 15 秒超时。增加 order Handler 本身不能得到时间窗或逐详情恢复能力。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 7 天窗 + 整页拉全详情 | 页内全部详情齐全后才提交；失败重拉整页；时间窗结束推进 | 结构简单，可复用页事务 | 某个详情长期不可用会卡全页；200 次调用难放进预算；重复扫描成本高 | 订单采集适配、带版本 cursor envelope、run 上限 | 2–4 人日 |
| B 固定时间窗 + 持久详情待办 + 补查（推荐） | 发现 ID 与待办/扫描位置原子提交；详情分批拉取并逐条处置，分别记录发现与完成进度；周期补查历史 | 崩溃不丢已发现订单，限流下可续跑，能暴露覆盖缺口 | 增加持久待办与两类进度，需平台能力与容量门禁 | order 采集端口、详情待办表、sync_cursor.cursor_meta/运行统计及 bootstrap 接线、单笔拉取 | 5–8 人日 |
| C 全历史扫描为主 | 每次或高频重新枚举全部可访问订单，再拉详情 | 不依赖可靠 updated_at，适合作为补偿能力 | 量大成本高；平台历史保留/分页漂移仍可漏；实时性差 | 全量分段计划、API 配额及遍历进度 | 4–7 人日，只作 B 的条件性补偿 |

**推荐 B 的可执行边界：**

1. 每个逻辑周期冻结店铺/平台、时区解释、下界 L 与上界 U；L 为上次完整覆盖水位减 7 天，U 为平台可确认的当前时间减安全迟滞。初次同步从批准的回溯起点开始，不能默认只取最近 7 天。成功覆盖才推进完整水位，不能直接取“已见最大 updated_at”。
2. timestamp 相同用稳定实例 ID/平台 token 继续；含头不含尾 `[L,U)`，平台只能闭区间时允许边缘重复交给幂等。无稳定二级排序时按更小窗口重复覆盖并记录平台分页限制，不能保证消除移动 offset 页漏项。
3. 发现页的每个 ID、月份分段、列表版本证据先进入持久详情待办，再与发现检查点一起提交；新增表候选为 order_sync_pending。发现进度不冒充完整订单进度，完整覆盖进度须等每个 ID 已落完整聚合或有可追踪的隔离/死信处置。后者是“已持久处置”，不是“订单已成功同步”；存在失败债务必须显示覆盖缺口并触发补查。
4. 200 是执行片/续跑上限，不是逻辑时间窗总量上限；断点必须定位到窗口、分段、列表页及页内详情待办。拿到 NextCursor 却只消费部分 IDs 时不能丢掉余下 IDs。新 run 的 cursor 重置行为要按资源模式适配，不把时间水位当普通 page_token 清空。
5. 列表和每次详情调用都遵守同店共享限流、Retry-After 与凭据审计；若采集适配器内部拉多个详情，必须提供逐调用限流端口，不能仅在外层扣一次令牌。详情拉取在业务事务之外，返回完整单个订单快照后才走 raw→mapping→聚合；网络错误不能变成“空 items”。详情分页也须完整。
6. 实际每片数量取 API 延迟、限流额度与 60 秒任务预算的更小值；不可假定 200 条能在现有一次 15 秒 Fetch 中完成。授权和店铺状态每片重验，待办续跑不获得长期越权能力，提交沿用既有 fence。
7. 详情重试发生在后续时刻，可能新于原列表窗口；可接收该单的新详情，但不能因此把整个时间窗水位推到该详情时间。重试超限保留可恢复待办/死信和明确 RawRef 或发现证据；无 raw 的详情失败不能伪造成已落 raw。

**漏单边界与补偿：**

| 情况 | 三件套仍会漏的原因 | 推荐处理及保证边界 |
|---|---|---|
| 平台迟到超过 7 天，或退款修改不更新 updated_at | 订单永远不进入增量窗口 | 增量之外周期性分段补查历史、近期终态和未完成订单；平台历史访问范围不足时保留不可恢复缺口，告警并要求平台/人工补数。 |
| 停机/凭据失效超过 7 天 | 若从“当前时间减 7 天”重启会跳过旧窗 | 保留上次完整水位逐窗追赶；7 天是回看宽度而非最大追赶时长；平台订单过期前恢复才可补齐。 |
| 列表可见但详情延迟/404/超时 | 扫描完成不代表订单已完整 | 保留 ID 待办与时间戳，重试并分辨权限/保留期/删除；详情积压年龄和最老缺口独立监控。 |
| 列表只按创建时间检索或 updated_at 不可靠 | 历史订单变更不会重新出现 | 能力降级为创建发现 + 已知订单补拉/全历史分段覆盖；若配额不足，无法承诺 REQ-ORD-001，接入前裁决。 |
| 时间戳精度、时区或 DST 混用 | 边界解释错一小时/一天导致缺口 | 带 offset 的输入按绝对时刻转 UTC；无 offset 必须按已配置的店铺/平台 IANA 时区解释，DST 歧义用覆盖两种时刻的查询窗并去重，非存在时刻隔离；禁止用服务器本地时区猜。 |
| 月份/年份分段订单号 | 当前月接口不能定位上月单，字典序不是时间序 | 保存平台保证的订单分段身份；按店铺本地日历生成相邻月窗后转 UTC，跨月重叠；详情/重同步携带原分段，不能按今日月份查询。 |
| webhook 漏投/重投/乱序 | 消息机制通常只保证至少一次且可能缺事件 | webhook 是加速发现线索，验签后先持久收件再确认，复用详情待办；P2 延后也不削弱轮询补查门禁。 |
| 窗口内订单量超吞吐 | 每周期七天重复拉取吃完配额，新增待办增长 | 设详情 QPS/最老待办/完整周期年龄门禁，压测七天真实规模；超载先告警和调整调度预算，不靠推进空水位假装追平。 |

**删除与 vanished：** 不从增量列表缺席推断删除。只有同实例、正确分段、凭据有效、权限确认后的平台明确删除标记/权威 not_found 才自动标记；不稳定平台建议间隔两次确认，但两次 404 不能替代权限/保留期校验。保留 vanished 原因、证据时间与最近成功观测，再出现经正常校验后清除标记并记恢复历史，原订单、items 和财务事实不删除。

运营“可见订单”统计沿用任务卡排除 vanished；历史成交/收退款统计保留该单并单独展示 vanished 数量，不把不可见等同于取消或退款。若产品仅保留一种统计口径，必须在接口说明中明确，不输出容易误解的净成交额。

**保证声明与验收**：在平台可完整枚举、详情最终可用、延迟处于回看/补查覆盖期、身份与时间契约可靠、处理吞吐足够的条件下，实现至少一次采集、一次业务效果及有界补齐；不能承诺未知平台的无条件不漏。门禁覆盖 ≥201 条续跑、页内第 200 条后崩溃、同时间戳跨页、空窗口推进、列表/详情时间差、超 7 天迟到、长停机、跨月/DST、详情长失败、误 404 与恢复；失败处置数量必须与“业务成功订单数”分列。

### Q6 售后与退款：M5 同步事实摘要，不悄悄扩成售后工作流

现状依据：M5 §3 明确“不做退款/售后流程（只同步状态）”；模型已有 partial_refund，未有售后实体；PRD EPIC-6 与 M6 §2 目前引用商品/报价，M5 是可选依赖，并无订单引用或退款流程要求。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 只存七态 | 仅更新 refunding/refunded 和原平台状态 | 最符合最窄范围，工作少 | 无法表达部分退款金额、取消未退款、退款失败恢复；后续无法可靠算实收 | 当前 status/history；无法满足 Q1/Q4 的摘要需求 | 0.5–1 人日 |
| B 同步售后摘要（推荐） | 保存售后状态、累计成功退款、可确认的行归属/类型/时间；无审批、退款指令或逆向物流流程 | 保护原订单快照，支持查询与金额说明；不要求 M5 建完整售后模块 | 多笔售后关联、过程详情和逆向物流不足；缺失只能标未知 | sales_order 摘要列、order_item 可确认的退款摘要、history 元数据、详情只读字段；不新增售后操作 API | 在 Q1/Q4 之上增加 1–2 人日 |
| C 独立只读售后单 | 新建 after_sale 与条目/退款记录，按外部售后/退款 ID 同步 | 多次售后、部分退款与退货路径可追溯；为未来流程打底 | 需要新的资源、接口、权限、幂等与测试；即使只读也扩出本卡列举的四表范围 | 新表、独立采集、详情聚合；须单独批准任务卡/需求 | 在 Q1/Q4 之上增加 5–8 人日；操作流程另估 |

**推荐 B 的边界：**

- 申请中、审核中、退款处理中不增加 refunded_amount_cents；只确认成功退款的累计额，重复快照直接覆盖经过校验的累计值，不把它累加。只有平台提供可靠增量退款 ID 时才可按唯一退款事实归并，不能靠“收到一次消息”计一次。
- 单笔订单可有多次部分退款；支付维度与履约维度独立，退款不等于库存回补/商品未发货/完成撤销。M5 不根据退款改 catalog 库存，退款摘要不构成账单对账或资金记账。
- 类型至少区别 refund_only（仅退款）、return_and_refund（退货退款）、mixed、unknown；若平台只有总体标志就存 unknown。退货是否寄回/签收与退款是否成功互不替代；B 不承诺每个售后单的物流状态，但可从可恢复 raw 查证。
- 外部 case ID、退款 ID、类型和可确认行金额在经过白名单过滤的摘要中保留；固定跨平台核心字段使用列，平台差异才进 ext。摘要不无限复制完整售后数组，也不存 PII；缺少逐单关联不编造。若验收要求逐售后单历史、退货数量或重试退款能力，应选 C 并另开卡。
- 部分退款后基础生命周期不回退，兼容投影按 Q1；全额退款额与平台最终退款状态同时确认才 refunded，金额缺失时不能把未知当全额。原始行 qty/价格/优惠维持下单快照，确认退款另列；不以商品当前价重算。

**M6 是否因此缺数据：** 当前 M6 不引用订单，故不建售后单不会阻塞已写明的分享/报价验收。若新增“从历史订单生成报价/分享”，必须明确引用原下单快照还是退款后净购买量、引用哪个聚合 version，且在创建分享时按既有白名单冻结；B 仅能提供已知摘要，不能支持完整售后轨迹。不得将 order_address、raw、买家内部标识或售后备注自动带入公开分享，也不能为潜在需求提前实现 C。

**验收门禁**：仅退款与退货退款不同摘要、处理中不扣款、重复部分退款、部分退款仍 shipped、全额退款、退款失败恢复、退款撤销证据、无退款明细时的 unknown、商品已删除仍可读原订单快照。

### 3.7 推荐组合、工作量与批准后的影响面

## 4. 未来 2 个里程碑的坑（只列不展开）

- **M6**：若新增订单转报价需求，必须选择原单快照或退款后净量，不能引用会变的商品当前值冒充历史成交。
- **M6**：同单号不同订单实例、明细行稳定 ID 与聚合 version 缺失，会使引用指错订单或失去可追溯性。
- **M6**：订单 DTO/raw/售后备注进入免登录分享快照会绕过 PII 二次授权。
- **M7**：凭据过期超过回看/平台保留期后自动恢复，若重置水位会永久跳过停机期间订单。
- **M7**：凭据轮换与详情待办跨片运行时，旧授权代次、店铺移交及密钥版本需要同时重验。
- **M7**：凭据刷新恢复后订单补拉洪峰会与商品同步竞争同店 API 配额，固定“200 条/run”不代表追赶能力。

## 7. 订单域与商品域的写入模式差异

“商品 upsert 单条”指一次来源裁决下的一条 listing 及其 SKU 集合，不能误解为商品只有一张表。现有 catalog.Upserter 已在调用者事务中锁父 listing、检查来源、写父与 SKU、写库存快照及重算 SPU。订单复用聚合原子性原则，但集合完整性、财务事实、地址与历史有不同约束。

| 维度 | 商品现有模式 | 订单应采用的模式 |
|---|---|---|
| 聚合身份 | tenant/shop/external_product_id；可挂接可变 SPU | tenant/shop/不可变订单实例 ID；展示单号非唯一身份，不以当前商品引用决定订单身份 |
| 子集合 | listing_sku 按 external_sku_id upsert，缺席项保留 | 完整 items 快照经数量、身份、金额及分页完整性校验后集合替换；省略 items 不等于空集合，部分详情不得删除旧项 |
| 替换方式 | SKU 行尽量原位更新 | 按稳定 external_item_id 原位更新/新增/移除缺席项，逻辑上整体替换，避免每次删光重插造成 item ID 变化；合法空集合须平台明确证明 |
| 历史语义 | 刊登属性可更新，当前 SPU/SKU 关系可改 | 下单商品标题、规格、成交价、数量及优惠是订单快照；商品删除/改价/归并不回写订单，关联 ID 可空 |
| 来源与并发 | 父 listing 来源校验后整组更新 | 同样整聚合校验；叠加平台版本证据、status 维度矩阵和聚合 version；人工/同步/resync/webhook 共用入口 |
| 私密数据 | 商品主要是可展示业务信息 | 地址字段加密、掩码/修订、raw 保护与解密审计共同构成边界；加密失败整聚合不提交 |
| 衍生副作用 | SKU 库存快照、SPU 价格/数量重算 | 状态决策历史、售后摘要、差异/分摊说明、必要 Outbox；不隐式变更商品库存、报价或钱包 |
| 金额 | 刊登价与 SPU 价区间 | 原单金额、已付、成功退款、币种、估算分摊明确分开；不平可见，禁止用当前商品价重算 |
| 重复应用 | 相同来源/checksum 跳过；新来源更新 | 相同业务效果不重复历史/退款/事件；同 raw 新 checksum 仍可重解释，历史明确记录映射纠正来源 |
| 删除与引用 | 刊登状态变化不自动删除既有 SKU | vanished 不删除主单/明细/历史，不当作退款；业务大表按既有规范不新增物理外键，依靠租户/店铺关系校验 |

**订单事务顺序与失败契约：** 外部列表/详情采集 → 完整原文受保护地先落 raw → 冻结 mapping 得到规范聚合并严校验 → 在调用者短事务内验能力/fence、锁订单身份与父单、比较来源/版本 → 同时写主单、完整 items、地址密文/掩码、维度历史/决策记录、应用凭据及必要 Outbox → 同页统计、处置与检查点提交。事务中没有 HTTP、对象上传或授权服务 IO；任何一步失败回滚规范聚合与检查点，已提交 raw 留待重试。

新单先分配稳定 order_id 才能建立地址 AAD；唯一键竞争后必须按已有订单身份重做判断，不可吞 DB 约束后在已失败事务里继续写历史。锁顺序统一为调度/job→run/检查点→订单父行→稳定顺序子行，所有写入口遵循同序；version 的读取与 CAS 在同一聚合边界。页面可包含多单，但每页总事务仍要满足 ≤2 秒持锁目标，不能把 200 单×数十明细机械塞进一个大事务。

父来源过旧、身份不可信、完整性不足、金额类型非法或地址加密失败时，禁止只更新某个 item/地址/状态；业务语义拒绝采用明确持久处置，基础设施错误回滚重试。详情读取需在同一一致性视图内取得父单、items、地址投影与历史（只读事务或 version 前后验证并重试），避免写入虽原子、多个独立 SELECT 仍拼出两个版本。统计不 join 明细后重复累计主单 paid，导出沿用已冻结投影。

**Gate A 验收建议**：聚合每阶段故障注入、唯一键竞争、手动与同步并发、子项缺失/空/重复/分页不完整、商品已删快照保留、加密失败零目标修改、历史/退款/Outbox 重投幂等、页事务回滚游标不动、跨租户引用和并发详情读取一致性。它们是批准后 M5 的验收要求，本次只完成设计文档核对，不声称已执行实现测试或迁移。
