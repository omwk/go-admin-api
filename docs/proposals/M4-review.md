# M4 设计评审

评审范围：`docs/milestones/M4.md`、`docs/03-data-model.md` §5、ADR-002/016，以及 M3 的 ingestion、connector、sync 和 `listing.ext._ingestion`。本文件给出评审建议，未改变既有规格；方案中的人日为增量估算，依赖实现前的人工作出裁决。

## 1. 规格冲突与歧义

| 位置 | 问题 | 两种理解 | 建议 |
|---|---|---|---|
| M4 §7.1、§11；§11 实现 prompt | §7.1 把商家编码相同列为自动归并；prompt 明确 T4.1–T4.3 只做人工归并。 | A：M4 全量交付编码自动挂接；B：M4 只提供人工归并，编码路径先给建议。 | 推荐 B。其误归并代价较大，且 T4.3 验收只验证人工归并；是否自动化列 Q1。 |
| M4 §7.3；数据模型 §5 product_spu | 列表要求 `price_min_cents/price_max_cents/sku_count`，数据模型没有这三列；M4 列表响应还要求 `shop_names`，表中也没有对应冗余字段。 | A：新增 schema 字段；B：先不物化部分响应值，或用受控聚合补齐。 | 推荐在实现前决定。字段不能在“只写 §5 已定义字段”的 M4 prompt 下自行新增；`shop_names` 应由 listing 关系查询得到或明确限制。 |
| M4 §7.3、§9；04-conventions.md §2.3 | M4 说 `page > 100` 改游标，但接口参数表只有 `page/page_size`，响应固定 `{list,total,page,page_size}`，没有 cursor 语义。 | A：深页返回 cursor 和下一页 token；B：拒绝超过 100 页并提示改用导出。 | 推荐 A，用同一筛选/排序绑定的 keyset token；常规分页响应和深页响应的兼容形状需在接口表补明。 |
| M4 §7.8；数据模型 §1 file_object | M4 要把进度写 `file_object.meta`、返回导出状态并清理过期文件；现有表只有对象、摘要、用途、上传者和创建时间，无 `meta/status/expires_at`。 | A：扩展 file_object 或新增导出任务表；B：只把对象记录当最终产物，另有任务持久化。 | 推荐 B，导出任务状态独立持久化，file_object 只登记完成文件；这需要批准明确的数据模型/迁移归属，不能假设已有 meta。 |
| M4 §7.4；数据模型 §5 platform_category/category_mapping | 同名规则的 `0.9`、父类继承的 `0.6` 没有阈值语义；`platform_category` 无启停/删除字段，类目消失后无法区分删除与暂时未拉到。 | A：`synced_at` 年龄表示过期，原行保留；B：加状态字段并更新映射生命周期。 | 首版推荐 A：按外部 ID 更新名称/路径，未观察到的行保留并标为“可能过期”，不自动删除/改映射。若 UI 必须有明确停用状态则需 schema 裁决。 |
| M4 §7.5；数据模型 §5 inventory_snapshot | “每次同步一条”未说明同步周期、无变化是否照写，以及 SPU 求和会重复计算；仅凭现有表无法推断平台/店铺间是否共用同一物理库存。 | A：保存每次成功同步的 listing_sku 观测；B：变化才写或定时降采样。 | 推荐 A 与任务卡一致，并明确汇总是“各平台 listing 报告库存之和”，不是去重后的实物库存。高频同步的降采样需另行裁决。 |

## 2. 实现风险（按严重度排序）

| 级别 | 触发条件 → 影响 | 建议规避方式 |
|---|---|---|
| P0 | 重放旧 raw 时只检查 raw 顺序，或把新 mapping checksum 当作来源更新 → 旧标题、价格、库存覆盖新数据，或新映射无法重算当前 raw。 | 分开判断来源新旧与映射新旧；同一当前 raw 的 checksum 改变允许重解释，低于当前来源顺序的 raw 整体跳过。父 listing 与 SKU 在同一事务/聚合锁内提交。 |
| P0 | Redis 共用锁租约丢失后旧 worker 仍写，或重放一次持锁过久 → 同店同步被饿死或过期 worker 覆盖新结果。 | 沿 ADR-016 每批最多 200 条，锁只覆盖一批；批次提交检查点后释放，有待跑同步先执行。续租失败取消任务；DB 提交前核验锁持有代次/检查点，避免只靠 Redis 租约形成时间窗口。 |
| P0 | 将批次 offset 作为检查点，或检查点与目标数据非原子提交 → 重复大量扫描或遗漏 raw。 | 固定 scope 和 mapping version；用 raw 分区键 `(fetched_at,id)` 做 keyset 检查点；目标 upsert、统计、检查点同短事务提交。 |
| P0 | 误归并自动生效 → 价格展示串货、库存跨商品汇总、SKU 绑定错误，并可能影响后续分享/报价。 | 先建议后人工确认；记录自动候选命中依据和人工撤销操作；以误合并率、受影响 listing/SKU、错误价格与库存差额计量，不能只报告总体准确率。 |
| P1 | 10 万 SKU 高频快照持续 30 天 → 行数、索引、WAL、备份和清理成本线性增长。 | 上线前按预计频率计算行数，运行后用 `pg_total_relation_size` 核实；按 `synced_at` 清理并监控删除滞后。 |
| P1 | service 同步维护 SPU 冗余字段但写入口不止一条，或批量 SKU 事务拆分 → 列表价格范围/数量与 SKU 不一致。 | 统一经过 catalog service 同事务更新；在数据库事务中重算受影响 SPU，而不是用不可靠增量；建立 SKU 增删、改价、listing 归并的事务测试。先裁定字段与计数口径。 |
| P1 | 类目全量拉取失败/分页不完整仍将未出现类目标成删除，或名称变化触发自动重映射 → 商品分类大面积漂移。 | 只有完整成功的同步周期才能比较缺失项；名称/父路径变化本身不覆盖人工映射；以稳定 external_id 作为映射身份。 |
| P1 | 导出没有固定过滤条件、排序与字段版本，或失败后遗留对象没有清理任务 → 下载内容无法复现、租户间越权或对象存储费用持续累积。 | 创建任务时持久化已校验过滤条件、排序、租户与字段版本；对象 key 用服务端生成 ID；失败/过期任务可重试清理；下载每次检查 tenant 和状态。 |

## 3. 方案对比

### Q1 归并策略：listing → SPU 是否自动？

误归并成本不应只看“错了几条”。建议记录期望损失：`误合并对数 × 受影响 listing/SKU 数 × 下游影响权重`，至少分开统计价格展示错误、库存差额、错误报价/分享引用和人工拆分工时。发布前用按平台、类目、品牌分层的人工标注样本测 precision/recall；若 300 个候选零误判，按“rule of three”其 95% 误判率上界仍约 1%，不等于零风险。实际财务损失与运营工时需从业务数据测量，不在本评审虚构金额。

| 方案 | 做法 | 优劣 | 影响面 | 推荐 | 工作量 |
|---|---|---|---|---|---|
| A：仅人工归并 | 后台选择 listing 建 SPU 或挂已有 SPU；自动路径只展示候选。 | 优：误合并可控、与 M4 prompt/T4.3 一致。缺：运营逐条处理，未归并数据无法共享 SPU 级属性。 | catalog merge API、权限、候选查询/运营流程；不改表。 | **推荐首版。** 标题+品牌只建议；人工确认才改 `spu_id`。 | 1–2 人日（候选理由/撤销审计另算）。 |
| B：商家编码精确匹配 | 规范化后按租户内唯一商家编码生成候选；仅编码唯一且关联关系无冲突时可自动挂接，其余转人工。 | 优：比标题规则精确、减少重复劳动。缺：编码可能为空、跨店复用或被商家重用；编码相同仍不证明是同一 SKU/SPU，误判仍会串价串库存。 | ingestion/catalog upsert；需要唯一性作用域、冲突池、撤销机制，可能影响 `product_sku.code` 唯一约束语义。 | **不建议首批自动写入。** 先影子运行并核验误判上界，达到业务阈值后再单独批准自动生效。 | 2–4 人日（影子统计与冲突处理）。 |
| C：标题+品牌自动规则 | 规范化标题、品牌后按相似度阈值自动挂接。 | 优：覆盖无编码 listing。缺：标题营销词、型号差一位、品牌别名和语言差异会造成高代价假阳性；规则漂移难解释。 | 文本规范化、品牌词典、审阅台、撤销/重算和离线标注集。 | **拒绝自动归并；只生成建议。** 误判代价最高且阈值难稳定。 | 3–6 人日（仅建议与抽样验证；自动生效另计）。 |

### Q2 重放执行器：50 万条如何安全运行？

M3 的现状：`catalog.Upserter` 将 `source_order/source_fetched_at/mapping_checksum` 写入 `listing.ext._ingestion`，映射不能覆盖此保留空间；来源新旧与映射版本新旧是两条轴。当前比较逻辑会先按来源顺序拒绝旧 raw，因此 M4 应只让**该实体当前有效来源**通过新 checksum 重解释，不能为了让历史 mapping 生效而让更旧 raw 抢写。`listing_sku.ext` 暂无同样元数据；必须确保父行仲裁通过后，父与全部子 SKU 一起原子更新，且旧来源整组跳过。

| 方案 | 做法 | 优劣 | 影响面 | 推荐 | 工作量 |
|---|---|---|---|---|---|
| A：小批共锁、同步优先 | 每批最多 200 条（沿 ADR-016），按 `(fetched_at,id)` keyset 读；每批在 `lock:sync:{shop}:{resource}` 下完成映射、upsert、stats 与检查点事务后释放锁；检查同步队列，有待跑同步先让出。 | 优：遵守 M3 锁与页语义，事务短，容易重试。缺：50 万条至少 2500 批，调度/检查点写放大，完成耗时受同步频率影响。 | replay worker、raw 读取端口、catalog upsert、`replay_run.stats`；锁按 ADR 不改。 | **推荐。** 恢复使用最后提交的 raw key，scope 与 mapping version 创建时冻结；严格按店铺+资源仲裁。 | 4–7 人日。 |
| B：按资源分区并行 | 把范围按 raw ID/时间切成互斥分片，各分片独立锁和检查点并行。 | 优：吞吐高、单分片失败局部恢复。缺：同 external_product_id 跨分片时目标写冲突；同步锁语义失效，排序和聚合 stats 更复杂。 | 新分片调度/锁身份、fence、scope 与统计格式，需验证同键不会并发乱序。 | 不推荐 M4；只有压测证明 A 不满足时再设计。 | 8–12 人日。 |
| C：长时间持有店铺锁 | 单次最多 50 万条期间一直持有同步锁，批次只保存检查点。 | 优：简单直观，正常同步不会和重放并发写。缺：单店可能被锁数小时，违反 ADR-016 明确否决整次重放持锁、同步优先的口径。 | worker 锁生命周期与同步延迟告警。 | **不采纳。** | 1–2 人日，但不满足已接受 ADR。 |

旧 raw 防覆盖建议：读取 raw 的来源序与 fetched_at；先与 `listing.ext._ingestion` 的当前值比较。新来源更新；同一 raw 且 mapping checksum 改变才重算；旧来源无论 checksum 如何均跳过。执行父行锁定后再写 SKU，整个商品聚合在同一事务。M3 的排序键是 `source_order`（当前由 raw ID 提供）和 `source_fetched_at`，M4 需测试同毫秒、跨分区、缺保留区元数据的旧行；缺元数据不能被假定为更旧或更新，建议仅允许正常同步初始化并记录需修复状态。不要把 raw 原文复制进 ext。

### Q3 类目映射与平台类目生命周期

| 方案 | 做法 | 优劣 | 影响面 | 推荐 | 工作量 |
|---|---|---|---|---|---|
| A：严格规则 + 每日同步 | 手工映射优先；规范化全路径同名且唯一才自动匹配（0.9）；父级继承仅给 0.6 候选，不自动覆盖；未匹配/多重匹配进池。平台类目每日完整同步一次。 | 优：可解释、低误映射；人工项稳定。缺：同名异义仍有风险；日同步会占上游配额。 | category worker、mapping service、未匹配池、`synced_at`；无需新增字段。 | **推荐。** 0.9/0.6 是候选置信分，不代表测得准确率；默认自动应用阈值建议仅唯一同路径且抽样验证后开放。 | 3–5 人日。 |
| B：模糊文本/路径打分 | 名称相似、父路径相似等特征打分；按阈值自动匹配并定期全量刷新。 | 优：覆盖改名、别名和局部路径差异。缺：词汇差异难校准；错误分类可能蔓延到商品筛选/运营分析。 | 词典/特征版本、候选解释、人工覆盖、阈值评估数据。 | 不推荐首版自动执行；可作为候选列表增强。 | 5–8 人日。 |
| C：人工映射为主、周更类目 | 所有新类目进入未匹配池；运营手工处理；每周同步上游类目。 | 优：误分类最低、API 调用少。缺：积压大、商品无类目时间长、运营负担高。 | 人工处理队列与类目同步调度。 | 可用于上游限流严格的平台；否则不如 A。 | 2–3 人日，另有持续运营成本。 |

覆盖优先级应为：`manual` 永远高于 rule/default；人工映射即使规则分数更高也不自动覆盖。类目改名或移动时按 `(tenant_id, platform_id, external_id)` 更新 name/path，映射仍绑定稳定平台类目 ID；若平台删除/不再返回，当前模型不能明确表达停用，首版保留旧行并按 `synced_at` 暴露陈旧提示，不自动重绑。建议 24 小时同步完整类目树；失败或不完整周期不用于推断删除。平台限流时退避，不为“每日”承诺覆盖平台配额。

### Q4 库存快照频率、容量与 SPU 汇总口径

| 方案 | 做法 | 优劣 | 影响面 | 推荐 | 工作量 |
|---|---|---|---|---|---|
| A：每次成功同步写快照 | 每次产品同步成功，按每个 listing_sku 追加 `available/reserved/synced_at`；每日清理 30 天前数据。 | 优：遵循 M4，趋势与来源观测完整。缺：快照量与同步频率线性增长。 | catalog 写入、清理任务、`idx_inv_snapshot` 与容量监控。 | **推荐 M4 验收口径。** 先实测，不偷偷降采样。 | 2–3 人日。 |
| B：变化写入、15 分钟去重窗口 | 数值变化立即留一行；无变化最多每 15 分钟留一次。 | 优：显著降容量，保留主要变化。缺：不再是“每次同步一条”，稀疏平台观测无法区分没变化和没同步。 | 同步 upsert 状态、快照去重状态/查询逻辑；现有模型不足以可靠判定无变化窗口。 | 若成本要求必须降采样，先修订规格并明确观测含义。 | 3–5 人日。 |
| C：按天留快照 | 每个 listing_sku 每天只保留一个日末值。 | 优：容量可预测。缺：日内库存波动完全消失，不能支持短期趋势调查。 | 时区、日末定义、唯一键与聚合查询。 | 不推荐与本里程碑“每次同步留趋势”目标并用。 | 2–4 人日。 |

数据量按 100,000 个 listing_sku 估算，行数分别为：每日 1 次，30 天 **3,000,000 行**；每日 4 次，**12,000,000 行**；每小时一次，**72,000,000 行**。这就是 30 天行数，不含 PostgreSQL tuple、索引、WAL、备份和副本空间；字节数必须在真实列/索引下用 `pg_total_relation_size` 测量，不能只按字段宽度报容量。建议实现前由业务确认预计同步次数，数据库压测按最坏频率造数。

SPU 汇总若按任务卡定义求和，应标注为“所关联 listing SKU 报告库存之和”，不是企业可售实物库存：同一实物在多店/多平台重复刊登会重复计算；还须区分 `available` 和 `reserved`，不能把二者再相加冒充可售量。建议只在有明确 SPU 归并关系的 listing 上汇总，未归并 listing 单独展示，不以 `product_sku.stock_cached` 再加一次。

### Q5 列表冗余一致性与 10 万商品深分页

| 方案 | 做法 | 优劣 | 影响面 | 推荐 | 工作量 |
|---|---|---|---|---|---|
| A：service 同事务重算 | listing/SKU 变更、归并/解绑时锁定受影响 SPU，在同一事务重算最小/最大价格、SKU 数与更新时间。 | 优：提交后立即一致，不需后台补偿。缺：批量写可能重复重算；字段口径不清就会算出错误值。 | schema（当前 §5 缺三列）、catalog service、所有 SKU 写路径和事务测试。 | **推荐。** 明确只重算受影响 SPU，并统一唯一写入口。 | 3–5 人日，不含 schema 裁决。 |
| B：数据库触发器维护 | 对 listing/listing_sku insert/update/delete 触发聚合更新。 | 优：覆盖所有写路径。缺：隐藏业务逻辑；并发聚合、批量操作和 SPU 归并的锁顺序难诊断。 | 迁移 SQL、DB 测试、触发器运维。 | 不推荐，当前架构要求事务边界在 service。 | 4–6 人日。 |
| C：异步重算 | 写入时标记 SPU dirty，由 worker 最终一致更新冗余字段。 | 优：写路径短，适合海量批次。缺：列表可能暂时陈旧，需要补偿与去重；数据模型无 dirty 状态/队列表。 | 新状态持久化、worker、重试/监控与响应语义。 | 不推荐 M4，除非性能测试证明同步重算超预算并批准模型变更。 | 5–8 人日。 |

字段口径待定：`price_min/max` 是活跃 `listing_sku.price_cents` 的范围，还是 listing 商品级价；`sku_count` 是 SPU 内 distinct `product_sku` 数、已绑定 SKU 数，还是平台 listing SKU 总数。建议用 distinct `product_sku` 计数，并让无绑定的 listing SKU 不混入内部 SKU 数；价格范围建议按活跃 listing SKU 真实平台价。M4 §7.2 规定展示取 listing 价，故推荐前者，但需补接口/数据模型说明。

深分页建议：普通 `page <= 100` 保持 offset 与现有 `{list,total,page,page_size}`；更深遍历返回/接受以 `(updated_at,id)` 为稳定 tie-breaker 的 cursor，token 绑定 tenant、过滤条件、排序和版本，不能把请求中的任意 SQL 值直接放入 token。若接口实现无法兼容 cursor，次选对 `page > 100` 返回参数错误并提示导出；不要继续执行大 offset。10 万商品并不代表深页应该扫描 10 万 offset，验收要分别测首屏、游标连续翻页和拒绝路径。预计 cursor API 与索引验收 1–2 人日。

### Q6 异步 CSV 导出

| 方案 | 做法 | 优劣 | 影响面 | 推荐 | 工作量 |
|---|---|---|---|---|---|
| A：固定筛选、keyset 流写对象存储 | 创建任务时校验并快照 filters/sort/请求者/租户；worker 每批 1,000 行 keyset 查询，CSV 行流式写私有对象；完成登记 `file_object`，presigned URL 有效 1 小时；对象生成 24 小时后清理。 | 优：内存有界、符合 M4 的批量/用时要求；任务可观测。缺：需要导出任务状态存储；对象上传失败需清理 multipart/临时对象。 | export API/worker、现有 `shop.ObjectStore` 端口适配、file_object、任务表或已裁定状态存储、定时清理。 | **推荐。** 24h 是建议的对象保留 TTL，需与业务下载窗口确认；下载签名 1h 不等同于对象 1h 删除。 | 4–7 人日。 |
| B：全量先写本地临时文件再上传 | 查询仍分批，但先落 worker 磁盘临时 CSV，完成后上传。 | 优：部分对象 SDK 只接受完整长度时更好接入。缺：要管理磁盘空间、崩溃残留和并发配额；大文件不具备纯流式。 | worker 本地目录、容量/清理与文件上传实现。 | 次选；仅在现有对象存储接口不支持流式写时。 | 3–5 人日。 |
| C：同步 HTTP 直接导出 | API 请求内查询并流式返回 CSV。 | 优：无任务状态与对象过期管理。缺：10 万行易超网关/请求超时；无法可靠重试或观测进度，不符合异步导出需求。 | HTTP 超时、客户端连接、列表查询负载。 | 不采纳。 | 1–2 人日，但验收目标风险高。 |

过滤条件快照至少包括 canonical filters、sort、字段集合/CSV 格式版本、请求人、tenant、创建时刻；worker 只能读取创建任务时授权范围，执行前仍验证任务所属租户。游标不由客户端提供。建议采用专用对象前缀 `exports/{tenant}/{export_id}.csv`，不使用用户文件名作为 key；对象私有，下载端检查完成状态与租户后签发一小时 URL。失败对象立即清理；完成对象 24 小时到期，DB 记录与对象删除分步可重试。`file_object` 当前没有进度、状态和过期列；M4 §7.8 的 `file_object.meta` 与 §5 不符，必须在人裁决后决定新增导出任务表还是获准扩展既有模型。ADR-016 的对象存储选型仍是待决项，但 M2 已有 S3/MinIO 兼容 `ObjectStore` 端口和 HTTP 实现，可先复用端口，不新增第三方依赖。

## 4. 未来 2 个里程碑的坑（只列不展开）

- M5：订单事件不能复用商品的来源新旧规则；状态机需避免历史重放倒退终态。
- M5：商品 SKU、订单明细与库存快照的跨资源关联需要稳定 tenant/platform/external identity。
- M6：分享/报价使用 listing 实价还是 SPU/SKU 参考价，价格来源和过期时间必须明确。
- M6：类目改名与内部类目迁移若需要审计历史，需要保留映射变更版本或事件。

## 6. M4 会暴露的 M3 遗留问题

| M3 现状 | M4 暴露点 | 建议处理 |
|---|---|---|
| `listing.ext._ingestion` 保存来源顺序、抓取时间和 mapping checksum；`compareSource` 先比来源顺序，后比抓取时间/checksum。 | 历史重放既要拒绝更旧 raw，又要允许当前 raw 换 mapping checksum 重解释；排序字段的优先级和同一 raw 身份需要边界测试。 | 保持来源排序与 mapping 版本分离；只对当前有效 raw 应用新 checksum；旧来源整组跳过。不要把 `raw_id` 或 fetched_at 单独当映射版本。 |
| `listing_sku.ext` 只有映射扩展字段，没有 `_ingestion` 元信息；SKU upsert 当前未执行来源比较。 | 若父记录被保护而子 SKU 不受保护，重放/同步可能出现父新子旧或子 SKU 回退。 | 父行通过来源仲裁后，父与完整子集合在同一事务更新；先评估是否把来源仲裁限制在父聚合锁内即可，若需子级元数据再单独评审，不擅加字段。 |
| M3 重放只覆盖 dead-letter/quarantine 单条重试，普通商品历史范围执行器留给 M4；raw 是只追加且按 `fetched_at` 分区。 | 50 万上限并不自动提供可遍历性：raw 分区 keyset、跨分区定位、scope 上界和归档读取会决定重放能否完整结束。 | 重放范围和 mapping version 入 run 时冻结；检查点用 `(fetched_at,id)`；当前只支持在线 raw 时明确限制 scope，不将不可访问归档计入可重放范围。 |
