## 2. 实现风险（按严重度排序）

| 严重度 | 触发条件 | 影响 | 规避 / 可验证门禁 |
|---|---|---|---|
| P0 | 按 C03 实现、明文存 secret 或把 hash 当无敏感性字段 | 验签失败，或 DB/日志泄露后可伪造请求 | Q2 的可恢复密文与 keyring；一次性下发、禁秘密重放；真实 HMAC 双密钥向量、并发创建最多两把 |
| P0 | 把应用 owner 当客户、复用 super/all 或缺 tenant 条件 | 客户查到其他客户/店铺订单及报价 | 独立应用主体、资源上限与当前 owner 权限交集；缺身份拒绝；列表/详情/计数/join/cursor/缓存均做跨客户矩阵 |
| P0 | 直接序列化内部详情、proxy 透传 JSON 错误与响应头 | 成本、PII、原文、凭据状态或供应链数据不可逆披露 | 公开 DTO 递归白名单、错误映射、响应头白名单；嵌套 canary 和 OpenAPI 精确字段对照 |
| P0 | 用客户 trace_id 扣费；重试生成新计费身份；先返回后异步记账 | 少扣、重扣或无法证明账单；异步缓冲断电漏计 | Q3 稳定服务端身份、持久意图/结果、投影去重；逐阶段崩溃注入及未知提交回查 |
| P0 | 轮换新 secret 顺带清 nonce、quota 或 client 限流桶 | 重放窗口和额度被重置，多 key 绕限 | nonce/配额按应用共享，轮换不重置；吊销后旧请求重放、并行 key、跨路由测试 |
| P0 | 首次准入/缓存命中后不再核验停用、移交、grant 或版本 | 旧权限/旧价长期可读，停用配置失效 | 主库准入、版本绑定缓存、长请求披露前复核；热缓存撤销、并发旧版本回填与依赖故障测试 |
| P0 | 可配 URL 被 DNS 重绑定/重定向、转发到本机 admin | 读取内网和元数据服务，绕开内部认证边界 | https、host 白名单、解析与实际拨号同一 IP 校验、禁非公网 IPv4/IPv6/映射地址；默认禁重定向，例外逐跳重验 |
| P1 | 日/月 quota 用异步日志 SUM，多个副本分别判断剩余 | 并发超发、Redis 丢状态后额度复活 | Q4 持久条件准入，与调用意图同事务；N/N+1、跨日跨月、重启、两 key 并发 |
| P1 | platform 401 在每个请求里触发刷新；unknown 当失败重试 | 一次性 refresh 被反复消费，凭据彻底失效 | M7 发送屏障/代次不变；请求不直接刷新；失效对外映射服务不可用，后台受既定维护授权约束 |
| P1 | 2MB 响应被截断仍先发 200；HTTP 写请求仅凭幂等头重试 | 客户拿到坏 JSON、成功收费但无有效结果、重复写上游 | 先有界缓冲/校验再发头；超限整次失败；写路由先证明端到端幂等，M8 不默认开放 |
| P1 | nonce/限流 Redis 不可用仍放行，或 SETNX 错误当重复 | 防重放/额度失效，或把依赖故障误报客户认证错 | 错误与“已存在”分开，503/10002 fail closed；有界退避、恢复检查，不用本地旧授权兜底 |
| P1 | 缺月分区、异步队列满、本地 fallback 盘满、迟到日志 | 用量不可查、重复入库或对账缺口 | 分区预建/覆盖告警沿用 ADR-016；持久事件可重投；饱和时拒绝新执行，脱敏与磁盘水位门禁 |

以上是设计风险及已查到的边界，未把未实现的 gateway 当作已存在漏洞；本次未执行攻击或容量测试。

## 3. 方案对比

工作量为熟悉现有代码的一名工程师的人日，包含相应契约、迁移和确定性回归；不同题有共享工作，不能直接相加。推荐项均须由人固化后实施。

### Q1 对外契约边界

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 内部 DTO 删除敏感键 | 管理详情序列化后递归删除 tenant/ext/成本等禁用字段 | 初期快 | 新字段默认泄露；嵌套/媒体/历史易漏，难形成稳定客户契约 | gateway 过滤器及每个内部 DTO 的隐式耦合 | 1–2；不推荐 |
| B 独立公开投影（推荐） | 单独 OpenAPI、显式 DTO 和逐字段映射；领域公开只读端口输出有界事实 | 默认不公开新增字段，演进可审核，M6 已有同类纪律 | 每个路由需维护映射和授权，不能直接挂管理 handler | gateway 公开 DTO/错误层、order/catalog 公共端口、bootstrap、独立 open OpenAPI | 3–5（首个业务读路由）；新增一种资源约 1–2 |
| C 可配置 schema 动态裁剪 | 管理员配置可见 JSONPath/schema，网关按配置选择字段 | 增加字段不必发版 | 配置等于安全代码，字段语义/价格资格无法仅靠 schema 判断；热更新扩大审核面 | api_route schema 发布流程、裁剪器、版本与审计 | 6–9；M8 不推荐 |

推荐 B；以下是**候选精确白名单**，人工批准并登记 OpenAPI 后才开放。所有嵌套对象适用同一规则；未列出的字段不输出，不用匿名嵌入、map 拷贝或透传 json.RawMessage。

| 对象 | 候选允许字段 | 边界 |
|---|---|---|
| 通用信封 | code、message、data、trace_id、可选 request_id；错误可选 details | details 只列获批参数名/限额种类/复位时间，不带输入原文、SQL、URL 或内部身份 |
| 商品基本信息 | id、title、subtitle、brand、status、updated_at、skus | id 暂建议沿用获批规范层 SPU/SKU ID、每次核验成员归属；这是待批例外，ID 不承担授权功能 |
| 商品 SKU | id、title；有独立价格授权时才加 display_price_cents、show_price、currency、moq、stock_display | 无价格绑定时整个价格组省略；库存只给“充足/紧张/缺货”，图片/描述/属性须另批，先不输出 |
| 订单状态首条能力 | id、order_no、status、updated_at | 默认只做这一最小订单能力；order_no 为展示字段，不作平台实例身份或授权键 |
| 完整订单候选能力 | 上行字段，加 currency、total_amount_cents、paid_amount_cents、refunded_amount_cents、item_count、placed_at、items | 不随状态路由自动开放；需要独立资源授权和契约批准，金额沿用 M5 事实，不做“最新平台”承诺 |
| 订单明细候选 | title、sku_title、qty、currency、price_cents、discount_cents、amount_cents | 只随已批准完整订单能力开放；不含平台 item ID、采购成本或分摊证据 |
| 网关内置查询 | usage：UTC 窗口、calls/error_calls、实际 units/amount_cents、as_of；routes：code/name/method/path/公开 schema/限额摘要 | 只查当前应用；不返回 client/tenant 内部 ID、owner、上游 URL、秘密或其他应用用量；balance 依 C09 |

统一禁止：tenant_id、ext（含 _ingestion）、cost_cents/成本、raw/raw_id/映射 checksum、平台与外部实例 ID、shop_id/owner_user_id、credential 引用、内部状态/备注/差额诊断、精确库存；订单 receiver 连同掩码字段首版整体省略。客户专属价格只从获批 customer/价目表/成员绑定解析，不把商品原价当默认专属价，也不复用 M6 浏览 Cookie 为 API 授权。

治理与统一协议：

1. 领域负责人确认字段业务含义，数据负责人批准价格/PII 分类，网关负责人维护公开 OpenAPI 和映射清单，评审人核对每次变更；内字段新增默认无外部变化。公开 schema 使用 additionalProperties=false，并对实际响应做递归精确白名单断言。
2. 新字段即使“向后兼容”也须字段级评审；记录来源、资格、可空性、枚举、版本、缓存/计量影响。敏感新增、语义/类型/删字段须新版本或显式迁移期，不能仅改 DB schema 配置就发布。
3. HTTP 与五位 code 双重语义；成功 code=0，错误由 §7 映射，不转发 AppError.Details/Cause。分页保持 list/total/page/page_size，默认 1/20、上限 100，排序只允许公开字段并加 ID 稳定次序。
4. offset 扫描不超过 1 万条；首版不宣称支持全量遍历。超过阈值返回 400/10001 并给固定说明；以后提供独立 cursor 契约，绑定应用/租户/筛选/排序/版本/有效期，重新验权，不能复用管理端游标或把 cursor 当固定快照。
5. 时间统一 RFC3339 UTC、范围含头不含尾，空业务时间为 null；金额 int64 分并带 currency，禁止浮点和跨币种合计；列表默认 created_at desc、id desc，业务例外须写入该路由。
6. nonce 是单次传输防重放，不是幂等键。写接口接受可选 Idempotency-Key；作用域为 tenant+client+route+method+key，绑定规范化请求摘要，24h，异请求同键 409/10006，进行中 409/10004；重放前重验权限。
7. secret 签发不缓存明文、不重放秘密，只返回“已交付”回执；丢响应需轮换。未来写业务的幂等 key 必须纳入获批签名协议并透传至受支持上游，不能擅改现有六段签名串。GET 的默认网络重试仍是新请求；需要避免响应丢失后再次计费的路由，可另行批准同样的显式幂等重放契约。

### Q2 认证与密钥生命周期

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A HMAC + 信封密文（推荐） | 公开 app_id，随机 secret 本地签名；服务端解密有效版本验签，保留 hash/前缀作指纹 | 保留 PRD/现有签名协议，有消息完整性和 nonce 防重放 | 必须纠正哈希存储结论；增加受控解密与退钥责任 | api_client_secret 密文/版本、crypto keyring、管理接口、SDK 向量/失效审计 | 4–6 |

推荐 A 的明确边界：

- app_id 为公开 ULID；secret 由 crypto/rand 生成 **32 字节、256 位随机熵**，按既定标准 base64 编码（44 字符，含 padding）；算法标签和环境标签不计熵。列表只显示已有 6 字符 secret_prefix 和 secret 行 ID。不在 URL、query、日志或示例夹具放真实值。
- 签名密钥按 M8 现有 openssl 示例，使用下发 base64 文本的 UTF-8 字节；客户端不得擅自 base64 解码后再签名。SHA-256 指纹也针对这份规范文本，密文恢复后应得到完全相同的文本；该口径须写入双端测试向量。
- 哈希保留 SHA-256 指纹；新增的密文信封包含 nonce/key_version，AAD 绑定用途、tenant/client/secret ID/版本，复用现有 Sealer/keyring，不新增依赖。数据库与备份不存明文；解密仅在验签内存中，不跨请求长期缓存明文，不认为内存清零能保证 Go 所有副本被擦除。
- 最多两把 active secret 由应用行锁/事务保证，不能“先数后插”；当前 HMAC 头没有 key ID，按固定上限尝试两把并用 hmac.Equal，记录匹配的 secret 行 ID 更新 last_used_at。应用、有效期和 revoked 状态每次在准入处核验，到期立即拒绝，不等清理任务。
- 日常轮换建议每 90 天：创建新 key → 客户验证 → 默认 24h 双 key 重叠（可缩短，建议最长 7d）→ 旧 key 定时过期/主动吊销。出现第三把前必须明确淘汰一把；禁止自动延长旧 key 有效期。secret 初次下发 no-store，一次性回执遵循 Q1。
- 泄露应急建议 SLO：收到确认告警后值班者 **5 分钟内完成停用应用或吊销受影响 key 的提交**；提交 t0 后新准入必须读到持久门禁，正常环境目标 ≤1s，不接受仅靠 30s TTL。Redis/DB 故障时 503 拒绝服务，不声称吊销已完成；已准入在途请求单列为不可追回边界。
- 应急流程：先吊销/停用 → 记录密钥 ID/时间/操作者的安全审计 → 换新并验证 → 按应用/路由/时间核查滥用与账务 → 明确批准后恢复；凭据/备份解密密钥泄露时同时轮换相关 keyring 版本。审计不含 secret、完整签名或请求体。
- 支持每应用两把 key，轮换不重置应用限额/nonce/配额；IP 白名单首版沿用 api_client 的 **应用级 inet[] 精确 IP**，空集合为不限。若要 CIDR 或每 key 不同白名单，须另批数据模型。来源 IP 用已有可信代理解析器，客户端自行提交的 X-Forwarded-For 无效，IPv4/IPv6 规范化一致。
- 首版安全总额按应用共享；按 key 限流可作为额外收紧维度，不能代替应用桶。若本轮启用每 key 配置，需新增相应 QPS/burst 策略字段；无该配置时两把 key 共享应用上限即可，不能对外声称已有独立 key 配额。
- 严格保留 app 状态 → 时间窗 ±300s → SETNX nonce TTL 600s → HMAC → IP → 路由授权的既定次序；SETNX 依赖错误为 503，真实已存在才是 80103，验签失败仍保留 nonce。nonce 按应用共享且不随轮换清除。限制头/nonce 格式、请求体 1MB，认证前另有入口滥用预算。
- 签名向量必须覆盖原始 PATH、空体/空 query、空值、空格/+/%、UTF-8、非法编码及代理重写；重复 query 键当前无明确规范，建议首版拒绝，裁决后写入 SDK/OpenAPI。不得一端排序多值、另一端取首值。客户端重试必须换 timestamp/nonce 后重新签名。

### Q3 计量点与准确性

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 仅异步日志 | 按原卡缓冲 500 条/1s，失败落本地文件，再做日聚合 | 延迟低、改动少 | 内存窗口/SIGKILL/节点丢失可漏计；重投可重复；不能作收费事实源 | api_call_log、flush/fallback、usage 查询 | 2–3；仅接受免费期有限日志保证时可选 |
| B 持久调用意图与结果（推荐） | 准入先落唯一调用身份，执行后短事务提交有界结果/计量事件，异步生成查询日志 | 明确计费与响应边界，崩溃可恢复、可去重，便于 M9 接账本 | 多一次或两次 DB 写；需未知结果状态与补偿，不能许诺跨网络 exactly-once | 新非分区调用/结果载体、outbox/去重、日志投影、M9 hook、quota 准入 | 5–8 |
| C 专用持久日志系统 | 执行前后同步确认写入外部持久队列/日志，再由消费者记账 | 高吞吐、服务实例易扩展 | 新基础设施、跨存储协调与运维复杂，仍需事务和去重；新增依赖须批准 | 队列服务、部署、生产者确认、账务消费者、灾备 | 9–14；当前不推荐 |

推荐 B，计费单位先选**一次成功的逻辑调用**（per_call=1；package 使用路由 units_per_call），字节/记录数只观测。按记录数计费需定义分页/重复记录/部分成功，按字节需定义压缩前后/错误体，均另开契约，暂不以 page_size 或 Content-Length 推算收费。缓存命中仍交付服务，建议同价一次；免费内置路由永不收费。

“成功”定义为网关已经形成获批的最终 2xx、有界完整结果且持久化可重放，不保证客户 TCP 已接收；204 也可成功，3xx 不自动算成功。HTTP 送达与 DB 提交不能组成一个原子事务，不能宣称“每个收到响应的客户且仅这些客户被扣费”。

| 场景 | API 调用配额 | 收费/逻辑计量口径（M9） |
|---|---|---|
| 签名/IP/路由拒绝、请求格式错误、QPS 超限 | 不占 | 0；安全事件不混成有效客户调用 |
| 准入后最终 2xx（含合法空列表、缓存命中） | 占 1 | 一次成功；route_version/价格/单位按首次准入冻结 |
| 网关内部 GET/HEAD 自动重试一次后成功 | 整个逻辑调用占 1 | 只算一次；另记 attempts，不把每次平台发送计给客户 |
| 内部重试耗尽、上游 4xx/5xx、熔断、解密/依赖错误、超时 | 占 1 | 0；已预留金额/套餐单元释放，平台自身成本由我们承担 |
| 幂等 key 命中已完成且重新验权通过 | 不新增 | 重放同一结果、不新增账；传输尝试仍受 QPS 限制 |
| 相同幂等 key 不同摘要 / 正在执行 | 不新增 | 409/10006 或 409/10004，不重复发上游 |
| 客户重新签名重试，无幂等 key | 新准入占 1 | 按独立调用判断成功，可能再次收费；SDK 必须明确说明 |
| 超时/断连发生在成功结果持久化之前 | 已准入则占 1 | 默认失败/未决，不补成收费成功；写上游结果不明需人工/上游对账 |
| 结果/账务终态已经提交后响应丢失 | 不回滚原准入 | 原成功仍收费；凭显式幂等契约重取原结果，不另收费 |
| 日志投影重投、补偿重复执行 | 不新增 | 同事件/同调用去重，账务只能一个 commit 或 release 终态 |

推荐事务与恢复顺序：

1. 通过认证/授权/QPS 后生成**服务端唯一调用 ID**，持久绑定 tenant/client/route/version、请求摘要、可选幂等 key、准入 UTC 时间和价格政策；短事务内做日/月 quota 条件占用与意图写入。调用方 trace/request ID 不参与全局去重。首次调用的服务端身份须在所有重试/补偿中稳定。
2. 业务读取或平台网络在该事务之外执行，遵守传入 ctx/截止时间；只读查询可用领域现有一致视图，不持 DB 锁等待网络。先形成有界、脱敏、可验证的完整结果，禁止流式发出成功头后才决定计量。长请求的权限/停用复核须先于成功终结，不能先扣费再因已撤权拒绝披露。
3. 结束短事务写最终结果/摘要、成功或失败状态与唯一计量事件；M9 在该终结事务中通过账务端口完成 commit/release 与 outbox。freeze 在执行前的独立短事务完成，失败时不发上游；DB 提交确认不明须按调用 ID 回查，不能新建请求重扣。
4. 成功提交后才发送成功响应；终结事务失败则返回固定 503，不返回内存中的成功体。已写入的终态结果可由受同等授权的重放路径获取，TTL/存储清理与 24h 幂等窗口一致；不将含秘密/PII 的结果存入该载体。
5. api_call_log 每 500 条或 1s 生成是观测投影，不是唯一账务事实；新增非分区调用唯一约束/消费去重记录解决跨月重投，不能只往分区表补一个无法全局唯一的 ID。匿名认证失败另存有界安全元数据，不伪造 client_id/route_id 来满足日志列。
6. 补偿扫描建议每分钟处理过期 intent/未决终态及未投影事件，按租约/代次推进；能从持久结果证明成功才补提交，无法证明则释放冻结并告警，不能重发未知写上游。M7 的 unknown 原则只作为恢复纪律参考，不调用凭据刷新状态机。
7. M8 强制免费，actual cost_units/cost_cents=0、billed=false；候选 billable_units/attempts/route_version/outcome 等需独立字段/事件，不用 billed 假装已收费。M8 /usage 可查自身调用日志并返回真实 as_of/延迟，不能提前依赖 M9 usage_daily；1s 可见目标仅适用于健康 flush 路径。
8. M9 每日对账同时检查调用事件、quota 计数、wallet_txn、套餐扣减及日志/usage 投影。按首次 called_at 的 UTC 日期归属，跨午夜晚完成会回补原日；原规格“调用日 vs commit 创建日”直接相减会产生假差异，须同一账务归属键比较并重算迟到窗口。

计量大小建议统一为网关读取/生成的解压后 HTTP 实体字节（不含头），仅作观测；传输层压缩字节若另采集应单列，不能混作费用。请求/响应摘要若获批新增，明确定义规范化、算法与用途；幂等摘要用带服务端密钥的摘要并绑定作用域，避免低熵内容被离线猜测，不进入客户响应或全文日志。

故障验收至少覆盖：执行前、返回后终结前、终结提交后发头前、flush 后确认前各崩溃；磁盘/DB 不可用、事件重投两次、跨月补写、提交确认丢失、同幂等键并发、客户端伪造同一 X-Request-Id。通过这些才能声称可恢复，不能用优雅退出代替断电验证。

### Q4 限流与配额

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A 单实例内存桶 + 日志计数 | 每进程限流，异步日志聚合判断日/月额度 | 简单 | 多副本可超发，重启额度清零，违反既定 Redis 令牌桶 | gateway 进程状态、日志查询 | 1–2；不推荐 |
| B Redis 令牌桶 + 持久 quota（推荐） | QPS 原子桶做突发保护，PG 原子日/月准入与 Q3 意图同事务 | 符合既有算法，硬配额跨进程/重启一致，单位不混用 | Redis 与 PG 均影响可用性，需要版本/周期与并发测试 | Redis Lua、api_client/route 策略、非分区 quota 载体、错误/响应头 | 4–6，与 Q3 有重叠 |
| C 独立网关统一准入 | 用独立入口服务集中管理多层限流/配额 | 跨多服务治理方便 | 新服务/组件和账务协调成本，超出当前单体需求 | 部署拓扑、配置发布、Redis/账务接口 | 8–12；后续规模需要时再议 |

推荐 B 的层次如下；并非把六层都宣称为当前卡已确定要求。

| 维度 | 推荐 key/来源 | 首版判断 |
|---|---|---|
| 全局 | rl:global，进程间共享同一 Redis | 既定必做；认证前另有全局/IP 滥用保护，避免随机 nonce/大体积请求压垮验签 |
| 租户 | rl:tenant:{tenant} | 单租户下可等价使用全局上限；预留维度，若启用独立阈值需配置并批准 |
| 应用总量 | rl:client:{tenant}:{client} | 补齐 PRD“应用级”；两把 key/多个路由共享，避免拆调用绕过总上限 |
| 路由 | rl:route:{tenant}:{route} | 既定必做；匹配到具体配置版本后取 rate_limit_qps/burst |
| 应用×路由 | rl:client:{tenant}:{client}:route:{route} | 既定第三桶；QPS 取有单位的一组 QPS 配置，不与 daily/monthly 数字取 min |
| key | rl:secret:{tenant}:{client}:{secret_id} | 可选额外收紧，需 Q2 的显式配置；不能替换应用限额 |

算法使用 Redis Lua 令牌桶（tokens/last_refill），统一 Redis 时间、明确单位/精度、有限 burst、闲置 TTL；同一次限流决策先检查所有适用桶，通过才一起扣减，拒绝不部分消耗业务桶，入口滥用桶独立。当前单 Redis 可原子完成；未来 Redis Cluster 的全局桶与租户桶跨 slot，不能直接复用同一多 key 脚本并宣称仍原子，届时另议部署。

当前表只有 route 级 QPS/burst；应用总桶建议先用配置中的统一应用默认值，若支持逐应用覆盖再新增相应字段。应用×路由桶首版可沿用 route 的 QPS/burst，独立覆盖同样需获批字段；每日/月次数不能换算成每秒速率。每 key、独立租户策略也是显式可选项，不暗塞进现有 JSON schema 或 quota 列。

日/月 quota 是**准入逻辑调用数**，与成功收费单位、套餐余额分开；0=不限，UTC 00:00/每月 1 日复位。准入后上游失败也占一次 API 配额，拒绝/幂等重放不新增；套餐只在成功时消耗。quota 原子检查日、月并占用，与持久调用意图同事务，任何一项不足整次失败。Redis 可缓存显示余额，但不能作为 Redis 丢失后重新赠送额度的事实源；配额降低至已用量以下时立即拒绝新增，不能清零已用量。

瞬时限流：429/10005，Retry-After 为所有阻塞桶等待时间的最大值向上取整、至少 1 秒；X-RateLimit-Limit/Remaining 指**实际起约束的桶**，多桶同时超限时选等待最长者，文档标明 limit_type，不能混报全局与路由余量。日/月耗尽：429/10005，details.limit_type=daily_quota/monthly_quota，Retry-After 指向最晚相关复位时间，禁止 SDK 紧循环。M9 余额不足为 402/90102，套餐用尽为既定 90201；是否回退 per_call 须客户/管理员显式政策，不能把 API 日配额耗尽映射成套餐耗尽。

所有 429 写安全调用记录且 billed=false；Redis 失败为 503/10002，quota PG 失败为 503/10002。使用假时钟/固定令牌确定性测试边界与 N/N+1，并验证两 key、多个路由、两个实例、UTC 日/月切换；严格吞吐/耗时断言走显式容量开关，遵循 AGENTS 的 CI 纪律。

| B 显式实时路由 | 独立代码/路由声明 live read，经获批店铺映射和目的限定端口调用平台 | 可满足特定实时读取 | 依赖平台限额/凭据/延迟，增加失败和刷新协调成本 | 新调用能力、shop 公共使用端口、connector、中立错误、共享平台桶 | 5–8，需新增授权/审计契约 |
| C 每次读取都同步刷新再查 | 客户请求触发同步/刷新并等结果 | 表面上接口简单 | 放大流量、超时和锁争用；与 M7 unknown/发送屏障及 M5 冻结同步边界冲突，实时也无法保证 | gateway/sync/shop/refresh/订单状态的广泛耦合 | 8–12；不推荐 |

推荐 A；HTTP 第三方代理仍按 M8 范围实现，它与“订单查询自动回电商平台”是两种路由能力。A 不把内部 updated_at 当平台观测时间：字段叫 updated_at 就只承诺规范记录更新时间，只有领域端口提供可靠观测时间才新增 as_of；M5 的 A/B/C 能力、回看窗口、迟到与 vanished 规则不因 API 发布而升级为强一致保证。

凭据与异常处理建议：

1. 独立 HTTP 代理使用管理员为该上游配置的专用秘密引用，经受控信封解密后只注入获批上游头；客户 Authorization/Cookie、X-App-*、X-Signature 不透传，上游 Set-Cookie/WWW-Authenticate/内部诊断头不回传。需解决 C14 的持久配置缺口，不混用 shop OAuth 版本。
2. 若以后选 B，按获批路由绑定 shop/credential，bootstrap 重新验证 tenant/client/route/resource grant、当前所有者、current_version_id/代次和调用目的；签发不可反序列化的**网关调用能力**，只能读取/执行该路由需要的方法。现有 CredentialRefreshAccess 只维护刷新运行，WorkAccess 只给同步，二者都不能伪造来适配 HTTP 请求。
3. 业务使用当前已发布且可用的 access 版本；refreshing 时未过期的已确认 access 可继续用，沿用 M7b 既定规则；不得读取 consumed 暂存、unknown 结果或旧 retired 版本来“凑成功”。凭据使用审计失败则不发平台调用，审计只含应用/路由/调用/版本引用。
4. 平台 401/明确凭据失效：客户收到平台无关的 502/80301“服务暂不可用”，不返回 30302/30303/60401、needs_reauth、哪个店铺或 token 状态。若后台已经确认是短暂恢复/维护窗口，可统一 503/80301 并给有依据的 Retry-After，不声称立即重试一定成功。
5. 平台 429 是我们的上游依赖限额，映射 503/80301；客户自身 QPS 超限才是 429/10005。平台超时为 504/80302，5xx/熔断为 502/80301；Retry-After 仅接受合法、有界值，未提供可靠恢复时限则不伪造。
6. 网关不在客户请求中消费 refresh token；只能由 M7 已批准的维护授权/协议/独立 grant 门禁统一调度，临时失败仍按既有五次预算、unknown 先对账。增加 gateway 来源触发也须先补端口与去重策略，不借同步过期事件伪造来源。
7. 实时路由若获批，与同步共享“平台账号/授权”级上游令牌桶及预算，不因每应用一桶放大平台请求；有界 GET/HEAD 重试一次，所有重试在路由总截止时间内，POST 不凭一个头自动重试。既有连接/读预算与 DB/Redis 预算均要计入总时限。
8. 默认禁止带 userinfo 的 URL、客户控制 host/port、重定向与内网例外；解析、Transport 拨号、重试逐次做目标地址检查，IPv6/映射地址也覆盖。请求上限 1MB、响应上限 2MB，同时约束传输与解压后的大小；超限返回统一上游错误，完整结果检查前不得发送成功头或收费；平台原始 body 不进客户错误或应用日志。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |

内置自查建议作为固定的“当前应用自身”能力：仍执行 HMAC 前五步和实时应用状态门禁，但不要求管理员为其创建动态 client_route grant，不走动态路径匹配；使用独立免费查询预算。动态路由才执行第六步的路由 grant 校验，该内置例外须随 Q6 写入契约。

独立栈建议按职责执行：入口方法/路径/大小/滥用预算 → 固定 HMAC 六步校验 → 应用主体及实时资源授权 → 适用限流桶 → 幂等/配额/持久意图 → 获批公开 handler 或受限代理 → 结果投影/计量终结 → 客户错误映射。Trace/Recovery 等公共能力可复用；JWT/LoadIdentity(sid)/人类 RequireRecent 不应通过伪造用户塞给 open。管理路由仍用 M1 JWT/RBAC/数据范围，网关管理权限使用集中三段码 registry，不将“list/create”缩写直接入库。

授权须同时满足：client/key 有效、route active 且 public、client_route active/未到期、资源属于运行 tenant、当前 owner 仍拥有相应业务权限/数据范围、资源在**该应用显式上限**内。api_client.owner_user_id 只作管理归属，不是终端客户证明；owner 的 is_super 不扩大应用边界。建议新增应用资源授权载体（如 api_client_resource_grant，绑定 tenant/client/资源类型/资源 ID/状态/版本），配合必要的 customer/价目表批准关系；由领域端口验证关系，不对客户端开放“任意 customer_id/shop_id”筛选。若不批准新增模型，M8 不开放订单/商品能力。

不能直接拿现有 order.QueryService 的 user 参数冒充应用。应由领域提供应用用途的只读契约，bootstrap 将验证后的应用能力转换为严格查询谓词；跨模块只调用公共端口，不 import repo/model，不改人类 scope.From 的“缺身份拒绝”语义。对所有列表/详情/计数/明细 join/缓存/分页纳入已有 ScopedQuery/DryRun 与跨 owner/跨客户矩阵，公开缓存键包含 tenant/client/resource grant 代次/route_version/DTO_version/筛选。

路由配置只接受显式注册的 handler_key；数据库新增未知 key、private、none、重复 method/path、与内置/系统/webhook 冲突路径均拒绝。精确优先、其次限定边界的 /*，不允许正则/跨段前缀误匹配；方法白名单和版本固定。独立 http 代理也不是自动公开：host、请求/响应 schema、公开资格经批准才可 active，新增 schema 不能突破编译时公开上限。

管理员可不重新部署地启停**已登记**路由、暂停应用、吊销 key/授权、调整获批范围内限额；不能靠热配置创造新 handler 能力或新增公开敏感字段。更新用 version 做乐观锁并写安全审计/持久失效事件；路由目录元数据可缓存 30s，但每次 dispatch 前读主库状态/版本/授权门禁，版本不符刷新，依赖故障 fail closed。停用提交后新准入拒绝；长请求披露前复核，在途不可回收边界明确。失效重试使用现有 outbox，不把 DB 已提交的配置更新因缓存失效错误谎报成未提交。

M6 的公网 allowlist 只承认 share 路径、GET/POST 且不接受 query；需**单独评审 open 入口发布规则**，保留管理/系统/运维拒绝和可信代理约束，不用放通 /api/**。实际路由、公开注册表、OpenAPI、入口规则应双向对账；既有全局 CORS 未列 HMAC 头，建议服务器到服务器首版不承诺浏览器 SDK，也不把长期 secret 下发网页，若需要浏览器调用另批边界。

实施估算：维持“免费网关、一个代理、明确日志损失边界”的收窄版约 12–18 人日；推荐的持久计量/硬配额/强吊销与一条最小业务读能力约 **24–36 人日**（不含 M9 扣费及真实平台实时回源）。建议分认证与应用、路由与代理、计量与额度、业务公开能力四批，各自验收；具体拆卡/范围由人固化，不在本评审代改任务卡。每批验证包括 OpenAPI/路由双向守卫、幂等/越权/失效/故障测试；新增 Gateway 域集成测试须恰好进入一个 CI 分片，race 由 CI 验证，满规模限流/延迟测试用显式开关。
