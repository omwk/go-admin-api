## 2. 实现风险（按严重度排序）

| 级别 | 触发条件 | 影响 | 规避与可执行验收 |
|---|---|---|---|
| 高 | owner 条件只加列表，不加 count、详情、写入或子查询 | 行数据越权、数量泄露、越权修改 | Q1 的逐方法逐分支 DryRun + reflection + 跨 owner 实测；写入同时校验目标与新归属 |
| 高 | 把 JWTAuth 当完整 LoadIdentity，或缓存用户状态 5 分钟 | 停用账号仍能调新管理端点；超管绕过错误扩散 | 每请求读当前用户状态；数据 scope 独立加载；is_super 只跳 RBAC |
| 高 | 角色变更提交后请求取消、进程退出或部分 INCR 失败 | 新权限已落库，旧授权仍命中 | Q2 写清非原子窗口、失败集合、告警与 TTL 边界；M3 才提供持久补偿 |
| 高 | 清理 refresh 历史、只查未过期行再强踢，或缓存「sid 有效」 | 丢失持久证据、踢出后错误放行 | Q3 保留既有无行拒绝与 DB 查询；覆盖过期行、无行、Redis 清空、刷新竞态 |
| 高 | 两个请求同时移动 A 到 B、B 到 A | 各自预检通过，最终成环；子树静默消失 | Q5 在同租户树写锁内重新读图、验证并写入，测试并发交叉移动 |
| 高 | 重跑当前种子，给已有角色重新插回被管理员撤掉的授权 | 权限意外恢复，且新缓存未失效 | Q6 明确初始化与升级语义；已有角色不自动补权；种子变更也进入同步失效 |
| 中 | LEFT JOIN 扩大行数、用户状态与角色权限投影混成一条查询 | total 错、分页重行、角色×权限乘积扩大 | 独立 count/授权投影；以受保护实体 ID 去重；冷缓存基数测试 |
| 中 | INCR 版本键丢失而旧版本缓存仍在，或从备份回退 | 版本复用导致旧授权重新可达（ABA） | 版本缺失走 DB，禁止当作 v0 命中旧缓存；恢复时成组清理授权缓存并隔离旧回填者 |
| 中 | 手写权限码、文档只检查响应、不核对鉴权声明 | registry、路由、文档各自正确但相互漂移 | Q4 把方法+路径+单个完整权限码做机器比对，未声明管理路由拒绝注册 |

## 3. 方案对比

### Q1 数据权限的声明方式与漏套检测

**现状**：`internal/kernel/db/scoped.go:19–45` 在建立查询时调用受信 Scope；没有身份策略就保存错误并禁止执行。它还允许通用 Where/Joins，缺少明确 alias、受限子查询和去重计数能力。现有 bootstrap 中 auth/profile/seed 是专用适配器，不是已完成的业务数据权限实现。

| 方案 | 做法 | 优点 | 缺点 | 对已有表与接口的影响 | 工作量 |
|---|---|---|---|---|---|
| A 可信查询声明 + 受限门面（推荐） | repo 方法选择内部查询声明 ID；声明包含根实体/固定别名、tenant 列、owner 映射、dept 来源、关联保护规则；bootstrap 绑定 Scope | 归属可见、别名不猜测；适配现有门面与 depguard | 要补门面能力与查询登记；同表不同 alias 需要不同声明 | 不改表/HTTP；扩展内部查询端口和装配；声明放模块内部公共类型，repo 不导入 kernel/db | 1.5–2.5 |
| B 每方法专用查询能力 | bootstrap 为每种列表/详情/写入提供封闭查询端口，SQL 内明确范围；不向业务 repo 暴露自由组合 | 与 M1a 专用认证查询相近；复杂 join/subquery 容易精确控制 | 重复条件与适配器数量多；把普通业务查询也做成免用户 Scope 会越界 | 不改表/HTTP；普通能力仍须调用 db.Scoped，若绕开则违反 ADR-011；内部端口更多 | 2–3 |
| C 仅按 model 登记列映射 | model 对应 owner/dept 默认列，Scope 自动使用默认表名，复杂查询另给声明 | 简单单表改动较少 | 单靠 model 无法识别同表别名、多个保护对象；容易遗漏子查询 | 不改表/HTTP；若补齐 alias/子查询契约，实际收敛成 A | 1–1.5，复杂补齐另计 |

**推荐 A 的声明边界**：列名和别名均为编译期可信白名单，HTTP 不接受 owner_column、alias、skip_scope 等配置；数据值参数化。未登记的模型、未知 scope、缺失身份直接拒绝，不降级 all。权限加载、登录、refresh 和 seed 保留已有专用能力与独立矩阵，不把它们扩成通用绕过入口。

**五种 scope 的落位**（以下记根 alias 为 r，仅为谓词说明，不是实现代码）：

| scope | 数据条件；所有情况先限定 r.tenant_id | join | 子查询 | count |
|---|---|---|---|---|
| all | 不加 owner/dept 条件，不是无 tenant 条件 | 每个关系带同租户连接；独立敏感对象仍按声明保护 | 内层也按所属租户限定 | 和列表同一受限实体集合 |
| dept | r.dept_id 等于当前部门 | dept 来自归属用户时，显式连接用户并对其 dept 施加条件 | 内层受保护实体使用自己的 dept 映射 | 保留相同 dept 条件 |
| dept_and_child | 部门路径等于本部门 path，或以「path + 点分隔符」为前缀，再取部门 ID 集合 | 按声明的 dept 来源加入集合条件 | 部门查询与业务子查询各自限定 tenant，不能仅保护最外层 | 用同一部门集合，不把前缀查询省掉 |
| self | 声明的 owner_user_id 等于当前用户；仅表确无此列且声明允许时用 created_by | owner 落在声明的实体 alias，不能随便使用被 join 表的同名列 | 每个独立受保护对象在其内层落 owner 条件 | 保留 owner 条件，不能只统计 tenant |
| custom | r.dept_id 属于当前有效角色在 sys_role_dept 配置的部门集合 | 关联表必须限定 tenant 与当前有效 role ID | 内层按同一角色部门集合保护；空集合为拒绝/空结果 | 同一集合；绝不能用空 IN 省略条件 |

- `dept_and_child` 不能用裸前缀 `1.3%`，否则会含 `1.30`；只有当前部门也算范围，当前部门路径缺失或非法时拒绝，不能把空前缀当全量。多有效角色建议按谓词并集加括号，再与 tenant 相交；all 吸收其他范围、无有效角色默认拒绝，不能靠枚举大小比较 self/custom/dept。
- JOIN 先确定查询结果的保护主体；只作查名的配置关联限定同租户，不额外扩大数据范围；若返回第二个独立受保护对象的数据，该对象也必须声明保护。LEFT JOIN 的附属对象过滤放 ON 或受限派生表，避免无意变成 INNER JOIN。OR 必须整体括号化，不能吞掉 tenant 条件。
- 子查询/EXISTS/派生表必须声明每个受保护对象；不能认为外层已有 owner 就足够。所需受限构造器由门面提供，业务 repo 不拿原始 GORM handle，也不新增任意 Raw 逃生口。
- 列表与 count 从同一个「过滤完成、未分页排序」的基础关系分别构造，join 一对多按根实体 ID 去重；不要复用已执行或带 limit/offset 的可变查询。更新/删除在最终写 SQL 中带 tenant、范围与目标 ID，不能仅靠先查后写；新建和修改归属另校验写入值，WHERE Scope 不保护 INSERT 值。

**M1b 管理表的适用性需明确批准**：建议用户 self 映射 `sys_user.id`、部门用 `sys_user.dept_id`；会话 self 映射 `sys_refresh_token.user_id`、部门经同租户用户关联取得。角色/菜单/权限是租户共享配置，无 owner/dept 列，采用明确登记的「配置管理：tenant + RequirePerm」策略，而不是虚构 created_by、自动 all 或客户端绕过。业务实体仍严格执行五种范围；grant 的目标角色、用户和部门同样要校验，不能利用写关联绕过可管理边界。

**可执行的漏套检测**（沿用 ADR-011，不依赖人工 review，不自研 AST）：

1. 所有 repo 只导出查询接口；在 bootstrap 测试中 reflection 枚举接口方法，与已运行的 DryRun 登记集合精确比较。新增方法无用例、只登记不执行、无 SQL 产出均失败；事务/锁方法也显式登记其特殊断言。
2. 每个受保护方法登记分支：列表、详情、count、更新/删除、join/alias/子查询（存在者必测）；每分支跑五种范围、其他 tenant、空 custom、缺身份。检查 SQL 结构/关键限定片段和绑定参数，而不是只找某处出现 owner 字符串；缺身份必须生成零条 SQL。
3. 沿用 `.golangci.yml` 禁止 repo 导入 GORM/kernel DB/SQL 驱动；bootstrap 的实现不受这条 import 禁令保护，必须纳入同一接口矩阵。作用域公共函数测试不能代替实际方法测试。
4. 用既有测试库设施构造同租户不同 owner、异租户相同关系值、空部门、自定义部门和一对多 join 数据；逐接口核验 list、total、读写副作用。is_super + self 仍不得跨 owner。
5. 用测试替身故意删掉某方法的 Scope、删掉 count 条件、漏掉子查询 tenant，各做一次负向验证，断言矩阵检测到遗漏；不提交故障版本。矩阵进 `make test`，真实数据隔离进 `make test-integration`，导入违规进 `make lint`。

该机制保证登记接口和已列分支受到机器检查，不声称 reflection 能自动发现任意新私有分支；因此必须配合缺声明拒绝、受限门面及真实越权测试。

### Q2 版本键的 fan-out、失败补偿与 5 秒 SLA

**前提**：ADR-011 已选择提交后同步 INCR，M1 明确不做 outbox。`cache/cache.go:86–97` 目前只有单键调用，每次最多 1 秒；2000 次串行网络往返不能作为设计交付。2000 个键不是 2000 次 RTT 的必要条件。

| 方案 | 做法 | 优点 | 缺点 | 对已有表与接口的影响 | 工作量 |
|---|---|---|---|---|---|
| A 请求内有界批量同步 INCR（推荐 M1b） | DB 提交后去重受影响用户，用 pipeline 分批 INCR，检查每条结果，在请求内等全部批次完成 | 保持既定同步路径与接口路径；正常路径可直接验证 5 秒 | 请求延迟随 fan-out 增长；进程退出仍无持久补偿 | 无表/HTTP 结构变化；补 cache 批量门面、失效服务和测试；失败响应语义另确认 | 0.75–1.5 |
| B 事务内 outbox + 异步批处理 | 变更与失效任务同 DB 事务；worker 分批、记录进度、重试，保留用户版本键 | 崩溃后可恢复；请求延迟低 | 排队/重试未必 5 秒；必须监控积压并具备降级；M1b 禁做 | 复用 kernel outbox 仍须提前 M3 T3.11；若返回排队状态可能改 API | 2–3，需先批准改范围 |
| C 角色/租户版本向量 | 角色改动只 INCR 角色版本，缓存依赖用户版本、有效角色集合及版本；菜单变动用租户版本 | 避免按用户大 fan-out | 读取依赖与角色集合失效复杂；权限/菜单需同一复合版本；角色移除尤其易漏 | 不必加表，但改既定 key/缓存协议及读路径，须新裁决 | 1.5–2.5 |

**A 的具体边界**：

- 变更事务内取得必要的旧引用，提交后结合新引用确定受影响用户并去重；角色删关联后才查会漏人。并发分配/移除角色各自也必须失效目标用户，不能只由角色修改承担通知。菜单祖先可见性/移动影响其子树；M1b 可保守失效租户内所有相关用户，包含超管。
- 建议起点为每批 500 键、最多 2 个固定执行单元，2000 人约 4 批；这是待压测参数，不是已证明性能。所有执行单元继承请求 ctx、限时、可退出并在返回前汇合；不把剩余工作丢给裸 goroutine。pipeline 只减少往返，不提供跨 DB/Redis 原子性，也不应当作整批全部成功。
- 每条命令保存对应内部用户标识与结果；部分成功只重试失败或结果不明的键。结果不明时重复 INCR 只多跨过一个版本，对版本失效本身安全。一次有界重试须在剩余请求预算内，不能重跑业务授权事务，也不能提前返回成功。
- 一旦 DB 提交，不能因 Redis 失败声称事务回滚；记录安全 Warn、`authz_invalidate_failed_total` 与失败数量。建议 API 暴露既有 503/10002 并说明「变更已提交、失效未确认」；这比任务卡已写的告警要求更严格，需在实现前确认错误语义。Idempotency-Key 重放不得把失效未确认伪装成已完成。
- M1b 没有持久重试队列：请求被取消、进程崩溃、长故障后自动补齐不能承诺；运维可按资源重新计算受影响用户后重做版本失效，不重放业务变更。正常恢复依赖最多 5 分钟旧缓存 TTL，这是已接受限制，不等于 5 秒补偿。

**5 秒能否保住**：只能对「Redis 正常、约定负载内、同步路径完成」作条件承诺，不能在没有压测证据时保证 2000 人。以 DB commit 为 t0，测受影响集合解析 + 所有 INCR + 后续鉴权/menus 冷读完成的总时间；并发回填也在压测场景内。批量路径应有小于 5 秒的总预算，不能把每批 1 秒超时简单相加后当作已满足 SLA。报告 2000 人、并发修改、慢 Redis 下的最大观测值与分位数，任一目标用户仍旧权限即失败；若正常设计负载下超标，回 Gate 裁决 B/C 或容量，不悄悄改异步。

**并发回填/恢复附加验收**：读版本 n → 读缓存/主库 → 只回填 n；旧读者不能读新版本 n+1 后把旧快照塞进去。缓存 payload 的版本必须匹配；数据范围也要共用这次授权版本。回填耗时设上限，旧快照不得无限迟到后重新获得完整 5 分钟寿命。版本键缺失不能直接回落 v0 并命中残存键；受控初始化与恢复清理必须防止版本重用，恢复期间隔离旧进程回填。

### Q3 强踢、过期 refresh 与 Redis 丢数据

**先纠正场景前提**：`auth.go:79–92` 每次签发同时产生 15 分钟 access 和 7 天 refresh；正常 M1a 链路中 access 仍有效时，同次 refresh 尚未自然过期。「过期」也不会自动删行：`identity_store.go:131–141` 撤销全部历史行，没有 expires_at 或 revoked_at 过滤。因此不能据题设直接认定现实现没有撤销载体。

更重要的是，`identity_session_query.go:15–22` 已定义：没有任何未撤销行，或有 logout/kick/replay 事实，就拒绝 sid；并没有按 expires_at 过滤存活行。`auth_session.go:60–89` 每次校验 Redis 后还查询该 DB 状态。已有 Redis 清空与未知 sid 的测试见 `identity_session_query_test.go`，不能把这项能力当成 M1b 缺失。

| 方案 | 做法 | 优点 | 缺点 | 对已有表与接口的影响 | 工作量 |
|---|---|---|---|---|---|
| A 复用全族历史 + 无行拒绝（推荐 M1b） | 找到可信 tenant/user/sid 后，在现有会话锁内把所有行置 kick；过期行照样标记；物理无行则已经是拒绝状态 | 沿用 M1a 与 ADR，无新增表；Redis 清空仍拒绝 | 历史保留和清理政策必须严格；无行时不能凭空恢复用户/设备归属 | 无表变化；补管理查询、强踢服务、边界测试；未知 sid 的 204/404 需定 | 0.5–1 |
| B 独立持久 session 表 | 每次登录建会话记录，保存归属、撤销原因、有效截止；刷新和强踢锁同一会话 | 生命周期清楚，清理 refresh 后仍有独立事实与会话索引 | 增表迁移、回填、双写与查询切换，超出既定模型 | 须批准新增模型与可逆迁移；可保留现 HTTP 路径，但要决定列表语义 | 1.5–2.5 |
| C 只写 Redis sid 黑名单并依赖持久化 | 无可更新行时只写 Redis，配置 AOF/副本 | 应用改动小，快 | Redis 丢失/回滚会失去事实；TTL 不知道目标最新 token 期限；违反 ADR-012 的 DB 事实源要求 | 无表变化，但降低既定保证，不能作为本期可选实现 | 0.25–0.5，但不推荐 |

**A 的完整处置**：

1. 有历史行：按管理员可管理的数据范围解析目标归属，用现有 `LockSession(tenant,sid)` 和刷新串行，重新查 family、写 kick 与审计后提交；不得只更新未过期行或只更新最后一行。提交后写 session 标记及确知的目标 refresh 标记，管理员的 JTI 不能充当目标 JTI。
2. 所有 refresh 已过期但行仍在：DB 仍能保存 kick；session Redis TTL 按最晚 refresh 剩余期，≤0 跳过；即使假设还存在有效 access，下一请求也被 DB 的 kick 拒绝。不要为了制造 Redis key 擅自延长 ADR 的 TTL。
3. 物理无行：按当前 DB 查询已拒绝此 sid，无需伪造 refresh/hash 行作为墓碑；返回是否幂等 204 或未知目标 404 需要固定。建议同租户已知目标重复踢为 204，完全未知或不可确认归属的 sid 为通用 404，不泄露其他租户会话存在性。
4. Redis 不可用仍为 503/10002；DB 已提交而标记失败也不宣称操作完整成功。Redis 恢复或 key 全丢后，DB kick/无行拒绝仍生效；不缓存「会话有效」到 access 到期。
5. 清理只能在所有可能 token 到期且不再需要重放判定后进行；若保留尚未撤销的行，却先删尽 kick 历史，可能移除否决事实。清理同样按 family 协调，不能在 refresh 解析与持久撤销之间制造重建窗口。超出 M1 生命周期需求时再评审 B。

**验收矩阵**：过期行仍可更新为 kick；删除整个 family 后 access 拒绝；Redis 清空/重启不复活；强踢与刷新并发无新 token；目标已撤销重复调用；异租户 sid；同用户另一个 sid 与管理员会话不受影响。另需明确「会话列表」当前只能可靠表达未撤销、仍有有效 refresh 的会话，不等于最近在线；last_seen 不在现模型中，不能凭空输出。

### Q4 权限码的单一事实源

**现状**：registry 已集中 5 个 M1a 码，`SeedService.Run` 已遍历 `permission.All()`；`permission.Validate` 只校验语法和 module，并不证明某码已经注册。现有认证 OpenAPI 是手写契约，且已有「恰好五个认证端点」测试；M1b 新路由要扩展明确清单，不能删除该测试以掩盖漏端点。

| 方案 | 做法 | 优点 | 缺点 | 对已有表与接口的影响 | 工作量 |
|---|---|---|---|---|---|
| A Go registry + 确定性导出 + 契约比对（推荐） | registry 定义码/元数据；seed 直接消费；RequirePerm 引用常量并验证存在；导出权限清单，核对路由声明与手写 OpenAPI | 延续现状，免重复维护码；保留 ADR-009 手写 API 契约 | 需要方法/路径到权限的结构化登记与 CI 校验；前端需消费产物 | 不改表/HTTP 响应；内部路由声明增强，OpenAPI 增 x-permission 扩展；导出器限现有 cmd/Makefile 范围 | 0.75–1.25 |
| B 中立目录生成 Go/seed/文档/TS | YAML/JSON 主目录生成注册表常量与多端清单 | 多语言复用，机械一致 | 改 registry 事实源约定；生成步骤容易遗漏；不能只靠码推导 endpoint 需求 | 不必改表；要批准构建协议与额外产物路径，不自动生成整份 API | 1.5–2 |
| C 全部手写但集合测试 | 五处保留手写，用测试比较代码集合与引用合法性 | 初始成本低 | 有效性测试不能发现误配到另一个合法码；前端不在本期仓库中 | 无表/API 结构变化；持续维护成本高，需同样建立路由元数据 | 0.5–1 |

**A 如何覆盖五处**：

| 位置 | 输入/生成方式 | 防漂移断言 |
|---|---|---|
| registry | 唯一权限词典；完整码常量 + Definition | code 唯一、三段格式、module/type 合法；注册存在性与语法分开校验 |
| 种子 | 直接遍历 registry，不另存权限字符串列表 | 新库实际 sys_permission 的键/元数据等于本发布目录；升级库只允许显式兼容项；菜单/角色引用都已注册 |
| RequirePerm | 结构化受保护路由声明引用 registry 常量，注册时绑定中间件 | 管理路由默认受保护；缺权限声明/未知码注册失败；枚举实际路由与声明集合无遗漏；无权限请求必须 403/20107 |
| OpenAPI | 路径/输入输出继续手写；权限清单可由 registry 导出，x-permission 与路由声明逐项核对 | 方法+路径一一对应；每个 operation 为一个完整码，如 permissions 列表确实使用 system:menu:list；不是只测「该码存在」 |
| 前端配置 | 从发布权限清单生成常量/类型，或消费既有 permissions 数组 | 前端流水线核对目录版本与生成差异，业务配置只引用生成常量；M1b 仅约定消费方式，不编写前端代码 |

可以自动导出权限词典、种子权限行、权限文档表及供前端使用的常量输入；仅有 registry 无法推导完整的 URL、请求体、路由树、组件路径或角色授权决策，不能声称五处全部自动生成。RequirePerm 仍需要明确的 endpoint→code 绑定；文档与路由二者核对，另用无权/有权行为测试验证实际执行。

CI 至少执行：导出前后无差异、registry/seed 引用校验、实际路由与 OpenAPI 权限映射比对。导出排序固定，禁止时间戳造成假漂移；Go 标准库和现有依赖足够，不要求新依赖。前端产物不在本期允许写入范围内，作为后续接入约定。

### Q5 菜单移动、防环与深度

**结论先行**：`sys_menu.path` 是 `/system/users` 这样的路由；`sys_dept.path` 才是 `1.3.7` 这样的物化祖先路径。移动菜单不能重写路由为祖先路径，也不能根据父菜单 URL 自动改整棵子树的 URL。现 `BuildMenuTree` 超深返回空树只是读取防御，不是写入校验。

| 方案 | 做法 | 优点 | 缺点 | 对已有表与接口的影响 | 工作量 |
|---|---|---|---|---|---|
| A 应用层邻接图校验（推荐） | 同租户树写锁内一次读取 id/parent_id，构建图，校验祖先与子树，更新 parent_id | 配置小表、最大 5 层，逻辑易测；无需改模型 | 读取 O(租户菜单数)，树写操作按租户串行 | 不改表/接口；path 保持路由；新增专用校验/锁能力，不实现部门移动 API | 0.5–1 |
| B 递归 CTE 校验邻接关系 | 同样持有树写锁；CTE 计算祖先、子孙和子树高度，service 判定后写 | 少传输，适合菜单规模增大 | SQL 测试较多；历史环需访问集合防护；CTE 本身不解决并发 | 不改表/HTTP；bootstrap 中专用查询能力，不能给 repo 通用 Raw | 0.75–1.25 |
| C 新增 ancestors_path/depth | 同锁同事务更新节点及子树物化路径 | 祖先、子树查询简单 | 写放大与冗余一致性；M1b 小树收益有限；需补回填/回滚 | 新列/索引/迁移，须先批准；不可复用 sys_menu.path 或放 meta 偷渡 | 1.5–2 |

**推荐 A 的移动事务顺序**：取得同租户树事务锁 → 在锁内读当前图与节点状态 → 校验 parent 存在且同租户，0 作为根哨兵 → parent 不等于自身且不属于移动节点子孙 → 计算新位置深度和子树高度 → 校验后更新 → 记录审计并提交 → Q2 同步失效。读取必须包括隐藏/禁用节点，不能只读前端可见树，否则遗漏环与深层节点。

- 约定根深度为 1、子树高度包含移动节点自身；新根深度 + 子树高度 - 1 必须 ≤5。不能只检查移动节点深度。service 是强制校验层，handler 只校验 ID 等基本参数；repo/DB 负责事务原子性与同租户限制，普通 CHECK/FK 不能替代跨行树校验。
- 单独锁 A/B 两行或在事务外预检不足以覆盖并发交叉移动；所有创建/移动/删除结构的入口（包括 seed）共用树写锁和固定锁顺序。建议使用现有 PostgreSQL 事务 advisory lock 能力，不新增分布式锁依赖；持锁事务不做 Redis IO。
- 发现环按既有 400/20106；深度超限用 400/10001，不新增错误码。父不存在/异租户按既有 not-found 语义，不能因跨租户猜出父节点。若 D1 最终引入 version，同一事务检查，冲突 409/10409。
- 测试覆盖自身/子孙成环、移动至根、异租户父、隐藏父、整棵子树从合法变超深、并发 A↔B、移动后菜单缓存失效；事务失败不能留下半个子树。

**如果实际要问 sys_dept 的路径维护**：那是另一项操作，不在 M1b 菜单 CRUD 内。未来部门移动须同锁同事务，计算新部门前缀，按点分隔边界替换节点与所有后代路径；保留 ID 并重新计算受影响用户范围后失效。选递归 CTE 找子树还是应用层维护路径，都不能仅改 parent_id。本文不借菜单问题提前实现部门 API。

### Q6 「完整种子」是否包含未来模块

**两个前提**：M1a 已有 `trade:order:list`、`crm:customer:list`、`crm:inquiry:list`，以及对应菜单/角色验收数据；不能直接删掉破坏已发布回归。另一方面，今天不预置 shop，并不意味着 M2 永远不能授权：M2 部署时先登记该版本权限、运行增量种子，再通过已有角色授权接口赋权即可。是否自动给现有角色新权限，是授权政策，不是权限目录存在性的同一个问题。

| 方案 | 做法 | 优点 | 缺点 | 对已有表与接口的影响 | 工作量 |
|---|---|---|---|---|---|
| A 预置全部规划模块 | M1b 枚举 shop/product/trade 等全部未来码，并预配角色/菜单 | 后续上线前可先配置授权 | 未来动作/接口尚未冻结；提前授权会在功能上线时静默生效；给不存在功能建立长期兼容负担 | 不必改表，但扩大 registry/seed 与管理界面目录；若区分未发布功能要另定状态/过滤契约 | 0.75–1.5，后续返工未计 |
| B 本期完整 + 已发布兼容 + 后续增量（推荐） | 补齐 M1b system 完整码，保留 M1a 既有码与菜单；不再批量扩充未来模块；每模块随上线注册并授权 | 最小权限、目录与实现同步；保住 M1a 验收 | 升级必须有权限目录步骤；普通角色需要明确的新权限授权 | 无表/现 HTTP 变化；增量同步沿用 tenant+code；已有非超管角色不自动获权 | 0.5–1 |
| C 仅预置冻结码但不授权 | 仅登记已明确契约的未来权限码，角色不挂授予，菜单不展示未来功能 | 可提前配置目录，减少动作猜测 | 仍有无接口权限；DB 无发布状态列；已有 M1a 授权项不能简单收回 | 不必改表，但要定义目录/前端显隐策略；若新增 published 状态须另审 | 0.75–1.25 |

**推荐 B 的升级与幂等语义**：

- 「完整」指本期接口表的全部完整权限码、角色/菜单与引用完整，兼容项单独登记；不代表把 M2–M9 的产品权限提前承诺。M1a 的未来功能验收项属于历史兼容例外，不作为继续预置的理由。
- M2 发布顺序：部署含新 registry 的版本 → 同步权限目录 → 显式授予现有角色需要的新码 → 同步版本失效 → 验证接口。超管 RBAC 按 is_super 跳过，但数据范围仍靠有效 all 角色；不能据此给 operator/sales 自动补全。
- 当前 `seedRoleGrants` 对现有角色无条件做 ON CONFLICT DO NOTHING 插入，会把被手工撤掉的默认 grant 再插回；密码不被重置不等于授权不被重置。建议初始化只给新建角色默认授权，已有角色只做显式批准的增量授权；重跑不覆盖菜单编辑、不复活被撤权限。需保留现有 admin 密码与 super_admin.data_scope=all 不变式。
- 权限目录可幂等 upsert 元数据，不静默删现存权限或回收授权；新增功能普通角色默认无权。真实删除/重命名要单独列迁移计划，先处理菜单/角色外键引用，不能改已合并迁移。
- seed 也会变更授权，不能绕过 Q2：提交后同步失效；离线初始化可在 API 启动前执行，在线升级须走同样失效规则。seed 现有独立事务/锁不能自动阻止管理请求，需明确共享锁和版本检查。
- 验收：新库与升级库分别运行两次种子，权限目录键稳定、密码不变；先手工撤默认 grant 再 seed 仍保持撤销；模拟 M2 增新码后现有角色可通过授权接口获权，但在显式授权前 403；M1a 两组角色菜单回归仍成立。
