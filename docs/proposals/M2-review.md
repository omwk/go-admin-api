## 2. 实现风险（按严重度排序）

| 严重度 | 触发条件 | 影响 | 规避方式 |
|---|---|---|---|
| 高 | 直接序列化请求、解密对象、通用审计 snapshot，或把上游错误写入 error_msg | 明文经响应、日志、审计、幂等响应或 JSONB 旁路持久化 | Q3 使用固定安全投影；失败注入覆盖各通道；不沿用 identity 的整对象 snapshot 处理凭据。 |
| 高 | 只保护 shop 列表；凭据按 cid 直查，或更新时先鉴权再执行无范围 UPDATE | 详情、写入、审计或轮换跨 owner；归属改变时发生竞态 | Q4 让所有子资源继承 shop 的范围；最终读写 SQL 仍含范围，写操作在短事务内锁定父店铺/目标凭据并复核。 |
| 高 | 同一店铺存在两份同类型凭据；解密只信任库中 aad | 四维 AAD 不能阻止同店同类型同版本之间调包 | 裁决 S5；至少测试这一组合，不能只测跨 shop 调包。 |
| 高 | 删除仍被当前版本/历史版本/备份引用的旧主密钥，或各节点切换时序不同 | 大量凭据不可解密，90 天历史保留也无法兑现 | Q2 双读单写、分阶段部署、引用盘点、独立密钥备份及恢复演练。 |
| 高 | HTTP 执行成功后才记录幂等响应，或已提交 processing 没有恢复语义 | 重试重复写、永久 409、并发覆盖首次响应 | Q5 业务、成功审计和完成结果同事务；对同键串行，提交前不发送成功响应。 |
| 中 | 授权提交后 INCR 部分失败，或发布脚本直接改关联表 | shop RBAC 暂时看到旧权限；单纯 seed 不会补权 | 沿用 ADR-014 的 2xx + pending/指标/Warn；发布流程处理逐用户失效；M3 再接 outbox，不宣称 M2 故障时仍有 5 秒保证。 |
| 中 | 通用 BodyLimit 先 io.ReadAll，或把 S3 PUT 放入数据库事务 | 上传耗内存、占用连接、超过 3 秒 DB 超时；事务回滚无法撤销对象存储写入 | 上传单独有界流式路径；对象写在 SQL 事务外，采用确定性对象键和可重复写协议；最终元数据/幂等结果用短事务。 |
| 中 | 把 M1b 小配置表的租户管理大锁推广到所有店铺写入 | 不同店铺互相阻塞，权限变更与业务写争用 | 只对同幂等键/同凭据串行，按固定顺序锁行；不要复用 identity 全租户大锁作为业务幂等锁。 |

原估算 3 人日不足以同时完成公共声明抽取、泄漏测试矩阵、可靠幂等、凭据与上传。建议保留 M2 范围，细分原任务逐项验收，整体按约 **8–11 人日**排期；真正信封/KMS/历史迁移需另估，不通过删验收来守住 3 天。

## 3. 方案对比

### Q1 查询声明的跨模块复用

**已核实的现状。** M1b 基线 `internal/modules/identity/scope/scope.go:11` 定义实体声明，`:17` 的 Lookup 是固定 identity 字典；`scope/queries.go:82` 集中登记方法到实体的映射，`:101` 做方法/实体校验。`internal/kernel/db/scoped.go` 只有受限数据库门面，并不是声明 registry。`internal/bootstrap/identity_scope.go:44` 的部门编译还直接写着 `sys_user.dept_id`，DepartmentSource 只是说明字符串，不能靠为 shop 多填一个声明就自动支持。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：仍由 identity 集中登记 | 把 shop 实体、repo 方法和 SQL 分支加入现有字典/编译器，由 bootstrap 复用 | 改动最少，只有一套 Scope | identity 了解业务表；未来每个模块都要修改 identity，部门来源仍靠分支维护 | identity/scope、bootstrap、shop；无表/API 变更 | 0.5–1 人日 |
| B：内核协议、模块声明、装配注册（推荐） | 将中立声明/访问事实协议与校验归入拟新增 kernel/scope；identity 与 shop 各自提供静态声明集合，bootstrap 显式合并、校验、冻结并注入编译器 | 复用一套机制，业务归属留在模块；内核不依赖 identity | 需要有限抽取及 M1b 回归；不能只搬类型而保留硬编码部门分支 | kernel/scope、kernel/db 门面接线、identity/scope 兼容层、shop 声明、bootstrap、矩阵测试；无 schema/HTTP 变更 | 1–1.5 人日 |
| C：shop 复制一套 | 本模块另写声明、身份上下文和范围 SQL | 短期不动 identity | 漏洞修复与五种范围规则会分叉；两套上下文难组合 | shop 与 bootstrap；短期无表/API 变更，长期重复维护 | 0.75–1.25 人日，另有持续成本 |

推荐 B 的注册与边界：

1. 模块仅导出代码内固定的实体声明和方法声明，名字带模块/端口命名空间；shop 声明根表、固定别名、tenant/owner/dept 映射及父级保护关系。SQL 标识符不得来自 HTTP。
2. bootstrap 在启动阶段合并集合；重复名称、缺失父关系、错误列映射、方法引用未知实体均启动失败，之后只读。无需运行时插件或重型依赖。
3. 部门来源区分「本表列」「受保护父表关系」「无部门的明确配置策略」，用受控结构表示，不执行模块提交的任意说明字符串。shop 使用自己的 dept_id；凭据通过 shop 继承。
4. identity 继续负责账户/有效角色加载、RequirePerm 和 authz 缓存，通过公开契约向 bootstrap 提供中立访问事实；kernel 不 import identity，shop 不 import identity/repo 或 model。无需为此迁走权限 registry 或 authz。
5. 未声明实体、未声明 repo 方法、缺身份、无有效角色继续拒绝；平台全局只读必须是显式独立策略，不能借 Shared=true 跳过一切限制。
6. 保持 depguard、ScopedQuery、三集合核对：repo 接口方法 = 生产声明登记 = DryRun 用例；每个方法再测实际 SQL 根/关联条件。现有 reflection 不能单独证明 join 或私有分支安全。

### Q2 凭据加密的密钥生命周期

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：单主密钥，只预留版本字段 | 环境变量注入一把密钥；key_version 仅落库，不支持旧版本选择 | 最快，沿用现有配置 | 换主密钥即无法读旧记录；不满足 M2 §7.1 和 T2.2 的可轮换要求 | crypto、现有配置、shop；表列不变 | 0.5 人日；不建议作为验收方案 |
| B：版本化 keyring，读旧写新（推荐） | 部署系统从秘密管理渠道注入环境变量，受控秘密挂载文件也可作为部署适配；多个版本可读，仅一个活动版本写入；M2 不做历史批量重加密 | 无新运行时依赖，轮换与回退可验证；匹配现有 Sealer/存储形状 | 旧数据仍依赖旧密钥；需人工保留和盘点，不能宣称已完成旧钥退役 | kernel/crypto、config、bootstrap、shop；配置 map/活动版本为新增契约，AAD 变更另裁决 | 1–1.5 人日 |
| C：KMS + 真正信封 + 历史迁移 | KMS 管 KEK，随机 DEK 加密凭据并被包裹，另做批量重包裹/重加密与进度恢复 | 中心化授权与密钥审计，具备受控退役能力 | 需确定供应商、DEK 封装、可用性和 SDK；扩大模型/依赖与运维范围 | crypto 端口/适配器、配置、密文封装或新列、新迁移/任务；须先批准 | 3–5 人日起，超出当前 3 日卡 |

**注入与 CI。** B 的生产密钥由部署秘密管理系统提供，禁止配置示例中出现有效密钥，禁止启动时打印配置对象；环境变量泄漏面与挂载文件权限由部署配置控制，应用只报配置项名称。拟增加版本集合及活动版本配置，保留现有单钥配置的显式兼容转换；具体配置名需写入任务卡，当前代码尚不支持 map。

单测每次用 crypto/rand 生成 32 字节材料并直接注入 Sealer；配置测试用测试环境注入；进程/CI 集成测试按作业随机生成并传给 API/CLI，作业结束销毁。CI 不依赖生产密钥，不提交固定字符串或可用 fixture，不回显环境变量。覆盖无配置、非法 base64/长度、活动版本不存在、历史版本缺失；失败信息不得包含值。未知历史 key_version 或错误密钥不能回退到「随便试一把」。加密固定 AES-256-GCM、12 字节随机 nonce；解密得到的明文用短生命周期的字节缓冲区，用完清零，不放入跨请求缓存或审计快照。

**M2 的轮换到达线。** 先把旧钥和新钥同时部署到所有 API/worker，活动版本仍为旧；确认所有读者都能读新版本后再切新写入；测试旧行仍可解密、新行使用新 key_version、nonce 每次随机、错误版本拒绝。回退时仍保留已经产生新密文所需的新钥，不能只回滚程序/活动版本。业务凭据轮换插入新 credential_version，旧行只更新 retired_at/purge_after；不为了换主密钥原地重写不可变密文。

历史重加密在 M2 不做。**保留 90 天不等于旧密钥 90 天后可删**：未轮换的当前凭据可能一直引用旧钥，备份也可能引用它。必须盘点在线未清理密文、当前版本与可恢复备份的 key_version；全部消除引用后才能退役。真正信封的重包裹是否属于不可变例外，也需另行裁决。

**AAD。** 既有四维为 tenant_id、shop_id、kind、version_no。推荐经批准增加 credential_id，形成固定编码的五维 AAD；M2 尚未落业务数据，适合此时定下格式。若坚持四维，必须明确接受同店铺同类型同版本多凭据之间调包的残余风险，不能把跨 shop 测试当完整证据。解密时从已校验的 tenant → shop → credential → version 关系重建 AAD，库中 aad 仅作一致性校验，不能直接信任。owner/dept、label、过期时间等可变展示/归属信息不绑定；它们变化不应导致凭据永久不可解密。

**恢复流程。** M2 应写最小运维流程并实际做一次隔离环境恢复：停用相关凭据调用/写入；确认所需 key_version；从与数据库分离的受控备份恢复对应密钥；抽样认证解密后恢复服务。不能确认密钥完整时持续拒绝解密并告警，使用既定 30501，不输出底层明文/材料。密钥永久丢失时密文无法恢复，只能由店铺重新授权/录入，保留原版本与失败审计。ADR-005 把正式导出/备份工具放 M10；本建议只前置操作说明和人工备份恢复演练，不新增凭据导出 API。

### Q3 「只写不读」的可验证契约

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：只跑任务卡 grep 示例 | 成功录入后检索响应/日志/一列密文 | 成本低，适合人工冒烟 | 固定明文违反夹具约束；不覆盖错误、JSONB、审计与重放；密文非空也可能只是编码 | 验收脚本；不改表/API | 0.25 人日，不能单独验收 |
| B：固定安全投影 + 全通道自动断言（推荐） | 实际路由集成测试串起随机凭据、加密落库、轮换、审计、失败和重放；同时捕获日志、错误、SQL | 可定位泄漏入口，能够验证 PRD 的 P0 契约 | 需要故障注入和递归检查；须维护元数据白名单 | shop 测试、安全 DTO、bootstrap 日志/DB 测试装配、OpenAPI；不因测试新增列或公开读明文接口 | 1–1.5 人日 |
| C：B + 系统性变异/端到端矩阵 | 临时注入响应/日志/元数据泄漏，验证测试失败，扩展编码与代理日志链路 | 能发现断言本身失效和部署层泄漏 | 全面矩阵维护成本高，超过中等强度最低要求 | B 加 CI/部署测试；无业务契约变化 | 2–3 人日 |

推荐 B；另做少量定点负向验证，不要求本期搭建完整变异框架。输入按 oauth2、api_key、cookie/session 参数化，token、Cookie、UA/指纹附加字段都由运行时随机生成；每个敏感值使用独立高熵标记，覆盖旧版本与新版本。

| 通道 | 具体自动断言 | 必测错误/旁路 |

推荐 B 的实体策略：

| 对象 | SQL 与授权策略 |
|---|---|
| shop | tenant_id + deleted_at IS NULL + 有效角色 scope 并集；self 对应 owner_user_id；dept/dept_and_child/custom 使用 **shop.dept_id**，不默认跟随负责人当前部门。all 也保留 tenant 和软删条件。 |

| credential_version / credential_audit | 从 credential_id 连接同租户凭据和受保护 shop；旧版本/失败审计同样受限；不得用历史 created_by 代替当前店铺 owner。 |

「运营只看自己的店」的前提是其有效角色并集只有 self；依 ADR-014，同时拥有 dept/all 时必然扩张，不能按角色名称 operator 强制改成角色交集。

| 入口 | 保证方式 | 跨 owner 的预期 |
|---|---|---|
| 列表 | list 和 count 从同一受限基础关系分叉；join 去重根 shop；筛选/分页前先约束 owner | 对方店铺不进 list/total，不在内存删行补救 |
| 详情 | 一条受限查询同时约束 tenant、id、owner/dept、软删 | 404/30101，和不存在一致，避免枚举 |
| 更新 | 事务内读/锁可管理的旧记录；最终 UPDATE 仍带相同 Scope；校验新归属在操作人可管理范围且引用同租户有效用户/部门 | 零行返回 404/30101；如采用 version，已确认可见记录的陈旧版本返回 409/10409 |
| 删除 | 受限 SQL 执行软删，并检查 RowsAffected；凭据后续访问也继承父 shop 未删除条件 | 404/30101；不能把零行 UPDATE 当成功 204 |

创建时未指定负责人/部门，建议服务端依据实时加载的访问事实填当前用户/部门；显式指定则验证可管理范围，tenant 只来自已验证身份且不可更改。更新负责人或部门必须同时验证「原记录可管理」和「目标归属可管理」，不能通过先把他人店铺改成自己来获得权限；owner 与 dept 关系是否必须一致需业务裁决，建议允许独立分配且不随用户调部门自动迁店。

凭据录入、轮换、检查、停用、审计查询都要复用上述父范围。凭据写事务按 shop → credential 的固定顺序锁行并复核关联，避免店铺移交/删除和凭据写入交错；实际平台 HTTP 检查留 M3，届时不得在这些 SQL 锁内执行外部调用。

验证至少包括五种 scope、角色并集/all 吸收、空 custom、无有效角色、缺身份、跨租户、已软删、别名/join、父归属转移、is_super + self；每个公开 repo 方法登记反射矩阵，并跑实际 shop HTTP 的跨 owner 四入口及子资源集成测试。

### Q5 幂等中间件的位置

**已核实的现状。** `idempotency_key` 已在 `migrations/000001_kernel_init.up.sql:71` 创建，TTL 默认 24 小时，无需在 M2 重建。M1b 的 `identity.AdminService.Execute` 把业务、审计与完成响应放在同一事务内，靠租户 management 锁串行；`internal/modules/identity/admin_http.go:78` 的 scope 含 user、方法和实际路径。`bootstrap/identity_admin_idempotency.go:41` 仅存完成结果并可 upsert，不能脱离其大锁/事务直接复制为通用并发方案。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：纯 httpx 中间件 | 读 key/body，调用 handler 后缓存 writer 响应 | 接入方便，Gin 逻辑集中 | 无法与 service 事务共同提交；提交后崩溃会重复写；容易存敏感体/头 | httpx、响应存储适配；表可复用但原子性不成立 | 0.5–1 人日，不推荐 |
| B：kernel/idem 核心 + httpx 薄适配（推荐） | 内核定义存储端口、哈希/状态规则；HTTP 只提供请求元信息；service 在自己的事务中协调占位、业务、安全结果 | 保持事务在 service；跨模块复用；可验证并发和回滚 | 不能靠一条 Gin Use 自动接好所有事务，上传需专门处理外部副作用 | kernel/idem、httpx、bootstrap DB 适配、shop service/测试；复用既有表，无新依赖 | 1.5–2 人日 |
| C：Redis 锁/响应为主 | Redis SET NX 占位和缓存，数据库单独提交 | 快，支持多实例抢占 | Redis 过期/故障与数据库提交间无原子性；处理租约和宕机恢复比本期需求复杂 | kernel/cache、idem、补偿/状态设计；可能需要新持久状态 | 2–3 人日，不推荐本期 |

推荐 B 的事务与重试规则：

1. 无 key 正常执行；有 key 先完成认证、RequirePerm、输入校验及当前资源范围校验。每次回放也检查当前授权，撤权后不得从缓存绕过；创建回放检查返回实体归属，删除回放可通过已软删记录的专用受限归属查询验证，不能因已软删就无条件 404 或无条件回放。
2. 唯一命名空间使用表中 tenant_id；scope 编码「当前用户 + 方法 + 固定路由模板」。JSON 端点的哈希包括路径参数、影响行为的 query、规范化 Content-Type 与有界原始 body 字节；不解析后重排 JSON，同内容不同字节视为不一致。multipart 则用固定排序的业务字段与文件摘要清单，不把随机 boundary 纳入哈希。这样同键指向另一 shop/cid 返回 mismatch，而不会错回放前一个对象。
3. key 限长，存其摘要而不记录原值；body 只保存哈希，不保存原文。哈希规则必须固定，不能把旧 M1 的实际路径命名空间直接改名导致已有 24h 记录失效；M2 新路由可先用新规则，M1 适配另列明确兼容任务。
4. service 开短事务，在同一连接取该完整键的事务级 try advisory lock；忙则立即返回明确的处理中冲突，不拿全租户大锁。获得锁后查询既有记录、比较哈希/TTL，再 INSERT processing（或原子回收已过期记录）。唯一索引仍作最终约束。
5. 在该事务内执行业务变更、成功审计和安全结果序列化，最后置 completed、写 response_code/response_body 并提交。processing 不先独立提交；事务崩溃/业务或审计失败全部回滚，不遗留永久 processing。接管来自其他实现的已提交 processing 必须先对账，不能仅凭超时重做业务。
6. 同键并发者可先收到处理中；随后重试要么回放已完成结果，要么在前事务回滚后成为执行者。同键不同哈希在可读到记录后固定返回 409/10006；建议处理中用现有 409/10004，区别于 mismatch，S7 裁决前不自行换码。
7. 事务提交后连接丢失/客户端超时，同键重试回放已提交结果；提交前失败不缓存 5xx，也不把未提交的 4xx 固化。记录首次**已提交成功**的语义数据与 HTTP 状态；204 存 JSON null、回放仍无体，trace_id/request_id 按本次请求生成，不存 Authorization、Cookie、签名 URL 等短期敏感头。

存储 SQL 适配放 bootstrap 或受信任的内核基础设施层，通过 kernel/idem 端口注入；shop repo 不取得原始 DB，不能跨模块调用 identity/repo。TTL 固定 **24h**，回放不延长；过期判定先于哈希比较，回收必须同键串行。清理只删除 expires_at 已过的记录，批量执行；过 TTL 后允许重新执行，业务唯一约束仍必须成立。需测试并发相同/不同体、跨用户/租户、不同资源 ID、提交前失败、提交后断连、204、过期键复用和回放后的权限撤销。

**文件例外必须落到协议。** 对象上传不能放进上述 SQL 事务。建议上传完成后才在短事务里登记 file_object + 幂等成功结果；对象键由租户/用户/幂等键摘要与文件内容哈希确定，上传前完成尺寸/MIME/内容哈希校验（可用有界临时文件），对同内容重复 PUT 可重入，不同内容不覆盖同一对象。最终同键对账只留下一个文件记录，SQL 失败产生的未引用对象需清理。该方案保证业务记录幂等，不能宣称对象存储调用次数恰好一次；若要求全程持久占位/租约，须另批状态与恢复契约。

推荐 B。M2 先扩展现有公共 permission 包，不另建第二个 shop registry，也不为本题顺手重构整个权限词典：

- 店铺精确登记 `shop:store:list`、`shop:store:create`、`shop:store:read`、`shop:store:update`、`shop:store:delete`。
- 凭据精确登记 `shop:credential:list`、`shop:credential:create`、`shop:credential:rotate`、`shop:credential:check`、`shop:credential:disable`、`shop:credential:audit`；module 均为 shop。

- 运营建议初次显式授予五个店铺操作，数据范围仍是 self；凭据操作默认不随店铺操作附赠，按岗位单独批准。销售默认不增权；super_admin 的数据范围 all 不变，其 is_super 跳过 RBAC，也不能借 seed 补回手工撤掉的关联。

**M2 上线操作顺序：**

1. 接入已验收的 M1b 基线，确认 ADR-014、000003 索引迁移和 seed 撤权测试均在发布版本中；确定本文待决项并更新相应实现任务的允许范围。
2. 代码构建阶段完成 registry 完整码、shop 结构化路由声明、手写 OpenAPI x-permission；运行权限导出及方法/路径/单权限双向核对，先阻止拼写漂移。
3. 先在隔离环境演练新增 `000004_shop_init` 的 up/down/up；生产只执行新 up。部署可读旧/新密钥的配置与兼容版本，按 Q2 顺序切换活动钥；业务路由先不对普通运营放量。
4. 执行更新后的词典/平台种子：先权限字典，再依赖它的菜单。对已有角色、用户角色、菜单授权与密码不做补齐；新数据库的新建角色才按本期默认集合初始化。
5. 生成仅含 M2 新权限的授权预览：tenant、角色 ID/code、当前集合摘要、拟新增完整码与权限 ID、操作者、发布 ID；由人批准具体清单。不能从「角色名称是运营」推导所有租户都同意新增权限。
6. 发布命令在既有租户管理事务锁内重读当前集合，校验清单摘要/可管理范围，插入批准的新增关联；授权、成功审计、sys_setting 的发布 ID/清单摘要标记同事务提交。已存在相同发布标记则不补权，不同清单摘要拒绝；曾撤销的旧码不在新增清单中。这里是显式发布操作，不能塞进普通 seed。
7. 提交后通过现有 authz.Invalidate 对受影响角色的用户去重 INCR，沿用 500/批、最多两个执行单元与预算内失败键重试；菜单变更按既有规则覆盖所有受影响用户。CLI 输出待失效用户的安全标识/状态，不打印敏感配置。
8. 部分失效失败时不回滚已提交授权、不把业务成功包装成 503；HTTP 沿用 2xx + pending，CLI 将发布留在「提交成功、失效待确认」。Redis 恢复后只重试失效步骤，不能重放授权步骤；故障期按 ADR-014 的 TTL 限制验收。
9. 用实际运营账号验证自有/他人店铺四入口、无凭据权限时 403/20107、授予后生效、撤权后生效；确认 Redis 正常时新鉴权和菜单查询在 5 秒内反映变更，再放量。
10. 撤销一项旧权限、一项刚发布的新权限及菜单/用户角色关联，重跑普通 seed 和同一发布 ID，均不得复活；再次授权必须是新的人工批准。回退业务代码时保留权限字典和发布标记，避免旧发布被当成首次执行；不要全量重置角色授权。

## 4. 未来 2 个里程碑的坑（只列不展开）

- M3：worker 没有 HTTP 身份，必须有声明过的任务租户/店铺能力，不能随意构造 all 或用 context.Background 绕过范围。
- M3：平台 Check/取 token 需要内部只读明文能力及 read 审计，必须通过模块公开 port，不能直接读凭据 repo/model。
- M3：实际平台错误、raw_payload 和重试队列可能携带 token/Cookie，不能沿用「上游原文进日志」的泛化规则。
- M3：outbox 失效重试要覆盖本期显式权限发布，不能只监听管理 HTTP 写入。
- M3：keyring 与 AAD 格式必须在所有 API/worker 一致；过旧 worker 不能读取新钥密文。
- M4：商品/listing 多对多 join 的数据范围和 total 必须按根去重；只测方法登记数量会漏关联旁路。
- M4：店铺移交、停用、软删对历史商品/导出权限的影响要从当前店铺继承，不能照搬采集时的 owner。
- M4：10 万商品分页/导出与文件签名 URL 不能把内存有界、访问范围和 URL 有效期交给通用幂等缓存猜测。

## 6. M2 会暴露的 M1 遗留问题

以下是已核实边界或待业务数据验证的假设，不意味着本次修改 M1，也不把已接受限制改称新缺陷。

| M1 假设/边界 | 证据 | 真实业务上的失效方式 | 建议归属 |
|---|---|---|---|
| 查询声明已经是通用能力 | M1b `identity/scope` 固定实体/方法字典；`bootstrap/identity_scope.go:48` 写死 sys_user 部门列 | shop 有 owner_user_id 与独立 dept_id，凭据只能经父表归属；直接套用会拒绝或生成错误 SQL | M2 Q1/Q4 做有限抽取，保留 M1b 回归 |
| 一个 Shared 布尔足以区分配置与业务 | 现有 Shared 仍先注入 tenant 条件，platform 模型却没有 tenant_id | 全局平台目录不能当租户配置查询，也不能为了避免错误开放通用跳过 Scope | M2 显式全局只读策略；不引入 HTTP bypass |
| 小配置表整对象审计可复用 | M1b `internal/modules/identity/admin.go:115` 的 snapshot 会序列化传入对象 | 凭据对象/请求自带 values、cipher 和私有元数据，通用快照会扩大泄漏面 | M2 凭据专用安全投影与 Q3 矩阵 |
| 租户管理大锁能承担通用写幂等 | M1b Admin.Execute / LockManagement 把同租户写串行 | 多店铺录入/轮换/上传互相排队，上传外部 IO 更不能纳入该事务 | M2 同键锁与同凭据行锁；M1 兼容行为另卡 |
| 权限登记等于已有角色可用 | seed 只给新建角色默认授权，撤权回归明确要求已有角色不补 | 老运营升级后看不到店铺功能；若恢复旧式 seed 补权又会复活撤销项 | M2 Q6 显式发布；不能改坏 M1b1 不变式 |
| 写授权 API 足够支持安全增量运维 | M1b GET /roles 返回角色标量，授权 PUT 采用完整 ids 替换，缺少可直接配对的当前授权读取契约 | 运维猜测全量集合会误撤/恢复权限；并发配置还会丢更新 | Q6 发布命令在事务内读取现状并审计；通用授权查询 API 另议 |
| 版本键解决所有撤权窗口 | authz 缓存固定旧代回填，但提交后 INCR 可失败，ADR-014 已接受最长约 5 分钟 TTL 收敛 | 失败窗口中的旧 RBAC 可继续放行部分 shop 操作；不能用缓存命中等价当前数据范围 | M2 保留 pending/告警与当前范围加载；M3 接 outbox，严格即时撤权需求另评审 |
| 菜单和权限共用版本键即同一次原子快照 | M1b ProfileService.Menus 先调用 Me，再独立 Load(menu)，两次版本读取之间可发生 INCR | 单次响应可能混合两个代际；下一请求收敛不等于当前响应绝对一致 | 作为 M1/M3 后续一致性议题登记，本期不顺手改缓存 |
| is_super 或 operator 名称能直接确定数据范围 | ADR-011/014：is_super 只绕 RBAC，多有效角色范围取并集 | 超管 self 仍只能看自己的店；运营被授 all 就不能再承诺「只看自己」 | M2 必须用实际角色组合做端到端断言 |
| 无 version 例外适用于后续所有表 | ADR-014 第 7 条只列 M1b 用户/角色/菜单，shop 数据模型又存在全局/逐表差异 | 真实多人编辑店铺或同时轮换凭据时产生覆盖；RowsAffected 本身不检测陈旧写 | M2 在 T2.1 前裁决 D1，不默默加列或放宽契约 |
| 通用请求体限制就是上传内存边界 | 现有 `internal/kernel/httpx/middleware.go` 的 BodyLimit 完整读取请求体 | 文件上传即使 handler 流式，前置中间件仍已整包读入内存；幂等哈希再读会放大占用 | M2 上传专用有界路径与实际超限/并发测试 |
| M1b 的方法矩阵可直接证明新业务安全 | M1b 报告 48=48，实际登记对象仍是 identity 端口，SQL 分支需另外检查 | 新增 shop 子查询、审计和版本读取不在原矩阵内，数量一致也挡不住错误关联 | M2 为实际 shop 端口独立登记，并测试移除范围条件时用例确实失败 |
