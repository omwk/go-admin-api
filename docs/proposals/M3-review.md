## 3. 方案对比

按本次要求展开六题，每题三方案；§3.7 另列已发现的 raw 去重阻断项。以下路径是裁决后的预期影响面，本次不会修改它们。

### Q1. 映射引擎的边界

**判断**：`collections` 的逐元素相对 JSONPath 已能表达“一个商品带多个 SKU”，expr 能处理状态查表与金额换算。不能因此宣称支持任意嵌套展开：嵌套分组、父字段广播、跨两个平行数组按键关联、笛卡尔积，需要额外语义。比如“颜色组 → 组内尺码 SKU”与“两个数组只凭位置 zip”是不同需求，不能让 expr 猜配对。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：纯现有 DSL | 只允许 fields + 一层 collections + value 转换；复杂结构拒绝发布 | 最小范围、易校验与解释 | 超过一层的真实 SKU 结构可能无法接入，后续返工 | ingestion/mapping、发布校验与 fixture；表及 Connector 不变 | 3–4 人日 |
| B：有界 DSL + 注册纯函数 | 保留现有结构；普通 SKU 用 collections，复杂数组由通用、确定性的 flatten/按键组合函数扩展，明确最大展开数，不在适配器解释字段 | 符合 ADR-004 扩展点，运营配置可变，复用较好 | 首次新增函数仍需代码发布；需定义空值、重复键、顺序、父上下文，不是任意程序 | ingestion 映射/函数注册与 bootstrap；spec 冻结依赖快照；目标字段目录；有新语义需先批准，Connector 签名不变 | 4–6 人日 |
| C：通用嵌套转换语言 | DSL 新增递归 collections、父/root 访问、join/flatMap 等 | 覆盖复杂平台、配置能力强 | 类型推导、错误定位、资源预算与兼容成本高，明显超 M3 | DSL schema_version、校验器、dry-run、映射存量兼容、使用文档 | 7–10 人日 |

**推荐 B**：M3 先固化“一层多 SKU + 状态 + 金额”支持集，以 Shopee 实际脱敏 fixture 判定是否真的需要某个通用扩展。不预造完整语言；没有父上下文契约时不能暗中给函数注入整份 raw。复杂输入不能表达就发布失败，而不是在 connector 写平台解析。

发布门禁应形成一条不可跳过的链：

1. 严格解析 spec 并校验 schema_version/resource；target 白名单来自最小 listing/listing_sku 规范 DTO，允许显式 ext 路径但禁止覆盖引擎保留空间。校验重复 target、父子路径冲突、collection 的业务 key、根 key 必填、集合元素唯一键与元素数量上限；空集合与字段缺失必须区分。
2. 预编译全部 JSONPath，包括 collections 相对根路径；限制支持的路径语法和深度。复杂 filter/wildcard 引用与必填漂移检测需共享规范化路径目录，不能靠字符串前缀猜。`$.fallback` 是否支持按 C10 裁决，不把它原样送给 expr。
3. expr 只注册确定性、无 IO 的白名单函数及显式 value 环境；禁止任意宿主方法/网络/时间随机数。按目标类型编译，校验参数个数/可推导类型、返回类型、常量正则与状态表存在性。若源类型只是 any，静态检查只能覆盖语法与可确定部分，必须在报告里标“源类型未知”，不能宣称所有类型错误已排除。
4. 发布的 spec 包含引用状态表的内容快照/摘要与函数集版本；checksum 覆盖这些依赖。缺状态表、非法目标状态、金额溢出与不支持的 DSL 在发布时拒绝。源值将来发生漂移仍需运行时 FieldError/隔离，静态校验不可能证明未来平台值合法。
5. 从有权限访问的最近 20 条 raw 做零写入 dry-run，另用固定 fixture 覆盖空值、数值边界、数组展开、未知状态、重复 SKU；发布端必须对实际即将发布的 checksum 重验，不能只信客户端传入“已验证”。版本发布与 active 指针切换用短事务/CAS，防止校验后 draft 被并发改写。
6. `required` 先检查源缺失，缺失不能通过 default() 悄悄变成有效主键；optional 的默认值可使用。`money_cents` 从 json.Number/十进制文本运算，明确四舍五入（含负数半分）与 int64 溢出规则，避免先转 float64 丢精度；外部 JSON 数字可接受，规范输出仍是 int64 分。使用 decimal 的依赖授权应在正式任务中统一，不能把示例 prompt 当所有子任务的隐式授权。

**性能预算，非实测**：100,000 × 50 = 5,000,000 次字段求值，另加 JSON 解码、数组展开、校验与存储。仅映射若平均 10/50/100 μs 每字段，则串行约 50/250/500 秒；这只是换算，不是所选库的跑分。1 小时上限相当于平均 720 μs/字段（若全部时间给映射），并不能覆盖任意 SKU 数量或复杂正则。

建议验收机器固定为 4 vCPU、8 GiB、SSD，记录 CPU/Go/库版本；100k 商品每条 2–8 KiB，50 字段，另测 10 SKU/商品与最大允许集合。建议纯映射热缓存目标 **≤300 秒**、额外常驻内存 **≤512 MiB**（不含 DB），冷启动单独报告；端到端 mock + 本地 PostgreSQL 目标 **≤1 小时**，吞吐至少 27.8 商品/秒。以 500 条/页为例共 200 页，即使只 Fetch 每页耗 15 秒也已占 3000 秒；真实上游配额/重试必须另报，不能无条件承诺真实平台一小时。

M3 应提交 Compile 冷编译、Apply 热缓存与多 SKU 的 benchmark（`go test ./internal/modules/ingestion/... -run '^$' -bench 'Compile|Apply' -benchmem -count=5`），以及 100k mock 端到端报告，附 allocs/op、RSS、CPU/heap profile、raw/目标写入耗时。对比串行与最多 GOMAXPROCS 的有界纯映射并行，不能为数字提前加无界 goroutine。

**缓存**：每进程线程安全 LRU，容量 100；主索引 mapping_version_id，校验 tenant/profile 关系，并用 checksum + 函数集版本防陈旧。Compiled 与状态表快照只读，求值变量/数组缓冲每次独立；同键并发编译合并，失败不长期缓存。draft 使用独立的短期 checksum 缓存或不缓存。每个 run 固定已发布版本，续跑继承；新 run 读新 active 指针，旧 run 不热切版本。不靠进程间广播保证正确性，不把编译错误忽略后回退到旧版本。

### Q2. raw_payload 分区维护

**现状与故障机制**：T3.1 只建当月+下月，不能覆盖长期运行。PostgreSQL 在没有匹配分区且没有 DEFAULT 分区时，INSERT 会报 `no partition of relation ... found for row`（SQLSTATE 23514）；同一语句的整批失败，事务进入错误态。不能吞错后继续映射或推进游标，也不能把所有 23514 都当缺分区自动重试。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：仅迁移/人工运维 | 每月上线迁移或人工提前建下月 | 应用无 DDL 权限、初期简单 | 将月初可用性绑定发版/值班；漏执行即停同步 | 新增分区迁移与运维手册，不改业务接口 | 0.5–1 人日，另有持续值守成本 |
| B：迁移初始化 + 独立维护任务 | 迁移建函数与当月/下月；维护任务启动及每日预建当前和未来两个月，告警覆盖不足 | 自动恢复停机跨月，主写入路径不做 DDL | 需要调度、DDL 角色隔离、监控与补建流程 | 新增 000005、维护 worker/bootstrap、配置与指标、分区/归档端口；已有 API 不变 | 1.5–2.5 人日，归档另计 |
| C：DEFAULT 分区兜底 | 在 B 基础上无匹配数据先入 DEFAULT，再搬运/挂载 | 维护失败时仍能收 raw | attach 时须验证 DEFAULT 中无冲突范围，搬迁/锁表复杂；容易把告警藏成长期堆积 | 分区迁移、搬运器、默认分区容量报警与恢复测试 | 3–5 人日，归档另计 |

**推荐 B**：迁移创建结构，定时任务负责持续生命周期；普通同步 DB 账号没有建表权，DDL 通过单独维护账号或严格限制执行范围的函数完成。函数只接受验证过的月份、固定父表/命名模板，固定 search_path；并发创建用数据库 advisory lock + 幂等目录核验，不能拼任意表名。UTC 月初闭开区间；用真实采集时间 fetched_at 分区，平台事件时间不得决定分区。

保护措施：维护进程启动先核查覆盖，至少提前 7 天报警 next-month 缺失；每日预建未来两个月。同步入口只做覆盖检查/请求维护补建，缺分区作为可恢复基础设施错误，保留原输入页与检查点、延迟重排；在 fresh 事务重试原批，补建失败时游标不动。不能在已 aborted 事务中补 DDL，也不在每条写入时做 DDL。所有副本停机到月初仍可能短暂阻塞，B 保证可恢复而非承诺绝对零停顿；若业务要求维护全失效仍不中断，选 C 并承担搬迁成本。

**180 天归档**：目的地为配置的私有 S3/MinIO 专用前缀，优先流式压缩 JSONL（带全部列、主键与版本引用），Parquet 等需求出现后再评估依赖。由同一维护角色的每日任务触发，不由用户同步事务或人工点“删除”触发；不使用 M2 图片上传白名单接口来上传归档。

按 UTC 截止 now−180d，只有分区上界 ≤ 截止点才整分区归档；因此实际在线保留约 **180～211 天**，不能宣称精确第 180 天删除。若严格要求 180 天，需逐行归档边界月/改日分区，属于额外设计与工作量（约 +1–2 人日）。选 B 的完整归档闭环再计 **2–4 人日**，含可重复触发与恢复演练。

归档流程必须是：标记候选且停止向过期月份补写 → 流式导出到确定对象键 → 校验条数、范围、内容摘要与读回 → 原子发布 manifest（分区界限、对象版本、校验和、格式版本、映射引用）→ 确认无在途重放/未决隔离死信引用或已具备可用归档读取 → detach/drop。网络传输不放长 DB 事务；每次状态推进可重入，上传失败/验证失败绝不删分区，drop 失败可重试且保留 manifest。

归档对象私有访问、传输/静态加密与访问审计；备份/旧映射版本保留覆盖恢复期。M2 keyring 只负责凭据，不是 raw 归档加密方案。M4 尚无归档恢复读取器时，未解决引用应阻止 drop 并报警，或先受控恢复为临时回放数据源；只留一个失效 raw_id 链接不算可重放。对象存储自身保留期限另需人确认，180 天在线并不意味着归档永久保存。

### Q3. 游标推进与部分失败

**回答**：“整页成功”应定义为“页中每条都有已持久化、可恢复的处置”，不是每条都成功入规范表。隔离与单条死信是有效终态；它们的写入失败不是终态。一条永久坏数据不应卡死店铺，但页级鉴权/Fetch 参数错误不能按坏记录处理。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：全页业务成功 | 任意失败不推进，修好后整页重拉 | 规则简单，严格全成功语义 | 一条坏数据永久卡住；违背隔离不阻塞要求 | sync 编排与游标；不用新表 | 1–1.5 人日 |
| B：持久处置后页提交 | raw 先独立提交；页内映射后把规范写入/隔离/单条死信/页统计与检查点在短事务提交 | 符合 05 §4.3，不丢坏数据、可崩溃恢复 | 页大小需受事务预算控制；必须明确页级和条目级失败 | sync/ingestion/catalog/bootstrap、新迁移约束与死信上下文；不改 Connector | 2.5–4 人日 |
| C：条目处理账本 | 每条持久状态与唯一操作 ID，完成集合后 CAS 推页 | 支持拆页、独立重试与高并发 | 新表/索引/清理与恢复逻辑，超 M3 首版 | 新账本 schema、编排、任务拆分、监控 | 5–7 人日 |

**推荐 B**。一页 100 条、97 条正常、2 条必填缺失、1 条不可恢复记录错误：raw 100 条先落库；97 条写规范层、2 条隔离、1 条死信全部提交后才推进。run.stats 必须保留 quarantined/failed，不把“可前进”伪装成零错误；建议存在记录级死信时 run=partial 且标明原因，续跑由 has_more/检查点决定，不能见到 partial 就无限重排。

| 情况 | 页处置与游标 |
|---|---|
| 单条缺必填/类型转换失败 | quarantine；保存 raw_ref、映射版本、字段路径及安全原因，提交后允许推进 |
| 单条永久非法/已达重试上限且有 raw | dead_letter；固定原映射版本与 raw 引用，持久化成功后允许推进；同条重排不得增加重复死信 |
| 单条可重试写入失败/DB 不可用/死信写失败 | 页事务回滚，不推进；已提交 raw 留存；重试原页 |
| Fetch 网络/500/429 | 没有可信完整页，按统一策略延迟重试；耗尽可记页级死信与失败 run，但仍不推进未知 NextCursor |
| Fetch invalid_param/auth_invalid/auth_expired | 参数配置错或凭据问题按资源/任务级暂停；页级死信保留请求检查点；修复配置/凭据后续跑，不能跳过尚未抓到的数据 |
| not_found / unsupported | 仅在适配器能指明具体对象时按该条 vanished/跳过；整个资源 unsupported 是终止该资源，不伪造一个成功空页 |

页提交边界：Fetch/解密/映射不在 SQL 事务；raw 独立短事务批量写；随后在 service 的短事务内提交目标父子表、隔离/死信、统计、sync_cursor 与必要 outbox。prepared 数据重复写须幂等。若 500 条及 SKU 无法满足事务 <2 秒目标/3 秒 DB 截止，先缩小平台 page_size；不能拆成多个提交却没有页完成账本就提前推进。只有确需大页时另批准 C。

DB 出错后要回滚整个事务；不能吞唯一约束等 SQL 错误后继续写死信。可预判的字段问题在入事务前分类；无法预判的单条错误若需容忍，使用明确 savepoint/回滚机制并纳入预算，否则按整页重试处理。目标行成功与 outbox 事件必须同一事务。

检查点需记录“当前请求游标/时间窗口、已提交 NextCursor、映射版本、逻辑遍历 ID、续跑状态”。可用 sync_cursor.cursor_meta、sync_run.stats、dead_letter.payload 的服务端保留字段表达，避免未审新列；元数据格式先批准。时间水位线与页 token 分开：续跑固定 Since/Until，完成整个窗口才更新已完成高水位，下一窗口按约定回看；不以坏记录时间或 NextCursor 当全窗口完成。

重试/恢复：数据库提交后、队列续跑前崩溃由同事务 outbox 重新投递；run_id 不能为 0 的所有 cron 消息各自新建 run，需逻辑触发幂等键（job + 计划触发时刻；手动用已提交 run/幂等键）。死信保存条目/页类型、raw_id+fetched_at、原 mapping_version_id、请求检查点、错误种类、尝试次数，不保存凭据或整份敏感请求。重放单条不能改变正常同步水位。分页 token 过期后用持久化窗口重建并靠幂等回看；平台不支持稳定重建时明确失败待人工处理，不伪装“不重不漏”已保证。

### Q4. 漂移检测的时机与基线

**回答**：推荐每页累积所有记录的结构摘要、每页结束比较一次，run 结束只收尾；字段路径完整扫描，样本值不完整收集。基线预热建成后只能人工 promote，不能用自动追随把事故抹成正常。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：run 结束全量摘要 | 每条更新摘要、run 结束比较；第 3 个成功周期后建基线，之后人工升版 | 符合 M3 T3.5，事件少、无额外 DB 回扫 | 大 run/故障时告警晚；若摘要只在内存，崩溃丢观测 | ingestion/drift、sync finalize、baseline/events | 1–1.5 人日 |
| B：每页完整结构摘要 | 页内全量结构扫描/合并，页末比较与持久化；人工 promote | 破坏一页内可见，部分失败也能发现，成本可界定 | 可选字段与空数组要特殊处理；需要去重并发控制 | ingestion/drift、页结束流程、初始化进度、scope、notification 写入 | 2–3 人日 |
| C：页内随机/分层抽样 | required 校验仍逐条，漂移只随机抽样，人工 promote | 大报文时可降低非关键结构扫描 | 不能保证一个周期发现稀有字段；删除推断误报，需补定期全量审查 | 抽样策略/配置/指标、审查任务、基线管理 | 2.5–4 人日 |

**推荐 B**，明确取代 M3 的“只在 run 结束比对”。结构采集针对每份可解析的原始 JSON，包括随后因映射失败而隔离的记录；映射结果不能成为漂移输入，否则恰好把最严重的数据排除。无需在结束后再扫描 raw 表，也不为每条记录写一个漂移事件。

基线维度固定为 tenant/platform/resource（与当前唯一键一致），不同 API/形态的返回需先确认是否可共用；同一平台不同店铺的数据稀疏性不能直接解释为删字段。前 3 个有数据、完整成功的逻辑采集周期收集路径/类型并集，partial 续跑不多算一次、空页不算、失败周期不建基线；初始化次数与摘要可放服务端 sys_setting，避免伪造不存在的 warming 状态列。第 3 次完成后在唯一约束保护下创建 active；已有 active 永不自动覆盖。必填逐条校验在预热阶段也执行，预热只抑制漂移噪声，不允许坏数据入规范层。

promote 必须由有权限的人选择已保存的候选摘要/来源范围，校验映射 dry-run 与 required 覆盖；同事务锁定当前 active、校验观察的 baseline_id、旧版 superseded、新版 active、写审计。ack 不更新基线；resolve 不隐式 promote；ignore 仅加入当前租户/平台/资源/基线范围的路径白名单，不得关闭必填校验或删除隔离。模型无白名单表时可经批准用 sys_setting 存有版本的规则；不把客户端 path 直接拼 SQL。

检测口径须补齐：数组遍历全部元素但路径归一为 []；每路径保留类型集合，null/缺失/空数组与真实类型变化分开。现有 fields jsonb 可改存约定的类型集合结构，但这是格式契约调整；旧格式如何读需批准。新增字段取并集即可；可选字段“移除”只表示观察窗口未出现，不是证明平台 schema 删除。建议完整逻辑窗口结束再确认可选字段消失，required 缺失则页内立即 critical + 隔离。空页、空集合、异常截断页不能宣告所有叶子被删除。

去重采用租户内 baseline_id/kind/规范化 path 的滚动 24 小时（不是自然日桶），shop 仅存首个例证，按 C17 统一；事务/advisory lock 串行检查+插入，不能并发“先查再插”。critical 事件与 channel=inbox 的 notification 同事务，通知 dedup_key 随同基线代次；M7 未完成只能保证站内通知记录存在，不能宣称邮件/Webhook 已投递。

**开销**：线性于 JSON 字节量/节点数，摘要内存 O(唯一路径数)，排序指纹 O(P log P)；复用 Apply 已解码树可省第二次解码。100k × 50 个叶子约 500 万访问，但实际数组/非映射字段也要遍历，不能只按 50 算。以上述 Q1 机器/数据测漂移开关 A/B，建议目标为总 CPU 增量 ≤15%、页摘要阶段 P95 ≤100ms；这些是验收门槛建议，无现有实测支撑。

**能否抽样**：样本值最多前三条，或只留 raw 引用，不代表只扫描三条结构。若随机独立抽样 n 条，异常比例 p 的漏检概率约 (1−p)^n；p=1%、n=20 时漏检约 81.8%，n=300 仍约 4.9%，n≈459 才约 1%。同页数据相关时该模型更不可靠。C 只可在明确接受稀有漂移漏检并加全量巡检时选用；required 安全检查不能抽样。

### Q5. 重放的并发

**回答**：整次 50 万条持同一把锁，同店铺同资源的同步确实全程停摆；其他店铺/资源不必停。按 200 条/批是 2500 批，假设每批 0.2～1 秒，仅计算约 8.3～41.7 分钟，还未含 IO/重试，因此不能用“有续租”当作不会饿死同步的答案。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：整次重放共锁 | 所有重放数据处理完才释放 | 逻辑简单、目标写入天然串行 | 同店同资源可停数小时，增量 lag 失控、退出恢复困难 | M4 replay worker/锁，无新增并发 schema | 1–2 人日 |
| B：小批共锁并让出 | 每批最多 200 条/一个有界时间片，提交检查点后释放并重排；同步优先、有公平调度 | 保留同锁约束，避免长时间独占，M3 可打好恢复基础 | 仍需防旧 raw 覆盖新数据；调度公平不是 Redis 锁自动提供 | M3 写入排序/版本策略、续跑与锁；M4 replay_run.stats 检查点及调度 | M3 公共基础 1–2 人日；M4 执行器 2–3 人日 |
| C：真正并行计算与写入 | 每业务键行级串行/CAS，按来源顺序和映射代次决定覆盖，SKU 作为聚合一起提交 | 同一店铺持续同步，吞吐可扩展 | 需正式版本列/排序规则，冲突重试与部分集合处理复杂，单靠 ON CONFLICT 不够 | listing/listing_sku 版本元数据、新迁移、Upserter 约束、回放/同步/后续订单状态机 | 5–8 人日，另含 M4 执行器 |

**推荐 B**，M3 仅准备共用 Apply/Upsert、固定版本与安全检查点；50 万条历史执行仍在 M4。每批锁内处理目标提交，批后延时重排；存在待运行正常 sync 时给其优先权，连续重放持锁最多一个批次。需显式调度仲裁/轮转，不可把普通抢锁称作公平。锁忙时内部任务延迟重排，手动重复触发仍按接口返回 60201。目标建议同店 sync 等待 P95 ≤30 秒，超过则降批量/时间片，以压测结果定。

**规范层避免写乱的必要条件（B 也需要）**：

1. 明确区分“来源新旧”和“映射新旧”。平台 updated_at 可映射进保留元数据；没有源时间时固定 fetched_at+raw_id 作为采集顺序代理，并承认它不能证明平台业务时间顺序。相同源时间但内容不同需确定 tie-break/冲突处理，不能用本地 updated_at 当来源版本。
2. 历史重放不能把旧商品价格/库存写回当前值。建议每业务键仅当该 raw 是当前已接受的来源，或该业务键尚无规范记录，才允许持久化其映射结果；范围内更旧 raw 可执行 Apply 用于统计但标 skipped，不覆盖新来源。要“恢复历史时点快照”是另一产品能力，不能在当前表偷偷实现。
3. 同一 raw、同一 mapping checksum：跳过且 updated_at 不变；同一 raw、新 mapping checksum：允许重新解释并更新。不能只按 payload_sha256 相等就跳过，也不能只因平台 updated_at 未变化拒绝修复映射。普通 sync run 与 replay 固定版本；旧版本续跑不能覆盖已经按新 active 版本解释的同一来源，检测到版本冲突应重排到新版本或记 skipped，不能 last-write-wins。
4. 由于当前表无 source_updated_at/hash/applied_mapping_version，可先提案使用 listing.ext 的保留引擎命名空间保存来源排序与已应用 checksum，raw_id 对应当前来源；禁止映射覆盖保留空间。需要类型化列/索引则新增迁移，由人批准，不能把字段硬塞进既有规范列。raw 的单个 mapping_version_id 不能表达历次解释历史，run/死信也要保留使用版本。
5. listing 父行与所有 SKU 增改在同一事务/父聚合锁内，顺序判断对整个聚合生效；不能父记录拒绝旧写但子 SKU 已覆盖。同步完整集合才允许替换，重放按 C13 不做删除，也不清除未映射旧列。
6. 固定 replay 范围上界/时间窗口/目标版本，按 raw_id keyset 分批（同时用 fetched_at 剪枝），不因新 raw 持续到达无穷扩展范围；last_processed_raw_id、统计与目标写同事务。中断重试不重复累计成功数，不推进 sync_cursor；旧映射若显式用于诊断不默认回滚当前规范层，写入旧版本须另有明确授权策略。

必须覆盖的顺序测试：旧 raw 重放后新 raw 同步；新 raw 同步后旧 raw 重放；同 raw 换映射；旧 run 在发布后续跑；SKU 完整/不完整集合；两个进程丢锁与提交竞争；批间正常同步确实取得执行机会。C 若未来采用，也需同样不变式，不能凭两把 Redis 锁并行写后声称幂等即安全。

### Q6. worker 的身份

**代码事实**：`kernel/scope/access.go:From` 要 Tenant/User>0 且存在有效角色；`bootstrap/shop_scope.go:query` 再核 tenant 与注册根实体。`bootstrap/scope.go` 只合并 identity/shop，尚无 sync/ingestion/catalog。`cmd/worker/main.go` 目前仅加载/校验配置，未装 DB、Redis、keyring 或任务授权。`bootstrap/identity.go:RegisterIdentity` 将 HTTP 路由、权限加载、shop 与 sealer 装在一起，不能让 worker 创建 Gin 来获得授权。

| 方案 | 做法 | 优点 | 缺点 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：代表用户执行 | manual 以 triggered_by 重载身份；cron 绑定指定负责用户，每页重新验证权限和店铺范围 | 直接复用现有 Scope，不需要非人身份 | 用户停用/移交即停同步；cron 没有既定授权人字段；不能自动拿店铺 owner 冒充发起人 | sync_job 授权人配置、bootstrap identity 能力端口、逐页权限检查 | 1.5–2.5 人日 |
| B：真实服务账号 | 每租户创建受控账号/角色，限制到具体店铺集合，worker 动态加载授权 | 可借用角色生命周期、可审计 | 当前 Scope 只有 self/dept 等，没有店铺 allowlist；self 会把 owner 改给机器人，dept 会过宽，all 禁用；需新增授权模型且防账号交互登录 | identity/角色/种子、店铺授权关系与新迁移、worker 配置 | 4–6 人日 |
| C：经验证的任务能力 | 独立 WorkAccess，只能针对已启用 job 的 tenant/shop/resource 与固定方法执行；人类权限与工作能力分轨校验 | 不冒充用户，最小范围，cron 生命周期清楚，保持 HTTP Scope 拒绝缺身份 | 要新增中立协议与执行器、启动授权与撤销测试，不能只塞 context 标记 | kernel/scope 中立工作声明、各模块静态集合、bootstrap 工作查询适配/凭据端口、cmd/worker | 3–5 人日 |

**推荐 C**。它是 ADR-014/015 的显式查询能力扩展提案，不是把 `From` 改成“没用户也放行”。不能通过给 User 填任意正数、Roles 填 all 来蒙混校验。

具体机制与信任链：

1. worker 进程从部署配置取得运行租户（当前单租户仍明确限定），signal 根 ctx 向下传递 deadline/cancel/trace；任务入口可创建根 ctx，业务调用不得改用 Background/WithoutCancel。bootstrap 构造不暴露给 HTTP 的任务入口与闭包能力；队列只携带标识，不携带 Scope、SQL 别名、tenant/shop 授权断言或明文凭据。
2. 调度器用登记的 `Schedule.ListEnabledJobs` 专用查询，在配置租户内只投影任务 ID/计划信息；执行入口用 `Sync.ResolveTask` 专用查询按 job_id+配置租户重读 DB，验证 job/run 关系、shop 非软删且 active、tenant/platform/resource 支持、job 未停用以及触发幂等。此处是建立身份之前的受限引导能力，类似 ADR-011 的登录/seed 专用查询；并非可调用任意表的 raw DB。客户端/队列传来的 run_id、trigger 不足以证明授权，必须对应持久化任务事实。
3. 手动/retry/隔离重放：HTTP 入队前验证 RequirePerm + shop Scope 并持久化 triggered_by、目标记录与映射版本；worker 开始及每页通过 identity 公共授权端口重载发起人的有效账户、功能权限与当前店铺范围，撤权即停止后续页，不能仅检查有角色。cron：由有管理权限的人启用 job 表示授予该店铺该资源自动同步能力，与发起人登录会话分离；在 job.options 服务端保留区保存批准者、授权策略版本、当时 owner/dept，禁止普通 options 更新覆盖这些字段。
4. cron 每页重读 job.enabled/授权版本与 shop 归属，停用、店铺删除/禁用、归属改变即撤销工作能力，移交后需重新批准启用。批准人离职是否撤销持续自动任务必须人裁决；建议持续授权独立于批准人状态，但移交必重授权。普通改名不必撤销。历史重放与授权失效投递器分别有自己的固定操作清单，不能借同步能力改角色。
5. 通过以上验证后，仅 bootstrap 可签发本次页的不可由请求反序列化的 WorkAccess/闭包：含 tenant、job/run、shop、resource、mapping_version、固定允许方法与授权代次。中立数据结构可定义在 kernel，签发入口保持内部；repo 只能调用装配好的端口，不能自行构造一个 context 即获得能力。每页重新签发并在提交前对 job 授权版本校验，确保队列延迟或在途转交不继续写旧授权。
6. 静态声明逐方法选择 Human 或 Work 策略，执行器拒绝未知主体/未知方法；Work SQL 强制 tenant+shop+resource，再经父 shop 非删/有效关系约束。sync_error 通过受保护 run，listing_sku 通过 listing，凭据通过 shop→credential→current version。mapping/baseline 是平台资源共享配置，只允许本 job 对应 profile/version 的必要读；写发布/忽略/基线 promote 不授给同步工作能力。计数、join、批量更新/删除同样套用，不能只给列表加条件。
7. HTTP 的 shopScope 与 kernel/scope.From 语义原样保留。Work 查询适配器通过 `db.WithScope` + ScopedQuery 门面绑定自己的严格谓词，不调用现有 `shopStore.query` 后寄望它接受无用户；需明确新增任务查询方法。bootstrap 启动时合并全部静态声明并冻结，depguard 继续禁止 repo 导入 GORM/kernel DB/SQL 驱动，sync 不跨 import shop 的 repo/model。
8. 新增 shop 公共凭据使用端口，向同步仅暴露受限回调/中立 DTO，不暴露 ciphertext/version model 或通用解密能力。入口先按工作能力查已验证关系，检查凭据状态/expiry/current_version，重建五维 AAD，再调用现有 `credential.OpenVersion`（放在 shop 内部或 bootstrap 适配边界），记录 `actor_type=system`、`detail` 中的 worker/job/run 标识与 `metadata_only=false` 的 read 审计；manual 另记发起人 ID，不伪造为实际解密主体。000004 的 actor_type CHECK 仅允许 user/system/api_client，不能直接写 worker，也不修改旧迁移。审计失败不调用平台；短事务取版本与审计后提交，HTTP Fetch 不持 DB 锁。回调内转换中立 Credential，用后释放/尽力清零；Go string/map 无法保证物理擦除，不把“clear byte slice”宣传为所有明文已擦除。
9. API 与 worker 复用同一 keyring 构造能力，配置缺旧钥时返回既有 30501、停本 job 并报警，不能回退成明文、当作认证过期无限刷新。工作解密路径保留 M2 的六通道敏感信息断言；队列/错误链/日志/审计不包含密文、签名或 Values。keyring 不等于身份验证，拿到密钥不能代替通过关系授权。

Q6 的验收矩阵至少包含：无主体、伪造 tenant/shop/run、disabled job、删除/移交店铺、未注册方法、越权资源、引用别人的 raw/死信、发起人撤权、批准后排队延迟、ctx 取消；每项读/计数/写与父关联 SQL 都覆盖。另做授权通过但审计失败、AAD 被调包、旧钥缺失等失败路径。缺失身份不能执行任何普通 repo 查询；只有明确登记的引导端口可运行，这与“默认 all”有本质不同。

### 3.7 附加阻断项：跨抓取时间 raw 去重

分区表的唯一约束必须包含分区键，无法直接在当前 fetched_at 月分区父表建立任务卡六列全局唯一约束。必须在人确认语义后写迁移，不能靠 ON CONFLICT DO NOTHING 无目标来掩盖问题。

| 方案 | 做法 | 优点 | 缺点 / 语义代价 | 影响面 | 工作量 |
|---|---|---|---|---|---|
| A：批次幂等 | 沿用模型七列唯一键，重试时复用原 fetched_at | 无新表，适合页重试去重 | 新一轮抓取时间不同仍增行，不满足 PRD“重复抓取不增行”，须明确降低要求 | T3.3 与验收说明，cursor_meta 保存批次时间 | 0.5–1 人日 |
| B：独立去重目录 | 新非分区 raw 去重目录，对六列建唯一键，原子取得或创建 raw_ref(id,fetched_at)，与 raw 插入同事务 | 保留月分区，能抗并发保证跨抓取去重，返回已有 RawRef | 新表/迁移、归档清理与历史引用策略需批准；目录也是需管理的大表 | 新增 ingestion 迁移、SaveRaw、范围声明/测试、归档与恢复 | 1.5–2.5 人日 |
| C：锁内查重 | 对六列摘要做事务 advisory lock，查已有 raw 后再插；保留七列约束 | 不新增目录，可保留当前表 | 依赖所有写入口遵守协议，查询可能跨分区变慢；归档后无法只靠在线表查重 | SaveRaw/bootstrap、查重索引与压测、归档目录读取 | 2–3 人日 |

**推荐 B，须单独批准新增目录表**。raw_ref 内部以 (id,fetched_at) 定位，现有 raw_id 单列接口若暂保留，至少要求 id 全局序列生成并持久保存其 fetched_at 供定位/分区剪枝，不能把“无物理外键”当作可忽略引用完整性。

先确认去重期限：建议在线与可重放归档保留期内返回同一 raw_ref，归档后从 manifest/目录定位；不因新抓取自动修改旧 raw.fetched_at，也不覆盖原 mapping_version_id 来冒充所有解释历史。业务的新鲜度由抓取/run 观测记录，不改变不可变 raw 内容；latest 选择不能只按旧 raw 的 fetched_at 推断“最近又看到”。若要不同日期留快照，需要明确改为内容体去重+独立观测记录，不得一面要求全局不增行一面要求 raw 每天新增完整快照。hash 对 JSON 原始字节还是规范化 JSON 计算也须固定，推荐语义规范化后摘要并拒绝无法保留的重复键；“仅空白改变是否新行”必须有 fixture。

## 4. 未来 2 个里程碑的坑（只列不展开）

- M4：只按 hash/source_updated_at 跳过会让新映射重放完全无效。
- M4：历史 raw 顺序覆盖 listing，会把最新价格/库存回退。
- M4：collections 整体替换与重放不删除冲突，旧 SKU 的处置需单独口径。
- M4：raw_id 跨分区定位、归档恢复与未决隔离引用会阻碍 50 万条重放。
- M4：重放长持锁与抢锁无公平性会把同步 lag 推到告警阈值以上。
- M5：timestamp 增量的固定窗口、同时间戳分页与回看去重会暴露游标元数据不足。
- M5：订单状态机不能复用商品 last-write-wins，旧事件/重放可能倒退已完成状态。
- M5：订单原文含 PII，JSONB raw、dry-run、ext 与归档必须共同落实访问控制和加密策略。
- M5：Webhook 与轮询合流需要同一业务排序/幂等规则，不能各自建锁即认为不冲突。
