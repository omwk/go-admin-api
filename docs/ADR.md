## ADR-001 · 采用模块化单体，而非微服务

**状态**：已接受（2026-10）

**背景**：单人 + Codex 开发；单租户；日订单量 ≤ 5 万。需要同步、网关、计费多个子系统，但它们共享用户、店铺、商品、订单数据。

**决策**：单仓库、单 Go module，`internal/modules/<domain>` 分包，模块间通过 `contract.go` 接口调用；进程拆成 `cmd/api` 与 `cmd/worker` 两个二进制，共享代码。

**理由**：
- 事务边界清晰：订单入库 + Outbox 事件在同一事务，微服务下要引入 Saga。
- 部署简单：一个 compose 文件即可跑全栈，符合 1–3 人团队。
- 模块边界通过目录和 lint 规则强制，未来拆服务时按 module 切即可。

**代价**：
- 单个二进制体积变大（可接受）。
- 模块间仍可通过 import 越界，需要 code review + 后续引入 `depguard` 规则兜底。

**替代方案与否决理由**：
- 微服务：跨服务事务、链路追踪、部署复杂度对当前规模是负收益。
- 纯单体无模块边界：半年后必然变成意大利面。

## ADR-002 · 数据分三层：原始层 / 规范层 / 映射层

**状态**：已接受

**背景**：多平台字段结构差异大且持续变化，文档滞后。若直接把平台字段映射进业务表，上游一变就必须改代码、改表、回刷历史。

**决策**：
1. **L1 原始层** `raw_payload`：上游报文原样落库（JSONB），只追加，带 SHA256 与解析版本。
2. **L2 规范层**：平台无关的 `product_spu/product_sku/sales_order/...`，核心字段建列，平台差异进 `ext jsonb`。
3. **L3 映射层** `mapping_version.spec`：声明式 JSONPath + 表达式，存库、版本化、可热更新。

**理由**：
- 历史可重解释：映射修好后可对历史 raw 重放，不用等平台补数据。
- 变更影响面收敛：字段变化 → 改映射，不发版、不动表。
- 调试友好：任何规范字段都能追溯到「哪条 raw、哪个映射版本」。

**代价**：
- 存储成本（分区 + 180 天归档缓解）。
- 映射 DSL 需要一套校验与调试工具（M3 必须做 dry-run 预览）。

**不可妥协点**：raw 必须先落库再解析，解析失败不能丢数据。

## ADR-003 · PostgreSQL 作为唯一主库

**状态**：已接受

**背景**：需要 JSONB 检索、部分索引、分区、`ON CONFLICT` 幂等写入、行级安全（未来多租户）。

**决策**：PostgreSQL 16，不用 MySQL。大表（`raw_payload`、`api_call_log`）按月 RANGE 分区。

**理由**：
- JSONB + GIN 是处理异构平台数据的关键能力。
- `insert ... on conflict do update` 天然做幂等 upsert。
- 部分索引（`where deleted_at is null`）节省空间且精确。
- 未来多租户可上 RLS，无需改应用层查询。

**代价**：团队若不熟 PG，运维（vacuum、分区维护）需要学习。

## ADR-004 · 映射用声明式 DSL（expr-lang），不写平台解析代码

**状态**：已接受

**背景**：若每个平台写一段 Go 代码解析，字段一变就要发版；且平台数量增长后代码量爆炸。

**决策**：
- 取源用 JSONPath（`$.item.price.amount`）。
- 转换用 `expr-lang/expr` 表达式，预置函数：`trim / upper / lower / int / decimal / ts / default / coalesce / map_status / concat / split`。
- 映射以 `mapping_version.spec` 存库，发布后不可变。
- 平台适配器只负责「取数据」，不负责「解释数据」。

**为什么是 expr 而不是 CEL / govaluate**：
- expr：Go 原生、类型安全、可静态编译校验、性能好、语法接近 Go。
- CEL：能力强但依赖重、语法对运营不友好。
- govaluate：已停止维护。

**代价**：复杂嵌套转换（如多 SKU 数组展开）表达力有限，需要保留「代码级 transform 扩展点」——通过注册自定义函数解决，不通过写死逻辑。

**约束**：`map_status` 的状态映射表存 DB（`sys_setting` 或 `platform.settings`），不硬编码在表达式里。

## ADR-005 · 凭据信封加密 + 不可变版本链

**状态**：已接受

**背景**：token/key/cookie 有效期 7–30 天，需自动刷新；刷新历史要可追溯；数据库泄露不能直接拿到明文。

**决策**：
- 加密：AES-256-GCM，字段级信封加密，`key_version` 支持主密钥轮换，AAD 绑定 `tenant:shop:kind:version`。
- 存储：`credential_version` 不可变，每次刷新插入新行，旧行标 `retired_at`。
- 保留：密文 90 天后由清理任务删除（`purge_after`），元数据永久保留。
- 审计：`credential_audit` 记录每次读取/刷新/轮换，**不记录明文**。
- 接口：只写不读；展示仅 `fingerprint`（sha256 前 12 位）。

**理由**：
- 版本链让「某笔订单当时用哪个 token 拉的」可追溯。
- 90 天足够覆盖绝大多数排障窗口，同时限制暴露面。
- AAD 防止密文在店铺间被调包使用。

**代价**：主密钥丢失 = 所有凭据不可恢复，必须实现导出/备份流程（M10）。

## ADR-006 · 分享采用「报价单 + 快照」双冻结

**状态**：已接受

**背景**：同一商品对不同客户报价不同；分享出去的页面若随上游改价/改字段而变，会造成商务纠纷。

**决策**：
- **价格**永远来自 `price_list_item`，不回落到平台价（除非配置允许且无报价）。
- **内容**默认快照（`share_snapshot.payload` 冻结），可切换 `live` 模式只实时读库存。
- 快照重新生成必须写审计并 bump `checksum`，视为一次「对外承诺变更」。
- token 只存哈希，支持有效期、次数、密码、撤销。

**理由**：对外承诺必须可举证。快照是把「当时给客户看的是什么」固化的唯一手段。

**代价**：改价后旧链接仍是旧价，需要运营显式重新生成——这是**有意的**，防止误改。

## ADR-007 · 网关预扣费 + 日终对账

**状态**：已接受

**背景**：开放 API 若后付费，会被刷爆；若只在网关层计数不落账，无法对账。

**决策**：
1. 请求进入 → 查授权与配额 → 预估费用 → `wallet` 条件更新冻结（`balance - frozen >= amount`）。
2. 调用成功 → 冻结转扣减；失败（5xx/超时）→ 释放。
3. 每个请求写 `api_call_log`（异步批量），按天聚合到 `usage_daily`。
4. 每日 02:00 对账：`usage_daily.amount_cents` 之和 vs `wallet_txn` 当日 `commit` 之和，差异 > 0 告警并落 `90401`。
5. 幂等键 = `trace_id`，重复提交不重复扣。

**理由**：预扣是唯一能同时保证「不超支」和「低延迟」的方案；对账是发现漏洞的最后一道闸。

**代价**：
- 失败释放有延迟窗口（需监控 `frozen_cents` 长期不归零的钱包）。
- 需要处理「上游实际收费但网关判定失败」的边界，用日终对账兜底。

## ADR-008 · 单租户运行 + 全表预留 tenant_id

**状态**：已接受

**背景**：当前只自用，但存在未来对外销售的可能。多租户改造的最大成本是「所有表 + 所有查询 + 所有唯一索引」。

**决策**：
- 所有业务表带 `tenant_id bigint not null default 1`。
- 唯一索引一律以 `tenant_id` 开头。
- 租户 `tenant_id` 的基础隔离可由 GORM 全局 Scope 自动注入；后台任务从任务载荷显式传递。该租户条件与 M1 的用户/部门/owner 数据权限不是同一机制；M1 的行级数据权限必须按 ADR-011 显式套用，不使用 GORM 全局 callback。
- **不做**：租户级独立库、RLS（预留，未来加策略即可）、租户计费。

**理由**：现在多花 5% 的成本，换掉未来 40% 的重构。

**代价**：每个查询多一个条件，索引多一列；开发者必须记得在原生 SQL 里也带上（用 lint/review 兜底）。

## ADR-009 · 契约先行：OpenAPI 手写，代码跟随

**状态**：已接受

**背景**：让 Codex 自由发挥接口设计，会导致前后端对接时反复返工。

**决策**：
- 每个里程碑先在任务卡里列出接口表（方法/路径/入参/出参/错误码）。
- 里程碑结束时导出 `api/openapi/<module>.yaml`，CI 做 diff，变更必须显式提交。
- 代码实现必须与契约一致；不一致时改契约要单独 PR 并说明。

**理由**：契约是人与 Codex 之间的「接口合同」，比口头描述稳定得多。

**代价**：多一道文档维护成本。用「里程碑末统一导出」降低频率。

## ADR-010 · 评审采用 Gate 提案制

**状态**：已接受

**背景**：让 Codex 在每个任务里都「深度思考架构」，会导致反复重构、过度设计、上下文漂移。

**决策**：
- 每个里程碑开始前一次 **Gate A**：Codex 只读文档，输出 `docs/proposals/Mx-review.md`，格式固定（问题 / 方案 / 优劣 / 推荐 / 影响面 / 待决策）。**禁止改代码。**
- 实现过程中，仅在遇到「数据模型变更 / 对外契约变更 / 安全相关 / 性能瓶颈」时发起**定向评审**，一次只评审一个点。
- 每个里程碑结束一次 **Gate C** 验收，对照清单打勾。
- 人的裁决写入 ADR 后才允许实现。

**理由**：把「思考」限制在有边界、有产出物、有人裁决的阶段，既拿到评审收益，又避免实现期震荡。

**代价**：每个里程碑多花 0.5–1 天在评审上。经验上这笔投入在 M3 之后回报极高。

## ADR-011 · 权限模型：三段权限码、菜单权限分表、显式数据权限、版本化缓存

**状态**：已接受（2026-10-31，人裁决 Q1=B、Q2=A 调整、Q3=A、Q6=C 核心；取代 M1 初稿中的权限码混用、超管绕过数据权限与全面不建物理外键的约定）

**背景**：M1 设计评审（`docs/proposals/M1-review.md`）发现权限码层级混用、超管数据范围不一致，以及 5 秒生效要求缺少主动失效保障。以下是本次人工裁决后的执行口径。

**决策**：

1. 权限码固定三段 `module:resource:action`，首段必须等于 `sys_permission.module`，service 层校验。
2. `sys_menu` 与 `sys_permission` **保持分表**；`sys_menu.permission_code` 建复合外键 `(tenant_id, permission_code) → sys_permission(tenant_id, code)`，删除用 RESTRICT。**只对配置类小表及其关联表建物理外键**；业务大表（如 `sales_order`、`raw_payload`、`api_call_log`）以及业务表到配置表的引用不建物理外键，由应用校验和一致性检查保证。此规则取代 M0 任务卡的全面不建外键约定，不追改已合并迁移。
3. 鉴权只认 `sys_permission.code`；`sys_menu.permission_code` 仅用于前端展示与关联。
4. 数据权限**显式套用**：由 bootstrap 注入封装 `db.Scoped(ctx, model)` 的 ScopedQuery 门面，repo 不取得原始 GORM handle；`depguard` 禁止 repo 层 import `gorm.io/gorm`、`internal/kernel/db` 和直接 SQL 驱动。使用现有 golangci-lint 的 depguard，**不写自研 AST**。每个受限 repo 的列表、详情、计数、更新/删除及 join 查询均纳入 DryRun 测试矩阵，核验 tenant 条件、五种 scope、别名及缺失身份时拒绝查询；另做跨 owner 集成测试。repo 只暴露接口，测试用 Go reflection 比较接口方法与 DryRun 用例登记集合，缺项失败，私有辅助路径归入调用方法的分支用例。depguard 约束导入，DryRun 核验 SQL，两者不能互相替代。登录、refresh hash 解析、身份/授权加载及 seed 由 bootstrap 注入专用查询能力，按已确定租户、已验证 token 的用户/sid 或内部 seed 租户限定，不依赖尚未建立的用户数据 Scope；同样登记 DryRun，不提供客户端可控的通用绕过开关。
5. `is_super` **只跳过 RBAC，不跳过数据权限**；超管看全量靠种子角色 `super_admin` 的 `data_scope='all'`，并写不变式测试防止被改坏。
6. 授权缓存版本化：版本键 `authz:ver:{tenant}:{user}` 无 TTL；权限键 `authz:perm:{tenant}:{user}:v{n}`、菜单键 `authz:menu:{tenant}:{user}:v{n}` 的 TTL 均为 5 分钟。读取先取版本，再查缓存/DB，回填只能使用该次读取的版本；变更事务提交后同步 `INCR` 所有受影响用户版本，旧 key 不再命中。权限授权、菜单授权、用户角色、角色状态/数据范围及菜单配置变化均覆盖失效；菜单和权限使用同一版本。
7. M1 只做版本键与同步 INCR，**outbox 失效重试推迟到 M3**。Redis 正常时，后端鉴权和下一次 `/auth/menus` 查询在 5 秒内看到变更；Redis 故障时不继续使用本地旧授权，鉴权按 ADR-012 拒绝服务。INCR 失败记录安全的 Warn 与 `authz_invalidate_failed_total`，恢复后遗留旧缓存最多按 5 分钟 TTL 淘汰，不宣称故障期间也满足 5 秒。已打开页面的菜单需前端重新请求；M1 不做前端代码或推送。

**理由**：

- 三段码给模块命名空间，模块首段与 `module` 字段一致，种子、鉴权配置及文档统一采用这一种语法。
- 分表保住「路由展示」与「接口能力」两个独立生命周期；外键把「菜单指向不存在的权限码」挡在写入时。
- 显式 Scope 让 join/子查询的归属在调用点可见；`depguard` 是配置级约束，比自研 AST 分析器便宜一个数量级。
- 版本键解决「删缓存后并发请求又写回旧值」的经典竞态，单纯 DEL 无法解决。

**代价**：

- 权限码变长，种子、前端配置、验收脚本都要跟着改。
- `module` 列与 code 首段冗余，需要校验保持一致。
- `depguard` 只能挡 import；绕过 `Scoped` 手写 SQL 仍需 DryRun 测试兜底。
- 缓存 key 依赖版本值，读取版本后才能读取对应缓存；这两步有依赖，不能当作独立查询合并到同一 pipeline。
- M3 接入 outbox 前，失效故障靠告警和 TTL 收敛；这是 M1 明确接受的暂时限制。

**被否决的方案**：两段码（改动面更大、与常见 admin 模板约定不符）；合并菜单与权限表（单表容纳互斥字段，迁移风险高）；GORM 全局 callback 注入（join/alias/Raw 下归属难判且不可见）；单纯 DEL 缓存（并发写回无法解决）。

## ADR-012 · 会话族、刷新轮换与失效命名空间

**状态**：已接受（2026-10-31，人裁决 Q4=B 加 30 秒宽限、Q5=A）

**背景**：轮换只撤销当前 refresh 本身不会踢掉其他设备；若按 user 撤销全部 token，才会误伤其他设备。现有单 token 记录缺少稳定会话关联，需要 family 支持按设备撤销，并区分三种失效对象的生命周期。

**决策**：

1. 每次登录生成 `sid`；同一 `sid` 的 refresh 构成一条链，轮换只影响本链。access JWT 带 `sid` 与 `jti`。
2. `sys_refresh_token` 增加 `session_id`、`replaced_by_token_id`、`revoked_reason`。
3. 轮换在单个 DB 事务内完成：锁定并校验旧行，插入同 `sid` 的新行，更新旧行的 `revoked_at`、`revoked_reason=rotated` 和 `replaced_by_token_id`。Redis 失效标记在提交后同步写入，禁止在 DB 事务内执行 Redis IO。同一 sid 的刷新与整族撤销必须串行协调，防止踢出与刷新并发产生新 token。
4. **30 秒宽限仅适用于轮换旧 token**：family 仍有效且 `revoked_reason=rotated` 时，距首次轮换时间 ≤30s 的复用返回 HTTP 409 / `20109 ErrRefreshInFlight`，**不撤 family、不签发、不重新计时**；超过 30s 才按重放撤销该 sid 全部 refresh，并返回 401 / `20103`。登出、强踢、重放撤销不享受宽限，立即返回 `20103`；自然过期仍为 `20102`。Redis 旧 refresh 标记不可在 DB 判定宽限前直接拦成 `20103`。
5. Redis 三套独立命名空间：
   - `auth:v1:revoked:access:jti:{jti}`，TTL = access 剩余有效期
   - `auth:v1:revoked:refresh:sha256:{token_hash}`，TTL = refresh 剩余有效期
   - `auth:v1:revoked:session:{sid}`，TTL = 该 sid 最晚 refresh 的剩余有效期
6. 轮换只写旧 refresh key；登出/强踢写 session key，并标记可确定的目标 access JTI 和 refresh hash，不能把管理员自己的 JTI 当成目标。JWTAuth 必须同时校验 JTI 与 sid；session 标记覆盖该 sid 的所有 access。DB 是 refresh 撤销事实源，Redis key 不保存明文 token，剩余 TTL ≤0 时不写。
7. Redis 不可用时 **fail closed**：依赖故障返回 HTTP 503 / `10002`，明确已撤销返回 HTTP 401 / `20103`；`/readyz` 反映降级。DB 已提交而 Redis 写入失败时不得声称撤销成功，需保留 DB 状态并暴露故障；恢复后鉴权仍应检查会话已被持久撤销，不能只凭 Redis key 不存在放行。

**理由**：

- 只有 `sid` 能同时满足「多端隔离」「按设备踢下线」「重放只影响该设备」三个需求。
- 宽限期吸收浏览器多标签页、移动端网络重试造成的并发刷新；没有它，严格轮换会把正常用户踢下线。
- 三类对象生命周期不同（15 分钟 / 7 天 / 7 天），key 必须分开，TTL 才能各算各的。

**代价**：

- 每次鉴权多一次 Redis 查询（可 pipeline 合并）。
- Redis 成为鉴权硬依赖，这是可用性上的明确取舍，需配套告警。
- 客户端收到 `20109` 后等待同一客户端的刷新请求结果，使用已经成功下发的新 token；服务端不重发明文。若成功响应丢失且客户端拿不到新 token，则重新登录，不循环重试旧 token。

## ADR-013 · 登录保护与 M1 分批交付

**状态**：已接受（2026-10-31，人裁决）

**决策**：

1. 登录失败按租户内用户名计数，连续 5 次失败锁定 15 分钟（423 / `20104`），更换 IP 不能绕过用户名锁定；IP 只限流，不触发账号锁定。IP 超限返回 429 / `10005`，不增加用户名失败计数。

## ADR-014 · M1b 的权限、失效与种子语义

**状态**：已接受（2026-10-31，人裁决；输入 `docs/proposals/M1b-review.md`）

**决策**：

1. **数据权限（Q1）= A**：repo 方法引用「内部查询声明」，声明包含根实体、固定别名、tenant 列、owner 映射、dept 来源与关联保护规则；bootstrap 绑定 Scope。HTTP 不接受 `owner_column`/`alias`/`skip_scope`。未登记的模型或缺失身份**直接拒绝**，不降级为 `all`。
   - 映射：用户 `self → sys_user.id`；会话 `self → sys_refresh_token.user_id`；角色/菜单/权限是租户共享配置，采用显式登记的「tenant + RequirePerm」策略，不虚构 `created_by`。
   - 多有效角色的 scope **取并集**，`all` 吸收其余；无有效角色 → 拒绝。
2. **失效（Q2）= A**：DB 提交后按受影响用户去重，用 pipeline 分批（起点 500/批，最多 2 个执行单元）同步 INCR，逐键记录结果，仅在剩余预算内重试一次失败键。
   - **对评审的修改**：失效失败**不返回 503**。业务变更已经提交，返回 503 会诱导客户端重放已成功的变更。改为：正常 2xx + 响应头 `X-Authz-Invalidation: pending` + `authz_invalidate_failed_total` 指标 + Warn 日志，由 5 分钟 TTL 兜底收敛。鉴权类接口（登录/刷新/登出）仍 fail closed。
   - 5 秒 SLA 只对「Redis 正常、约定负载、同步路径完成」成立，需附 2000 用户的实测数据，不接受推算。
3. **强踢（Q3）= A**：复用 refresh 全族历史 + 「无未撤销行即拒绝」。过期行照样可以写 `kick`；物理无行时本就拒绝，不伪造墓碑行。已知目标重复踢返回 204；完全未知或不可确认归属返回 404（不泄露其他租户会话）。不新增 session 表。
   - **纠正评审前提**：refresh 过期不等于行被删除，现有查询也没有按 `expires_at` 过滤，这一点评审说得对。
4. **权限码（Q4）= A**：Go registry 是唯一词典；种子遍历 registry；`RequirePerm` 通过结构化路由声明绑定常量；确定性导出权限清单；OpenAPI 手写但必须带 `x-permission`；CI 比对「方法+路径→单个完整码」。前端消费方式留后续。
5. **菜单移动（Q5）= A**：`sys_menu.path` 保持路由语义，不改物化路径。同租户树 advisory lock 内重读全图（含隐藏/禁用节点），校验父存在、非同租户、非自身子孙、新根深度 + 子树高度 − 1 ≤ 5，再更新。成环 400/`20106`，超深 400/`10001`，不新增错误码。
6. **种子（Q6）= B**：M1b 只补本期 `system` 完整码并保留 M1a 已有兼容项；未来模块随各自里程碑增量登记。**重跑种子不得复活被手工撤销的授权**：新建角色才写默认授权，已有角色只做显式批准的增量。
7. **D1 = 例外，不加 version 列**：M1b 的用户/角色/菜单沿用现有表结构。更新语句必须检查 `RowsAffected`，为 0 时返回 404（目标不存在或超出范围），禁止把零行修改当成功。乐观锁推迟到真正出现并发编辑诉求时（M10 之前复审）。本例外写进 `docs/04-conventions.md` §2.5。
8. **D2 = 专用授权端点**：`PUT /users/{id}` 只改标量字段（昵称、邮箱、状态等）；角色分配走 `PUT /users/{id}/roles`，自定义部门走 `PUT /roles/{id}/depts`。授权范围受操作人自身可管理范围约束，不能借关联写入越权。
9. **删除语义（2026-10-31 追加，替代评审未覆盖项）= 按表分类，本期不加迁移**：
   - **业务实体软删除**：`sys_user` 已有 `deleted_at`，保持软删（登录与历史引用需要）。
   - **配置类小表物理删除**：`sys_role`、`sys_menu`、`sys_permission`、`sys_dept` 无 `deleted_at`，本期物理删除。理由：配置表被引用时删除本来就该被拒绝；软删会制造「已逻辑删除但仍被外键引用」的幽灵行，导致权限解析、菜单树、种子比对每条查询都要加过滤，收益为负。
   - **物理删除前必须显式检查引用**，返回 409 而不是让外键抛出 500：角色被 `sys_user_role`/`sys_role_menu`/`sys_role_permission`/`sys_role_dept` 引用 → 409/`20105`；菜单有子节点或被 `sys_role_menu` 引用 → 409/`10004`，`details` 指明是 `children` 还是 `roles`。
   - **删除必须检查 `RowsAffected`**，为 0 返回 404（不存在或跨租户）。
   - **内置角色不可删**：`super_admin` 删除返回 409/`10004`；内置管理员账号不可删除。
   - **硬删必须写完整快照到审计**（`before` = 整行，`after` = null），因为物理删除后无法回溯；本系统不提供「从回收站恢复」，需要时从 `audit_log` 手工重建。

**理由**：这八条把「越权、撤权不生效、种子复活授权」三类事故挡在实现前，且都不需要改表结构。

**代价**：
- 查询声明与 DryRun 矩阵是实打实的工作量（约 2 人日），且新增 repo 方法必须同步登记。
- 失效失败时返回成功但可能短暂保留旧权限，属于已接受的 M1 限制（≤5 分钟）。
- 无 version 列意味着并发编辑是 last-write-wins，只能靠审计追溯。

**被否决的方案**：`sync 503`（会诱使重放已提交的变更）；新增 session 表（超出既定模型）；菜单加物化路径列（收益不抵迁移成本）；预置全部未来模块权限（给不存在的功能建长期兼容负担）。

## ADR-015 · M2 的加密、数据范围、幂等与权限发布

**状态**：已接受（2026-10-31，人裁决；输入 `docs/proposals/M2-review.md`）

**决策**：

1. **Q1 = B · 查询声明分层**：中立声明协议与校验放 `kernel/scope`；identity 与 shop 各自导出**静态**声明集合；bootstrap 启动时合并、校验、冻结。身份、有效角色、`RequirePerm`、authz 缓存仍归 identity。`kernel` 不 import identity，`shop` 不 import identity 的 repo/model。重复名、未知实体、缺父关系 → 启动失败。
2. **Q2 = B · 版本化 keyring**：多版本可读、单一活动版本写入；密钥由部署注入（环境变量或受控挂载文件），配置示例不得含有效密钥。M2 **不做**历史批量重加密、不接 KMS。
   - **术语修正**：现有实现是**版本化 AEAD**（主密钥 + `key_version`），不是真正的信封加密（没有 DEK / wrapped DEK）。ADR-005 的「信封」按此理解；真信封留后续，不在本期假装已有 DEK 层。
   - **AAD 改为五维**：`tenant:shop:credential:kind:version_no`。解密时从已校验的 tenant → shop → credential → version 关系**重建** AAD，库中 `aad` 列只做一致性校验，不直接信任。
3. **Q3 = B · 只写不读的可验证契约**：固定安全投影 DTO；六通道自动断言——响应/响应头、应用与 SQL 日志、错误链、审计 `detail`、数据库全列直查、加密正向证明（能用预期 AAD 解开且等于提交值）。
   - Cookie 的 UA/浏览器指纹、Cookie 附加数据**一律进加密 values**；`extra` 只放明确公开的元数据。
   - 元数据读取也记 `read`（`detail.metadata_only=true`）；审计写入失败 → 不返回成功。
4. **Q4 = B · shop 为范围根**：`shop` 受 `owner_user_id` 与 `dept_id` 保护；`shop_credential` / `credential_version` / `credential_audit` 通过父 shop 继承范围，不冗余归属列。
   - `dept` 系列 scope 用 **`shop.dept_id`**，不跟随负责人当前部门；owner 与 dept 可独立分配，移交店铺不自动改部门。
   - 越界（含跨租户、已软删）统一 404 / `30101`，不区分「不存在」与「无权限」以防枚举。
   - 创建时未指定归属 → 默认填当前用户与部门；显式指定 → 校验在操作人可管理范围内。更新归属要同时校验**旧记录可管理**与**新归属可管理**。
5. **Q5 = B · 幂等**：`kernel/idem` 定义端口与哈希规则，HTTP 只做薄适配；占位、业务变更、成功审计、结果序列化在**同一 service 事务**内，最后置 `completed`。
   - TTL 24h，只回放**已提交成功**的结果；提交前失败不缓存。
   - 处理中 → 409 / `10004`；同键不同请求体 → 409 / `10006`。
   - 哈希包含路径参数与规范化后的请求体字节；**multipart 用固定排序的字段 + 文件摘要**，不含 boundary。
   - 文件上传不进 SQL 事务：对象键由租户/用户/幂等键摘要 + 内容哈希确定，可重复 PUT；上传完成后在短事务里登记 `file_object` 与幂等结果。
6. **Q6 = B · 权限增量发布**：本期 registry 只增 shop 的 11 个完整码（5 个 `shop:store:*` + 6 个 `shop:credential:*`）。已有角色**不自动获权**，通过一次性 CLI 发布命令：事务内重读当前集合 → 只插入批准的新增 → 同事务写 `sys_setting` 发布标记与审计 → 提交后走既有 `authz.Invalidate`。同一发布 ID 重跑不补权。
7. **D1 = shop 采用全局 version**：`shop` 表加 `version integer not null default 0`，更新走乐观锁，冲突 409 / `10409`。凭据响应里的 `version` 指 `version_no`；凭据轮换用主记录行锁，不用 `shop_credential.version`。
8. **D2 = 平台与上传的边界**：`platform` 只做种子 + 登录后只读（全局目录，无 tenant/owner）；上传先做 multipart 有界流式，不做预签名直传；凭据 `Check` 返回 `ErrUnsupported`，**不得**当作健康成功；审计动作统一为 `disable`（不混用 revoke）。
9. **D3 = 排期**：M2 按 **8–11 人日**排期，沿既有任务逐项交付；KMS、历史重加密、凭据自动刷新、outbox 失效重试均不并入本期。

**理由**：M2 是第一个真实业务模块，也是「权限机制能否跨模块复用」的第一次检验。若在 shop 里复制一套范围逻辑，M1b 的矩阵就作废；若不改 AAD，同店同类型多凭据存在调包残余风险；若幂等不进业务事务，重试会重复写。

**代价**：
- `kernel/scope` 抽取要带 M1b 回归，约 1–1.5 人日。
- keyring 让配置多一层版本管理，运维必须保留旧钥并做恢复演练。
- 五维 AAD 与全通道断言显著增加测试量（这也是工期从 3 涨到 8–11 的主要原因）。

**被否决的方案**：identity 集中登记 shop（业务表进身份模块）；单主密钥只留版本字段（换钥即失读）；shop 子表冗余 owner/dept（移交时易漂移）；纯 httpx 幂等中间件（无法与业务同事务）；先人工逐角色授权（易漏且无法核对）。

## ADR-016 · M3 的同步骨架、映射边界与任务身份

**状态**：已接受（2026-11-01，人裁决；输入 `docs/proposals/M3-review.md`）

**决策**：

1. **Q1 = B · 有界 DSL + 注册纯函数**。首版只支持「一层 collections + value 转换 + 状态查表 + 金额换算」；跨字段回退（`coalesce(value, $.x)`）不支持，需要时按真实 fixture 再加，不在适配器里写平台解析。
   - 发布门禁：schema_version/resource 校验 → target 白名单与重复检测 → JSONPath 预编译与深度限制 → expr 类型检查与纯函数白名单（禁 IO/随机/时间）→ **状态表快照纳入 spec 与 checksum** → 20 条 dry-run → CAS 切换 active。
   - `required` 查源缺失，**不得被 default 掩盖**；金额用十进制运算，不经 float64。
2. **Q2 = B · 迁移建结构 + 独立维护任务**。迁移建函数与当月/下月分区；维护任务启动核查、每日预建未来两个月、缺覆盖告警。**不做 DEFAULT 分区兜底**。缺分区视为可恢复基础设施错误：保留原页与检查点、延迟重排，游标不动。
   - 归档：流式压缩 JSONL → 校验（条数/范围/摘要/读回）→ 原子 manifest → 才 detach/drop。在线保留 **180～211 天**（整月粒度），不宣称精确 180 天。
3. **Q3 = B · 「整页成功」= 每条都有已提交的持久处置**。raw 独立短事务先落；随后一个短事务提交「规范层写入 + 隔离 + 单条死信 + 页统计 + 游标」。有单条失败时 `run=partial` 但允许推进；**页级 Fetch 失败不推进**（无可信 NextCursor）。DB 错误整页回滚重试，不吞唯一约束后继续写死信。
4. **Q4 = B · 每页全量结构摘要**。结构从**原始 JSON**采集（含随后被隔离的记录），映射结果不作漂移输入。前 3 个「完整成功的逻辑采集周期」预热，第 3 次后建 active 基线；之后**只能人工 promote**，永不自动覆盖。去重按租户内 `baseline_id + kind + 规范化 path` 滚动 24h，shop 只记首个例证。
5. **Q5 = B · 每批共锁并让出**。M3 只准备共用 Apply/Upsert、固定映射版本、来源排序策略与安全检查点；**50 万条历史执行器留 M4**。每批 ≤200 条或一个时间片，提交检查点后释放并重排；有待跑的同步时优先同步。
   - 来源新旧 ≠ 映射新旧：同一 raw + 新 checksum 必须允许重解释更新；旧来源不得覆盖更新来源；父 listing 与全部 SKU 在同一事务/聚合锁内提交。
   - 来源排序与已应用 checksum 先存 `listing.ext` 的保留命名空间，禁止映射写入该空间；需要类型化列时另开迁移。
6. **Q6 = C · 独立任务能力（WorkAccess）**。worker 不冒充用户：bootstrap 在启动时合并「工作声明」，执行器按 `job_id + 运行租户` 重读 DB 验证 job/run/shop/resource，签发**不可由请求反序列化**的按页能力（tenant/job/run/shop/resource/mapping_version/允许方法/授权代次）。
   - 人类 `scope.From` 语义不变，缺身份仍拒绝；Work 走独立适配器与严格谓词，不复用 `shopStore.query`。
   - 手动/重试：HTTP 入队前校验 `RequirePerm` + shop 范围并持久化 `triggered_by`；worker 每页重载发起人权限，撤权即停。
   - cron：以「有管理权限的人启用 job」作为授权；停用、店铺删除/移交立即撤销，批准人离职不自动撤销。
   - 凭据：新增 shop 公共使用端口，worker 只能拿到中立 DTO；解密记 `actor_type=system`、`detail` 含 worker/job/run，审计失败不调平台。
7. **D1 = B · 独立 raw 去重目录**。新建非分区目录表，对去重六列建唯一键，与 raw 插入同事务，返回既有 RawRef。保留七列分区唯一键做批次级兜底。去重期限 = 在线 + 可重放归档期；hash 口径固定在**语义规范化后的 JSON**，用 fixture 锁定「仅空白变化」行为。
8. **D2 = 只建 listing/listing_sku**；M3 交付「失败记录重试 + 隔离重放」，预建 `replay_run` 表但**不实现任意历史范围重放**（M4）。不再提前实现 SPU/SKU 归并。
9. **D3 = 不做按需自动刷新**。凭据过期 → 暂停 job 并要求重新授权；`Connector.Refresh` 保留但返回 Unsupported，**不得**伪装成功。自动刷新在 M7。
10. **D4 = 保留 `TargetUpserter` 签名**，GORM 只在 bootstrap 适配器内持有；模块不跨 import repo/model。
11. **D5 = 60 秒是任务预算**，到点持久化已完成页并续跑，未完成页不推进；outbox 超限终止并告警（不无限重投），processing 有租约回收；单店所有资源**共享**令牌桶与下次允许时间。
12. **D6 = 未知字段只走显式 `ext` 映射**；JSONB 只保证语义完整（不保证字节保真、重复键）。未知 listing 状态 → 隔离（`invalid_value`），不得当 online/offline；重放不删除 SKU。
13. **D7 = 排期与拆分**：M3 拆为 **M3a（数据管道：迁移/分区/去重/映射引擎/listing 落库/mock 平台）** 与 **M3b（编排与运行：页语义/游标/死信/worker 身份/drift/Shopee/outbox）**，各 10–13 人日，独立验收、独立 tag。归档演练另计 2–4 人日。

**理由**：M3 同时引入「异构数据解析」「分区表」「后台任务身份」三类新范式，任一处理错都会造成静默漏数或越权。把映射与数据管道（M3a）先做扎实，再接运行编排（M3b），每次只引入一类风险。

**代价**：
- M3a 没有真实 worker，验证靠直接调用引擎 + mock 平台，集成度低于最终形态。
- `listing.ext` 承载来源排序等引擎元数据属于过渡方案，M4 可能要求类型化列。
- 归档在整月边界执行，在线保留期不是精确 180 天。

**被否决的方案**：通用嵌套 DSL（超期）；DEFAULT 分区兜底（把告警变成静默堆积）；整次重放持锁（同步饿死数小时）；给 worker 一个 all 身份（等于取消数据隔离）；同批去重（不满足 PRD「重复抓取不增行」）。

## ADR-017 · M4 的归并、重放、类目、库存与导出

**状态**：已接受（2026-11-04，人裁决；输入 `docs/proposals/M4-review.md`）

**决策**：

1. **Q1 = A · 只做人工归并**。后台选择 listing 建 SPU 或挂到已有 SPU；商家编码只做**影子候选**（不写入），标题+品牌只做建议。自动挂接需要先有分层标注样本与误判率上界，另批。
   - 误归并的度量：受影响 listing/SKU 数 × 下游权重（价格展示、库存差额、报价引用），不是「错了几条」。
2. **Q2 = A · 重放小批共锁、同步优先**。每批 ≤200 条，按 `(fetched_at, id)` keyset 读；批内完成映射、upsert、统计、检查点后释放锁；有待跑同步时先让出。范围与 mapping version 在建 run 时冻结。
   - **来源新旧与映射新旧分开**：同一 raw 且 checksum 改变 → 允许重解释；来源早于 `listing.ext._ingestion.source_order` 的 raw → 整组跳过（父与全部 SKU 一起）。
   - `listing_sku` 不加子级 `_ingestion` 元数据；父行仲裁通过后，父与完整子集合在同一事务更新。
3. **Q3 = A · 类目每日完整同步 + 人工优先**。`manual` 映射永远覆盖规则；唯一同路径同名可自动（0.9 仅作候选分，需抽样验证后开放自动应用）；父级继承（0.6）只进候选池。
   - 平台类目消失：保留旧行，用 `synced_at` 标记陈旧，**不自动删除、不自动重绑**；不完整周期不用于推断删除。
4. **Q4 = A · 每次成功同步写库存快照**，保留 30 天；不做降采样。SPU 汇总口径明确为「所关联 listing SKU 报告库存之和」，**会重复计算**（同物多店刊登），且 `available` 与 `reserved` 不相加冒充可售。
   - 容量：10 万 SKU × 每日 1 次 × 30 天 ≈ 300 万行；每日 4 次 ≈ 1200 万行。上线前用 `pg_total_relation_size` 核实，不按字段宽度估算。
5. **Q5 = A · 批准新增冗余列**：`product_spu` 增加 `price_min_cents`、`price_max_cents`、`sku_count`、`version`。
   - 口径：价格取**活跃 listing_sku 的平台价**范围；`sku_count` 取 distinct 已绑定 `product_sku` 数；未绑定 listing SKU 不计入。
   - 维护：唯一写入口在 catalog service，同事务重算受影响 SPU；禁止触发器与异步方案。
   - 深分页：`page ≤ 100` 保持 offset；更深走 `(updated_at, id)` keyset cursor，token 绑定 tenant/过滤条件/排序/版本，禁止把任意 SQL 值塞进 token。
6. **Q6 = A · 独立导出任务表** `export_job`（新迁移）：创建时快照 filters/sort/字段版本/租户/请求人；worker 每批 1000 行 keyset 流式写对象存储；对象键 `exports/{tenant}/{export_id}.csv` 由服务端生成。
   - 对象保留 24h，下载签名 URL 1h，两者语义不同；失败任务的临时对象立即清理。
   - `file_object` 只登记完成文件，不承载进度与状态。
7. **分批交付**：M4 拆为 **M4a（商品主数据：迁移、类目、人工归并、库存、列表与游标）** 与 **M4b（历史重放执行器 + 异步导出）**，各 9–13 人日，独立验收与 tag。

**理由**：M4 的两个高风险都来自「批量写历史数据」——自动归并会串价，历史重放会覆盖新数据。先把单条路径（人工归并、单次同步）做对，再开批量通道。

**代价**：
- 人工归并需要运营投入，未归并的 listing 不参与 SPU 级属性。
- 库存快照 30 天可能到千万行，需要容量监控。
- 新增 4 个 SPU 列与 1 张导出表，迁移数为 2（000007/000008）。

**被否决的方案**：自动编码挂接（编码可空/可复用，误判仍串价）；长持锁重放（同步饿死）；小时级库存降采样（丢失趋势语义）；同步 HTTP 导出（超时不可重试）；触发器维护冗余列（隐藏业务逻辑，锁顺序难诊断）。

## ADR-018 · M4b 的重放执行器与导出

**状态**：已接受（2026-11-04，人裁决；输入 `docs/proposals/M4b-review.md`）

**决策**：

1. **Q1 = A-B · 有界同步优先 + 持久 grant**。同一锁域最多一个活动 replay；sync 通常先获 grant，但 replay ready 期间最多允许 **4 个 sync 执行片段**越过，第 5 次必须给 replay。计数、owner、代次、截止时间在 job 调度行锁下原子决定，进程重启不清零。
   - 健康未暂停时的等待上界：4×60s + 5×5s = **265 秒**；sync 被 replay 额外阻塞 ≤ 7 秒（2s 持锁 + 5s 交接）。
   - 提交授权以 **DB 代次 fence** 为准，Redis 只做跨进程互斥；失租的旧 worker 不得在新代次提交后再写。
   - 高延迟保护可暂停 replay，但必须持久记录原因与起止；暂停期间不适用 265 秒上界。
2. **Q2 = B-B · 持久成员清单 + 在线 pin**。建 run 时在同一 MVCC 视图物化成员（`replay_run_item`，含完整 RawRef `(fetched_at,id)`），精确 total、上界、mapping version/checksum/函数集版本一并冻结；HTTP 201 只在该冻结成功后返回。
   - 每批 ≤200，与目标 upsert、库存快照、SPU 重算、死信、stats、checkpoint **同一事务**；检查点不动 `sync_cursor`。
   - 计数守恒：`processed = inserted+updated+skipped_stale+skipped_same+quarantined+failed`，`processed ≤ total`。
   - **首版只支持在线 raw**；已归档范围明确拒绝（60601），运行中 raw 不可读则停在原检查点并告警，不按空页成功。
   - 50 万成员冻结必须在既有 3 秒 DB 预算内通过压测，否则创建回滚、另议预算。
3. **Q3 = C-B · 保留 raw ID 来源主序 + 完整身份校验**。来源序 `source_order = raw.id`；完整 RawRef（id + fetched_at）与目录、external_id 匹配才算同一来源；checksum 只决定是否重解释，不决定新旧。
   - 缺保留区、时间非法、ID 与 order 矛盾、目录多义 → **零目标修改**，进隔离（`source_metadata_unknown` / `source_identity_ambiguous`），不按「较晚时间」放行。
   - 明确边界：只保证「已接受的来源序不倒退」，不保证上游真实最新观测；A→B→A 的最新性另卡解决。
4. **Q4 = 冻结后新 raw 不追加入旧 run**。冻结后到达的 raw 由正常同步处理或另建 run；active mapping 切换不影响既有 run。
   - 交错场景终态：R0 重放与 R1…R5 同步交错后，目标保持 **R5 + 同步映射**；同 raw 换 checksum 才重解释。
   - before/after 摘要只作观测，**不是重放因果统计**（期间同步也在写）。
   - 冻结租户不冻结权限：每批重验请求人权限与授权代次，撤权即停。
5. **Q5 = D-B · worker 时刻内容物化**。创建时冻结 filters/sort/字段版本/tenant/owner；worker 开始时在 ≤3 秒事务内把完整投影值、排序键、稳定序号写入 `export_job_row`，之后每批 ≤1000 按 `(export_id, attempt, ordinal)` 流式上传。
   - 并发上限：全局 2、每租户 1、每请求人 1；pending 每租户 10，超出 429/10005；执行硬预算 5 分钟，10 万行目标 <180 秒。
   - 对象保留 24h，下载 URL `min(1h, 剩余寿命)`；发布走版本保护，旧 attempt 的迟到上传不得覆盖新成果；失败清理进 outbox 重试。
   - CSV 字段白名单，禁止导出 `_ingestion` 与 raw 原文；文本单元格做公式注入转义。
6. **Q6 = 接受评审阈值作为发布门禁**：replay ready 等待 240/265 秒、最后提交年龄 300/900 秒、批次持锁 >2 秒、sync ready 等待 60/120 秒、sync 被阻塞 10/30 秒、完整周期新鲜度 20/30 分钟、导出执行 180/300 秒、清理待办 300/900 秒。混合负载与假时钟故障注入验证后才算通过。
7. **分批与迁移**：M4b 拆为 **M4b1（重放执行器）** 与 **M4b2（异步导出）**。迁移 `000008` 归 M4b1（replay 成员与调度结构），`000009` 归 M4b2（export 暂存）；**M5 及以后顺延**，且从此以后任务卡里的迁移编号视为「落地时当前最大号 +1」的建议值，不再是固定分配。
8. **存储发布协议（2026-11-05 追加）**：引入 S3 兼容 SDK `github.com/minio/minio-go/v7`（锁定 **v7.0.83**，兼容 Go 1.23；禁止 `@latest`，它会把 go 指令升到 1.26）。**不启用桶版本管理**。
   - 对象键按 attempt **不可变**：`exports/{tenant}/{export_id}/attempt-{n}.csv`。迟到的旧 attempt 只能写自己的键，永远不会被引用。
   - **发布 = 一次 DB 条件更新**：`UPDATE export_job SET object_key=?, attempt=?, status='succeeded' WHERE id=? AND attempt=? AND status='running'`；影响行数 0 即放弃本次发布。DB 指针是唯一发布事实。
   - **禁止**「检查存在 → GET → PUT」这类先读后写，也**不依赖**存储层 CAS 或对象版本。
   - 下载用 SDK 预签名，URL 有效期 `min(1h, 对象剩余寿命)`；下载前校验 tenant 与 owner。
   - 旧 attempt 与失败暂存对象由清理任务删除（按记录 + 前缀扫描），失败进 outbox 重试。
   - 若将来确需桶版本管理，另开 ADR，不影响本协议。

**理由**：M4b 是第一个「长任务改写历史数据」的功能，三个保证都必须有持久载体——成员清单（防漏）、DB 代次（防旧写）、内容物化（防混时点）。任何一条用内存或近似实现，都会在故障时静默出错。

**代价**：
- 新增两张表与调度列，M4b 工期由 9–13 上调至 **14–20 人日**（拆两批后各 7–10）。
- 公平调度要求 sync 与 replay 共享持久调度状态，两个模块都要改。
- 首版不支持归档范围重放，50 万条以上需另议。

**被否决的方案**：严格同步绝对优先（无限积压下 replay 永远跑不完）；只存上下界（无法排除晚提交成员）；缺元数据时默认新（会把旧价格写回）；导出按批实时读（混时点，无法复现）。
