# PROMPTS · 与 Codex 协作的提示词模板

> 用法：复制对应模板，替换 `<...>` 占位符。**不要**在提示词里重复文档内容，只给路径和范围。
> 核心原则：Codex 的上下文越聚焦，产出越稳。**一次只给一个任务卡。**

---

## 模板 1 · Gate A 设计评审（里程碑开始前）

> 目的：让 Codex 在写代码前把风险、歧义、冲突暴露出来，由人裁决。
> 关键：**明确禁止改代码**，否则它会「顺手实现」。

```
你是本项目的实现工程师。现在处于里程碑 <Mx> 的【设计评审】阶段。

请只做评审，不要写任何代码，不要修改任何文件——除了新建 docs/proposals/Mx-review.md。

必读：
- AGENTS.md
- docs/01-PRD.md 中 <本次涉及的需求 ID 列表>
- docs/02-architecture.md
- docs/03-data-model.md 中 <涉及的表>
- docs/ADR.md
- docs/milestones/Mx.md
- 如涉及现有代码：<列出需要看的目录/文件>

请输出 docs/proposals/Mx-review.md，严格包含以下五节：

1. 规格冲突与歧义
   逐条列出任务卡 / PRD / 架构 / 数据模型之间不一致或说不清的地方。
   每条给出：位置（文件+章节）、问题、两种可能的理解、你建议哪种。

2. 实现风险（按严重度排序）
   只列可能导致返工或线上事故的风险，例如：并发、幂等、事务边界、N+1、索引缺失、
   上游限流、数据一致性、迁移锁表。每条给出：触发条件、影响、建议的规避方式。

3. 方案对比
   对本里程碑中 2–4 个真正的设计分叉点，各给 2–3 个方案：
   方案名 / 做法 / 优点 / 缺点 / 对现有表与接口的影响 / 工作量(人日) / 推荐哪个。
   不要为了凑数制造分叉点；没有分叉就写「本里程碑无重大分叉」。

4. 未来 2 个里程碑的坑（只列不展开）
   用一句话一条，标注会在哪个里程碑爆发。

5. 待决策清单
   编号 Q1..Qn，每条一句话，便于逐条回复「同意/选 B/再议」。

约束：
- 不要写实现代码、不要给伪代码超过 10 行。
- 不要修改 docs/ 下任何已有文件。
- 不要提出「重写架构」类建议，除非有具体的线上事故场景支撑。
```

**人怎么用这份产出**：逐条回答 Q1..Qn → 把结论追加到 `docs/ADR.md` 或任务卡 → 再进入模板 2。

## 模板 2 · 实现单张任务卡（最常用）

```
实现 docs/milestones/<Mx>.md 中的【任务 <x.y>】。只做这一张卡。

必读（按顺序）：
1. AGENTS.md
2. docs/04-conventions.md
3. docs/milestones/<Mx>.md 的【任务 <x.y>】小节
4. 该小节「必读文件」列出的文件
5. <如涉及表：docs/03-data-model.md 的 <table> 节>

范围：
- 允许修改：<明确列出目录/文件>
- 禁止修改：<明确列出，例如 migrations 下的既有文件、其他模块>

要求：
- 遵循 docs/04-conventions.md 的分层与命名。
- 每个新增行为都要有测试；P0 需求的用例注释里写 REQ ID。
- 不要引入新依赖。
- 不要留 TODO 或空实现。
- 完成后按 AGENTS.md §4 输出自检，按 §10 输出交付回复，必须含「偏差说明」。

如果遇到以下情况，立刻停下并按 AGENTS.md §5.2 提问，不要自行决定：
- 需要改表结构 / 改接口契约 / 加依赖
- 任务卡与现有代码矛盾
- 需求有两种合理解释且实现不同
```

## 模板 3 · 修复 / 返工

```
上一个 PR 有 <n> 个问题，请只修这些，不要顺手改别的。

问题清单：
1. <文件:行> <问题> <期望行为>
2. ...

约束：
- 不改动问题清单之外的代码。
- 不删除、不放宽现有测试。
- 修完后重跑 make lint test，贴输出。
- 如果某个问题你认为是需求本身的问题，停下来提问，不要擅自改需求。
```

## 模板 4 · 定向评审（实现中遇到硬问题）

```
实现 <任务 x.y> 时遇到一个必须现在决定的设计问题，请只做分析，不要改代码。

问题：<一句话>

现状：
- 相关表：<table>
- 相关代码：<file:line>
- 当前做法：<...>
- 触发条件：<...>

请给出：
1. 这个问题的本质是什么（不超过 5 行）
2. 3 个方案：做法 / 优点 / 缺点 / 对已有数据的影响 / 迁移成本
3. 你推荐哪个，为什么
4. 如果选你推荐的，需要改哪些文件、要不要写数据迁移

不要展开到其他模块，不要提「顺便重构」。
```

## 模板 5 · 里程碑验收（Gate C）

```
请对照 docs/milestones/<Mx>.md 的【验收清单】逐条自检，不要改代码。

对每一条输出：
| # | 验收项 | 状态(通过/不通过/无法验证) | 证据（命令 + 输出摘要 或 文件:行） |

另外检查：
1. 该里程碑所有 P0 需求是否都有对应测试（列 REQ ID → 测试名）
2. 是否有 TODO / 空实现 / 调试代码残留
3. 迁移是否可 up/down
4. 新增接口是否与任务卡接口表一致（逐条比对）
5. 是否有与 docs/ 规格不一致但未在「偏差说明」中声明的改动

最后给出：可以进入下一里程碑 / 需要先修 <列表>。
```

## 模板 6 · 生成某个平台的适配器（M3 之后复用）

```
为 <platform> 实现 connector.Platform。

必读：
- docs/05-platform-sync.md（接口与错误归一）
- internal/modules/connector/types.go
- internal/modules/connector/platforms/<参考平台>/（照抄结构）

要求：
- 只实现接口，不做字段解释（解释交给 mapping spec）。
- 所有 platform 特有错误映射到 ErrKind（auth_expired / rate_limited / ...）。
- 分页、限流、重试遵循 docs/05-platform-sync.md §3。
- 提供 testdata/ 下的真实响应样例（脱敏），并写 httptest 单测覆盖：
  正常分页 / 401 过期 / 429 限流 / 字段缺失。
- 在 connectors 注册表登记，并在 docs/05 的能力矩阵表补一行。

不要修改 sync / ingestion 模块。
```

## 模板 7 · 写迁移与数据回填

```
新增迁移：<描述>。

要求：
- 文件名 migrations/0000NN_<name>.up.sql / .down.sql
- 只新增，不修改既有迁移
- up 必须幂等（create table if not exists / add column if not exists）
- down 必须能回滚（drop 新增对象）；若不可逆，文件头写 `-- irreversible: <原因>` 并让 down 为 no-op
- 大表加索引用 create index concurrently，且单独一个迁移文件
- 如需回填数据，单独一个迁移，分批（每批 ≤ 5000 行），可重复执行
- 同步更新 docs/03-data-model.md 对应表（这是唯一允许改数据模型文档的场景）

完成后贴：up/down 各执行一次的输出。
```

## 附：提示词反模式（不要这么写）

| ❌ 反模式 | 为什么不行 | ✅ 改成 |
|---|---|---|
| 「帮我实现一个电商中后台」 | 范围无限，必然发散 | 一次一张任务卡 |
| 「参考最佳实践设计数据库」 | 它会自创一套，和你的文档冲突 | 指向 `docs/03-data-model.md` 具体表 |
| 「顺便优化一下代码结构」 | 引入未评审的重构 | 单开 proposal |
| 「测试跑不过就调整一下」 | 会改断言而不是改实现 | 明确指出是实现错还是用例错 |
| 「你看着办」 | 决策权转移，偏离需求 | 给选项 + 让它推荐，人来定 |
| 把整个 PRD 贴进对话 | 上下文稀释，重点丢失 | 给文件路径 + 章节 + 需求 ID |
