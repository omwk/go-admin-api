### T0.2 配置

`internal/kernel/config`：

```go
type Config struct { App App; DB DB; Redis Redis; Crypto Crypto; JWT JWT; Storage Storage; Worker Worker; Log Log }
func Load(path string) (*Config, error)   // viper: default < file < env(CH_)
func (c *Config) Validate() error         // 必填项、密钥长度、DSN 可解析
```

- 环境变量映射：`CH_DB_DSN` → `db.dsn`，`CH_CRYPTO_MASTER_KEY` → `crypto.master_key`。
- `Validate` 必须检查：`db.dsn` 非空、`crypto.master_key` base64 解码后 32 字节、`jwt.secret` 生产环境非空且 ≥ 32 字符。
- `main` 里 `Load` 失败或 `Validate` 失败：打印明确字段名并 `os.Exit(1)`。

**验收**：单测覆盖「缺必填项返回错误且错误信息含字段名」「环境变量覆盖文件值」。

### T0.3 日志与 trace

`internal/kernel/logger`：

- 基于 `log/slog`，JSON handler，支持 `level`、`format=json|text`。
- `httpx.TraceID()` 中间件：从 `X-Request-Id` 取，没有则生成 ULID，写入 `context` 与响应头。
- `logger.From(ctx)` 自动带 `trace_id`。
- 固定字段：`ts level msg trace_id module action duration_ms error_code`。

**验收**：请求后日志含 trace_id；响应头含 `X-Request-Id`。

### T0.4 错误与响应

`internal/kernel/errs`：

```go
type AppError struct { Code int; HTTPStatus int; Message string; Details map[string]any; Cause error }
func New(code int, httpStatus int, msg string) *AppError
func (e *AppError) Error() string
func (e *AppError) Unwrap() error
func From(err error) *AppError        // 非 AppError 统一转 10002，Cause 保留
func Invalid(err error) *AppError     // 10001
```

- 错误码常量按 `docs/04-conventions.md` §3 定义，**先只定义 10xxx 段**。
- `httpx.OK(c, data)` / `httpx.Created` / `httpx.NoContent` / `httpx.Fail(c, err)`。
- 响应结构严格按 `docs/04-conventions.md` §2.2。

**验收**：单测断言成功/失败响应 JSON 结构与 HTTP 状态码；`From` 不泄露 `Cause` 内容到 `message`。

### T0.5 数据库

`internal/kernel/db`：

- GORM 初始化，连接池参数来自配置，`PrepareStmt` 开启。
- `Transaction(ctx, fn)` 助手：嵌套调用复用外层事务（用 context 传 tx）。
- 健康检查：`PingContext` 带 2s 超时。
- 迁移：`cmd/cli` 提供 `migrate up|down|version`，用 `golang-migrate` + `embed.FS`，启动时加 PG advisory lock 防并发。
- 写 `000001_kernel_init.up.sql` / `.down.sql`。

**验收**：`make migrate-up` 建出 7 张表；`make migrate-down` 能全部删除；重复 `up` 不报错。

### T0.6 Redis

`internal/kernel/cache`：

- `go-redis/v9` 客户端，连接池参数来自配置。
- `Lock`：`SET key val NX PX ttl` + Lua 安全释放（比对 val）。
- `TokenBucket`：Lua 脚本实现（tokens/last_refill/rate/burst），返回 `(allowed, remaining, retryAfter)`。
- 健康检查 `Ping`。

**验收**：单测用 `miniredis`（加入允许依赖 `github.com/alicebob/miniredis/v2`）覆盖：加锁互斥、释放、令牌桶速率。

### T0.7 HTTP 服务

`internal/kernel/httpx`：

- Gin engine：`Recovery`（自定义，返回统一错误）、`TraceID`、`AccessLog`、`CORS`、`Timeout(30s)`、`BodyLimit(1MB)`。
- 路由注册分函数：`RegisterSystemRoutes(r *gin.Engine, deps)`。
- `/healthz` 永远 200；`/readyz` 检查 DB + Redis，任一失败 503 并返回哪个依赖挂了。
- `/metrics` 用 promhttp；注册 `http_requests_total`、`http_request_duration_seconds` 两个基础指标。

**验收**：`curl` 三个端点符合预期；停掉 Redis 后 `/readyz` 返回 503 且 body 指明 redis。

## 8. 关键实现要点（容易踩坑的地方）

1. **`/readyz` 不要每次全量 ping 所有依赖**，加 1 秒缓存，避免探针打爆 DB。
2. **trace_id 必须在 Recovery 之前生成**，否则 panic 日志没有 trace。
3. **GORM 的 `PrepareStmt` 与事务助手**：事务内必须用 `tx.WithContext(ctx)`，否则嵌套查询走主连接，事务失效。
4. **迁移的 `down` 顺序**：先删有外键的子表，再删父表。原全面不建外键的约定已由 ADR-011 取代：配置类小表及其关联表建物理外键，业务大表不建；不追改 M0 已合并迁移。
5. **配置里的密钥不要打日志**：`Config.String()` 要脱敏，或干脆不实现 `String()`。
6. **docker-compose 的健康检查**：pg 用 `pg_isready`，redis 用 `redis-cli ping`，api 依赖 `condition: service_healthy`。

## 9. 验收清单

```bash
# 1. 静态检查与测试
make lint && make test

# 2. 迁移
make migrate-up
make migrate-down
make migrate-up

# 3. 启动
docker compose -f deploy/docker-compose.yml up -d

# 4. 配置校验

# 5. 故障演练
docker stop <redis容器> && curl -s localhost:8080/readyz | jq -e '.status=="degraded"'
```

## 10. Gate A 评审关注点

- 目录结构是否足以承载 11 个模块，有没有需要提前拆的
- 事务助手的设计能否支持「跨模块同事务」（M3 的 raw + 映射 + outbox）
- 统一错误码是否与 HTTP 状态码职责重叠（避免出现两套语义）
- 日志脱敏策略是否可复用（M2 会传凭据）
