# M9c · 持久准入优化与容量校准

测量日期 2026-11-10。结论：本机样本达到 ADR-023 的暂定目标；现金/权益的并发 1 open p99 分别为 **45.878 / 41.153ms**，配对额外开销 p99 为 **42.555 / 39.800ms**；固定 50 QPS 的实际端到端 p99 为 **54.198 / 53.793ms**。这不是生产持续容量承诺。

原始证据：[优化前 JSON](M9c-performance-before.json)、[优化后 JSON](M9c-performance-after.json)。入口同为 `scripts/gateway/benchmark.ps1 -Billing`，样本数和负载模型相同；before 使用 M9b 产品路径，after 使用已批准的 A。没有用 M8c 免费调用冒充收费基线。

## 从 M8c 的 58ms 定位到本批优化

M8c 单并发配对额外 p99=58.560ms；独立阶段中，认证主库/nonce/Touch p99=16.773ms，准入与终结计量 DB p99=24.062ms，HMAC 批均值 p99=0.002535ms，nonce 和限流 Redis 分别为 0.662/1.038ms。独立阶段的分位数不能相加还原请求 p99。

代码对应的主要往返是：调用意图和 processing 日志、日/月配额的建行/锁行/更新、Start/Finish 持久事务，以及请求前后主库应用/key 使用状态写。M9a/b 又加入 charge、冻结和权益事实。M9c 收费基线进一步验证：钱包认证阶段 p99=12.676ms，准入/终结 DB p99=57.066ms；权益对应为 12.821/53.371ms。主要耗时仍在持久数据库路径。

已实现的 A：

- `000021_gateway_admission_batch` 新增 SECURITY INVOKER 函数；调用意图、processing 日志、charge、日/月 PG 配额及钱包冻结/权益预留在同事务、一次应用层 SQL 往返中执行。`TestBillingGatewayIntegrationAdmissionRoundTrips` 对现金/免费权益/付费权益均精确断言 1 次 SQL。BEGIN/COMMIT 不计为这 1 次业务 SQL。
- 原有 api_call、api_call_log、两条 api_quota、call_charge、wallet_txn/unit_txn 和余额/预留事实均保留；失败整体回滚。Finish 的调用结果、终态日志、结算流水及唯一 meter 保持原事务，没有减少持久事实写入。配额最终依据始终是 PG。
- 应用/路由/密钥缓存按版本及安全状态识别，TTL=5 秒；管理撤销主动清空本实例缓存，每次缓存命中仍读主库安全版本/状态，跨实例即时撤销和依赖故障拒绝有回归。密钥缓存只保存密文并复制可变字段。没有引入 Redis 配额裁决。
- 前后 `Touch` 的应用/key 核验及使用时间更新合并为一个 CTE 往返，两个状态写仍持久化。对账读取批量化属于次要优化，本批保持原有有界分页，未扩大范围。

## 同口径运行方法

```powershell
$env:GOCACHE = Join-Path $env:TEMP 'm9c-go-build'
$env:GOLANGCI_LINT_CACHE = Join-Path $env:TEMP 'm9c-lint-cache'
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/gateway/benchmark.ps1 -Billing -RedisAddr 127.0.0.1:16379 -Samples 1000 -Concurrency '1' -Output docs/milestones/M9c-performance-after.json
```

before 运行同一脚本、同一参数，输出改为 `M9c-performance-before.json`，产品代码为优化前版本。数据库配置只从被忽略的 `.env`/环境读取；报告不含 DSN、凭据。真实 PG/Redis，独占测试数据库/schema 与 Redis DB，结束清理。Windows/amd64、Go 1.25.4，PG 最大连接 10，Redis 池 32；没有修改生产池、限额或依赖。

每个场景单应用、单热钱包或单权益、同一订单路由，单价 5 分/1 单位；测量专用限流桶设高，持久配额仍记录。闭环并发 1：direct/open 各 1000 请求、各预热 20 次，配对 500 对且交替次序，额外开销取每对 open−direct 的分布。两入口均 loopback HTTP，闭环业务读使用同一预取的真实状态快照以隔离网关开销。Windows direct p50=0 表示低于时钟分辨率。

固定到达阶段另使用真实订单领域读，1000 请求、20ms 间隔（目标 50 QPS），独立调度，记录派发延迟和从计划时刻计算的延迟，避免闭环掩盖排队。最近秩分位数；阶段测量各 100 次，HMAC 为批均值。错误不从样本中隐藏；任一失败使容量命令失败。普通 CI 不执行容量：必须同时开启 `gatewaybench` tag 和 `CH_GATEWAY_BENCHMARK=1`。

实际完成速率：现金 49.844→49.941 QPS，权益 49.820→49.950 QPS；四组 errors=0。吞吐包含最后请求收尾，因此略低于 50。单场景每次共核对 2620 个成功调用、日志、meter、settled charge 和配额计数；现金扣款 13100 分/零单位，权益零现金/2620 单位，冻结归零。

阶段 p99：现金认证 12.676→6.259ms，准入/终结 DB 57.066→27.056ms；权益为 12.821→6.417ms、53.371→24.879ms。后测 nonce/限流 Redis 仍为毫秒附近，HMAC 为微秒批均值。

## 目标、限制与后续

| ADR-023 暂定目标 | 本次最坏值 | 判定 |
|---|---:|---|
| 并发 1 配对额外 p99 ≤85ms | 42.555ms | 达到 |
| 并发 1 open p99 ≤100ms | 45.878ms | 达到，未触发停止条件 |
| 固定 50 QPS p99 ≤150ms | 54.198ms（计划时刻口径 54.521ms） | 达到 |

这些是单机短样本校准。50 QPS 每场景仅约 20 秒，未覆盖 30 分钟稳定段、72 小时长跑、多实例/多钱包矩阵、对账并跑、生产 Linux/磁盘/WAL/备份和长期体量。未采集 PG 锁等待、SQL 子阶段和连接池等待 trace，不能宣称已经精确分摊各项开销或测得最大持续 QPS。保留 PG 配额/热钱包行的串行区；需要更高容量时先补上述观测及生产环境复测，再由人裁决后续 ADR。未实施 B。
