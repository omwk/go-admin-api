# M8c · 网关额外开销压测

- 测量日期：2026-11-10（原始 UTC 时间见 JSON）；基线 `5a9bbaf`，分支 `feat/M8c-gateway-hardening`。
- 目标：不含业务查询的网关额外开销 p99 < 20ms。
- **结论：未达标。** 单并发配对额外开销 p50/p95/p99 = **40.961 / 52.757 / 58.560ms**；本轮最高观测吞吐 **123.47 QPS**（并发 32，零错误）。这不是生产容量承诺。
- [原始测量 JSON](M8c-performance.json)；测量入口为 `scripts/gateway/benchmark.ps1` 和 `internal/bootstrap/gateway_benchmark*_test.go`。

## 运行方式与隔离

```powershell
$env:GOCACHE = Join-Path $env:TEMP 'm8c-go-build'
$env:GOLANGCI_LINT_CACHE = Join-Path $env:TEMP 'm8c-lint-cache'
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/gateway/benchmark.ps1 -RedisAddr 127.0.0.1:16379 -Samples 2000 -Concurrency '1,4,16,32' -Output docs/milestones/M8c-performance.json
```

数据库连接从 `TEST_DATABASE_URL` 或被忽略的根 `.env` 读取，不放入命令或报告。脚本复用 S3 的 schema/Redis 独占与清理机制；测试数据另由现有测试框架的隔离 schema 管理。测量使用真实 PostgreSQL 和真实 Redis，默认开发 Redis DB 被排除。结束输出 `remaining_schemas=0; remaining_redis_keys=0`。没有改动产品限额、连接池默认值、数据模型或第三方依赖。

容量测试同时要求 `gatewaybench` build tag 和 `CH_GATEWAY_BENCHMARK=1`；脚本显式传入样本数、并发及输出路径。普通 `go test ./...` / PR CI 不编译该测试，不执行容量阈值或统计断言。开启后的测试检查响应成功和测量文件有效性，**不会把 p99 超目标伪装为达标，也不会用耗时断言干扰 PR CI**。

## 测量口径

环境为 Windows/amd64、Go 1.25.4、16 个逻辑 CPU，PG 最大连接 10，Redis 池 32。网关使用单个应用、单条路由、单个订单，日/月额度为不限；测试专用 QPS/burst 设为 100000，以测持久化路径的容量。该设置只存在于 opt-in harness，未覆盖生产配置。

对照是进程内专用 HTTP 内部入口，直接调用领域读端口；实验入口是生产 `gateway.OpenHandler`，包含 HMAC/主库状态、真实 nonce Redis、路由双门禁与授权、Lua 分层限流、准入/配额、结果/日志/计量持久化及返回前主库复核。两者均通过真实 loopback HTTP、连接复用、有界超时读取完整 JSON 响应。

为排除业务 SQL，先用真实 `NewGatewayOrderReader` 取得已授权订单状态快照，再将同一只读快照端口注入两个入口。领域订单/资源与 owner 范围查询在计时外；没有在生产路径增加绕过端口。内部对照不运行管理 JWT/RBAC；结果只回答额外网关开销，不代表管理接口或完整订单查询的端到端延迟。客户端生成 nonce/签名在每次 HTTP 计时前；吞吐的总时段包含请求构造和调度。

每档先预热两入口各 20 次，再分别采样 2000 次；固定并发闭环发压，无额外 think time。延迟从发送 HTTP 到读完 body/关闭响应，分位数用 nearest rank。另取 500 对请求、交替先后顺序，在相同并发下计算每对 `open - direct` 的分布；**没有将两个无关 p99 相减**。QPS 为该档成功样本数 / 整档墙钟时间。任一 HTTP/code 错误都会计入 errors 并使容量命令失败，不能从百分位中静默隐藏。

## HTTP 结果

时间单位为 ms，QPS 为次/秒；每行 direct/open 各 2000 次，配对额外开销 500 对，errors 均为 0。

| 并发 | 内部直连 p50 / p95 / p99 | open p50 / p95 / p99 | 配对额外开销 p50 / p95 / p99 | 直连 QPS | open QPS |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.000 / 0.528 / 1.001 | 40.499 / 51.719 / 72.351 | 40.961 / 52.757 / **58.560** | 8918.91 | 23.65 |
| 4 | 0.000 / 0.532 / 0.586 | 45.349 / 65.614 / 100.283 | 46.527 / 62.034 / **75.488** | 30635.94 | 81.86 |
| 16 | 0.000 / 1.006 / 2.212 | 135.998 / 192.460 / 218.531 | 122.446 / 160.540 / **179.831** | 56787.53 | 114.10 |
| 32 | 0.000 / 1.304 / 4.299 | 250.299 / 363.655 / 419.447 | 240.809 / 339.099 / **389.135** | 65262.44 | **123.47** |

本轮 QPS 观测上限为 123.47；并发从 16 加倍到 32，吞吐只增加约 8.2%，open p99 从 218.53ms 增至 419.45ms，已出现明显排队。固定应用的配额行和 last_used_at 行是共享写热点，此数字不能外推多应用总容量，也没有证明更高并发下的绝对上限。它是本机、当前连接池、当前样本区间的容量边界。Windows 的短时钟测量出现直连 p50=0，表示低于可分辨时间片，不表示 HTTP 没有成本。

## 瓶颈定位

以下各阶段独立顺序采样 500 次，未与 HTTP 发压并行，不能相加还原 HTTP p99。认证阶段包含应用/secret 查询、nonce 和主库 Touch 事务；计量阶段是实际 `CallService.Run` 的准入与终结事务，业务端口仍为相同快照。HMAC 为每样本批量执行 1000 次后求每次均值，用于避免 Windows 短计时归零；它的 p99 是**批均值分布的 p99**，不是单次 HMAC 尾延迟保证。

| 阶段 | p50 | p95 | p99 | 判断 |
|---|---:|---:|---:|---|
| HMAC-SHA256（每次批均值） | 0.001030 | 0.002008 | 0.002535 | 微秒级，对本轮毫秒级延迟贡献很小 |
| nonce Redis SETNX | 0.519 | 0.530 | 0.662 | 未见其支配请求耗时 |
| 四桶 Lua 限流 Redis | 0.521 | 0.594 | 1.038 | 明显小于持久化阶段 |
| 认证主库 + nonce + Touch | 7.897 | 9.849 | 16.773 | 主库读取与使用状态事务带来额外往返 |
| 计量 DB：准入 + 终结 | **19.783** | **21.951** | **24.062** | 单独此阶段 p99 已超过 20ms |

定位证据是阶段实测与代码路径一致：

1. `gateway.CallService.Start` 在一个事务中插入 `api_call/api_call_log`，读取授权额度，逐个创建/锁定日、月 `api_quota` 行并更新准入计数；即使额度不限，仍保留持久准入事实。
2. `Finish` 再开事务锁定调用、写结果/日志及唯一 `api_call_meter`。完整请求还执行前后两次 `gatewayStore.Touch`，分别锁应用并更新应用和 key 的 last_used_at，再复核路由和授权。
3. 同一应用的 day/month quota 行及应用/密钥更新时间形成写热点；PG 池仅 10，高并发还会排队。实测吞吐趋平且尾延迟快速上升，与这些串行区和数据库往返一致。

因此本轮主要瓶颈指向**持久配额/计量 DB 和主库生命周期事务**，没有证据将它归因于签名 CPU 或限流 Redis。尚未采集 PG 锁等待/SQL 分项与连接池等待的 trace，不能把各项占比、磁盘/WAL 或宿主调度的贡献说成已经精确量化。

## 后续方案（本批只记录）

先在相同单应用/多应用工作负载下采集 SQL 数量、PG 锁等待、提交时延和 DB pool wait，区分网络往返、事务提交、热点锁及池排队；使用与生产相近的 Linux/PG/Redis 布置复测，保留同样的真实门禁与计量，不直接提高并发或扩大池就宣称解决。

若数据库往返为主，可评审合并 quota 创建/锁定/占用及日志终结 SQL，减少往返而保持原子准入、成功结果与唯一 meter 同事务。若 Touch 热点为主，可评审将安全状态读取和非安全 last_used_at 观测写入分离；必须保留吊销后下一请求拒绝与返回前复核，不能用带 TTL 的鉴权缓存抵消性能。若配额热点持续限制单应用吞吐，再单独评审锁/分配策略及重启、降额、UTC 边界与回收语义。

这些都可能改变事务或可靠性设计，应由人另行批准后实施。M8c 保留 M8a/M8b 的即时吊销、持久计量及 fail-closed 语义。本次已完成性能测量与超标定位，**20ms 指标仍未通过**，没有开启 M9。
