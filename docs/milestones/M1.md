## 7. 关键设计

### 7.1 Token

- access：JWT HS256，15 分钟，claims：`sub(user_id) tid(tenant_id) jti exp iat`。**不放权限码**（避免权限变更后 token 仍有效；权限每次查缓存）。
- refresh：32 字节随机，存 `sys_refresh_token.token_hash`（sha256），7 天，轮换（每次刷新旧 token 立即作废）。
- 黑名单：登出/强踢时把 `jti` 写入 Redis `bl:{jti}`，TTL = 剩余有效期。
- 权限缓存：`perm:{user_id}` → 权限码集合，TTL 5 分钟；角色/菜单变更时删缓存。

### 7.2 登录安全

- 密码 bcrypt cost 12。
- 连续失败 5 次 → `locked_until = now + 15min`，返回 `20104`。
- 登录成功清零计数，记录 `last_login_at/ip`。
- 响应时间恒定（用户不存在时也做一次 bcrypt 比对，防用户名枚举）。

### 7.3 菜单树

```
GET /auth/menus → [
  { id, name, path, component, redirect, icon, sort, type, visible, keep_alive, meta,
    permission_code, children: [...] }
]
```

规则：
- 只返回 `status=active` 且 `visible=true` 的菜单（按钮类型不返回，按钮权限走 `permissions` 数组）。
- 按 `sort` 升序，同 sort 按 id。
- 树深度 ≤ 5；父节点不可见时子节点也不可见。
- 超管（`is_super`）返回全部菜单。
- 同时返回 `permissions: ["shop:create", ...]` 供按钮级控制。

### 7.4 数据权限

`data_scope` 解析成 GORM Scope：

| scope | 条件 |
|---|---|
| `all` | 无附加条件 |
| `dept` | `dept_id = 当前用户部门` |
| `dept_and_child` | `dept_id IN (本部门及子部门)`，用 `sys_dept.path` 前缀匹配 |
| `self` | `owner_user_id = 当前用户`（表需有该列；没有则退化为 `created_by`） |
| `custom` | `dept_id IN (sys_role_dept 中该角色的部门)` |

- 通过 `scope.DataScope(ctx, "owner_user_id")` 在 repo 查询里显式套用，**不做隐式全局注入**（隐式注入在 join 查询里容易出错）。
- 超管绕过数据权限（但仍记录）。

### 7.5 中间件链

```
TraceID → Recovery → AccessLog → CORS → Timeout
  → (auth 组) JWTAuth → LoadUser → RequirePerm("shop:create")
  → (open 组) HMACAuth（M8）
```

- `JWTAuth`：解析 token → 校验签名/过期 → 查黑名单 → 注入 `ctx` 中的 `UserIdentity`。
- `LoadUser`：查用户状态（停用立即拒绝）、角色、权限码（缓存）。
- `RequirePerm`：`is_super` 直接放行；否则权限码集合包含即可。

## 9. 验收清单

```bash
make migrate-up && make seed
make run-api &

# 登录
TOKEN=$(curl -s -X POST localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"<seed>"}' | jq -r .data.access_token)

# 菜单
curl -s localhost:8080/api/v1/auth/menus -H "Authorization: Bearer $TOKEN" | jq '.data | length'

# 无权限（用 operator 账号）
curl -s -o /dev/null -w "%{http_code}" -X POST localhost:8080/api/v1/admin/users \
  -H "Authorization: Bearer $OP_TOKEN" -d '{}'    # 403

# 登出后 refresh 失效
curl -s -X POST localhost:8080/api/v1/auth/logout -H "Authorization: Bearer $TOKEN"
curl -s -X POST localhost:8080/api/v1/auth/refresh -d "{\"refresh_token\":\"$RT\"}" | jq .code  # 20103
```

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 登录成功/失败 | 错误密码 401/20101；5 次后 423/20104 |
| 2 | token 生命周期 | access 15min 过期 401/20102；refresh 轮换后旧的失效 |
| 3 | 菜单按角色过滤 | 两个角色返回的菜单 id 集合不同 |
| 4 | 按钮权限 | 无 `shop:create` 调用创建店铺 403/20107 |
| 5 | 数据权限 | 运营 A 看不到运营 B 名下店铺 |
| 6 | 菜单成环 | 返回 400/20106 |
| 7 | 角色被引用 | 删除返回 409/20105 |
| 8 | 强制下线 | 踢出后 1 次请求内 401 |
| 9 | 审计 | 登录、授权变更在 `audit_log` 有记录 |
| 10 | 权限缓存失效 | 改角色权限后 5s 内生效 |

## 10. Gate A 评审关注点

- 权限码的粒度：是否按「资源:动作」两级够用，还是要三级
- 数据权限用显式 Scope 还是全局注入（本卡选显式，需确认 join 查询的漏套风险）
- 菜单与权限点是否合并（当前分开：菜单管展示，权限码管接口）
- refresh token 轮换策略对多端登录的影响
