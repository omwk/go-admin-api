## 0. 已裁决的边界（不要重新讨论）

| 议题 | 结论 |
|---|---|
| 幂等 | 持久阶段 + 加密暂存 + 对账；已消费未落地 → `unknown`，不重试 |
| 互斥 | `(tenant, credential)` 为单位；所有入口共用发送屏障 |

| 迁移 | 000015 起 |
| 上线门禁 | 平台协议 + fixture 验证前，只开放手动刷新 |

## 1. 目标


把凭据从「静态配置」变成「会自我维护的状态机」。这是系统能长期无人值守运行的前提。

## 2. 范围

1. 表：`credential_refresh_run`（迁移 `000010_credential_refresh`）+ `notification` 使用
2. 刷新调度：扫描 `refresh_at <= now() + lead_time`
3. 分布式锁 + 并发控制
4. 指数退避与最大重试
5. 状态机：`active → expiring → expired → needs_reauth`
6. 到期预警
7. 通知模块（站内信 + 邮件 + Webhook）
8. 刷新历史与统计

## 3. 不做

- 不做 OAuth 授权码流程的 UI（平台侧授权仍在平台后台完成）
- 不做 cookie 自动续期（只做预警）
- 不做多账号主备切换
- 不做密钥托管服务（KMS 集成放 M10）

## 5. 关键设计

### 5.1 状态机

```
active ──(距过期 < 3d)──▶ expiring ──(过期)──▶ expired
  │                          │                   │
  └──────── 刷新成功 ◀───────┴───────────────────┘
                             │
                     连续失败 ≥ 3 次
                             ▼
                       needs_reauth ──(人工更新凭据)──▶ active
```

- `active`：`expires_at - now > 3d` 或静态凭据。
- `expiring`：`0 < expires_at - now <= 3d`，仍在正常工作。
- `expired`：`expires_at < now`，同步任务应暂停。
- `needs_reauth`：刷新失败达阈值，必须人工介入。

### 5.2 调度

- 每分钟扫一次：`select id from shop_credential where status in ('active','expiring') and refresh_strategy='auto' and refresh_at <= now() + interval '5 min'`
- 每个凭据一把锁 `lock:cred:{id}`（TTL 2min）。
- 提交 asynq 任务 `credential:refresh`，`MaxRetry=0`（重试由业务层控制）。

### 5.3 退避

| 尝试 | 间隔 |
|---|---|
| 1 | 1 分钟 |
| 2 | 5 分钟 |
| 3 | 30 分钟 |
| 4 | 2 小时 |
| 5 | 6 小时 |

- 每次失败写一条 `credential_refresh_run(failed, next_retry_at)`。
- 达到 3 次 → `needs_reauth` + 通知 + 暂停该店铺的 `sync_job`。
- 人工更新凭据后，`consecutive_failures` 清零，状态回 `active`，恢复 `sync_job`。

### 5.4 刷新实现

```
connector.Get(platform).Refresh(ctx, cred)
  ├─ 成功：Seal 新值 → credential_version(v+1) → 旧版 retired
  │        → 更新 expires_at / refresh_at / status=active / failures=0
  │        → 写 credential_audit(action=refresh, result=success)
  └─ 失败：failures++ → 计算 next_retry_at → 写 run(failed)
           → 若 failures>=3：status=needs_reauth, 通知, 暂停任务
```

- 刷新前**必须**校验当前凭据仍是 `current_version_id`（防止并发重复刷新）。
- 刷新接口返回的新 `refresh_token` 若为空，保留旧的（部分平台不轮换 refresh_token）。
- 新 `expires_at` 缺失时，按平台默认 TTL 估算（配置在 `platform.settings.default_ttl`）。

### 5.5 通知

`kernel/notifier`：

```go
type Notifier interface { Send(ctx, Notification) error }
// 实现：Inbox（写 notification 表）、Email（SMTP）、Webhook（POST JSON）
```

- 模板化：`credential.expiring`、`credential.needs_reauth`、`sync.failed`、`drift.critical`、`billing.low_balance`。
- 去重：`dedup_key = template + resource_id + 日期`，24h 内只发一次。
- 失败重试 3 次，之后落 `notification.status=failed`，管理端可见。

### 5.6 到期预警

- 每天 09:00 扫描：3 天内到期、已过期、`needs_reauth`。
- 同一凭据同一状态 24h 只提醒一次。

## 8. 验收清单

```bash
# 造一个 5 分钟后过期的凭据
psql "$DSN" -c "update shop_credential set expires_at=now()+interval '5 min', refresh_at=now() where id=1;"
# 等调度（或手动触发）
curl -X POST localhost:8080/api/v1/admin/credentials/1/refresh -H "Authorization: Bearer $T"
psql "$DSN" -c "select version_no, retired_at is null from credential_version where credential_id=1 order by version_no;"
psql "$DSN" -c "select status, consecutive_failures from shop_credential where id=1;"   # active, 0

# 模拟失败
MOCK_FAULT=auth_invalid make run-worker
# 连续触发 3 次后
psql "$DSN" -c "select status from shop_credential where id=1;"     # needs_reauth
psql "$DSN" -c "select enabled from sync_job where shop_id=1;"       # false
psql "$DSN" -c "select count(*) from notification where template='credential.needs_reauth';"  # >=1

# 去重
psql "$DSN" -c "select count(*) from notification where dedup_key like 'credential.needs_reauth%';"
```

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 自动刷新 | 到期前 5 分钟触发，版本 +1 |
| 2 | 版本链 | 旧版本 retired，密文可解到 90 天 |
| 3 | 并发 | 同时触发两次只产生一个版本 |
| 4 | 退避 | 失败后下次执行时间符合退避表 |
| 5 | 阈值 | 3 次失败进入 needs_reauth 且暂停同步 |
| 6 | 通知 | 站内信 + Webhook 都收到，24h 不重复 |
| 7 | 人工恢复 | 更新凭据后状态回 active、任务恢复 |
| 8 | 历史 | refresh_run 可按凭据查，含 next_retry_at |
| 9 | 审计 | 每次刷新一条 audit，无明文 |

## 9. Gate A 评审关注点

- 刷新失败的判定：网络错误是否也算（当前算，可能误判）
- `needs_reauth` 后自动恢复的边界（人工更新 vs 平台恢复）
- 通知渠道的优先级与降级
- 静态凭据（Shopify）是否需要「健康检查」也纳入调度
