## 0. 已裁决的边界（不要重新讨论）

| 议题 | 结论 |
|---|---|
| 映射 DSL | 首版仅「一层 collections + value 转换 + 状态查表 + 金额换算」，跨字段回退不支持 |
| 映射发布 | 静态校验 + 状态表快照入 checksum + 20 条 dry-run + CAS 切 active |
| raw 去重 | 新建去重目录表，跨抓取时间去重；分区表七列键仅作批次兜底 |
| 分区 | 迁移建结构 + 独立维护任务每日预建两月；不做 DEFAULT 分区 |
| 页成功定义 | 每条都有已提交的持久处置；页级 Fetch 失败不推进 |
| 漂移 | 每页从原始 JSON 采集结构；前 3 个完整周期预热；基线只能人工 promote |
| 重放 | M3 只准备共用能力与检查点；50 万条执行器在 M4 |
| worker 身份 | 独立 WorkAccess，不冒充用户；按页签发，每页重校验 |
| 凭据 | 过期即暂停要求重授权；M3 不做自动刷新 |
| 未知字段 | 只走显式 `ext`；未知 listing 状态进隔离，不当 online/offline |

## 1. 目标


建立一个**平台无关**的同步引擎：适配器只管取数，映射配置负责解释，引擎负责幂等、重试、游标、监控。

## 2. 范围

1. 表：`raw_payload / schema_baseline / schema_drift_event / mapping_profile / mapping_version / quarantine_record / listing / listing_sku / sync_job / sync_cursor / sync_run / sync_error / dead_letter`（迁移 `000005_ingestion_init`、`000006_sync_init`）
2. `connector` 包：接口、注册表、错误归一、mock 平台
3. 一个真实平台适配器（Shopee），带 fixture 单测
4. 映射引擎：JSONPath 取源 + expr 转换 + 静态校验 + dry-run
5. 漂移检测与基线管理
6. 同步编排：run、游标、锁、重试、死信
7. Worker：asynq 队列 + cron
8. 管理端：任务配置、手动触发、run 列表、死信重放、漂移事件处理、隔离区

## 6. 接口清单

### M3a 第一批：raw 与分区维护（无新增 HTTP 路由）

| 接口 | 说明 | 访问边界 |
|---|---|---|
| `ingestion.Service.SaveRaw(ctx, shopID, resource, items)` | 每批最多 500 条；目录六列去重与 raw 同事务；返回原始 `RawRef{ID, ExternalID, FetchedAt, IsNew}` | `RawResolver` 注入可信店铺访问校验；本批不接入 worker 身份 |
| `ingestion.PayloadHash(payload)` | 语义 JSON SHA256；空白、键序、等值数字不影响 hash，数组保序 | 以 fixture 固定规范化口径 |
| `ingestion.ParseMonth("YYYY-MM")` | 严格月份校验，UTC 闭开区间；拒绝零年与无合法上界的末月 | DDL 只接收 `Month` |
| `ingestion.PartitionMaintainer.Run(ctx)` | 启动即检查当月及未来两月，此后每日 UTC 零点补建；缺覆盖告警，维护失败返回错误 | 独立维护连接 |
| SQL `ensure_raw_partition(text)` | 固定父表、固定命名、advisory transaction lock；返回是否新建 | `SECURITY INVOKER`，撤销 PUBLIC EXECUTE；仅维护角色执行 |

`errors.Is(err, ingestion.ErrPartitionMissing)` 表示缺分区，可修复后重试；失败批次的目录与 raw 全部回滚。调用方必须保留页与游标，不得推进检查点。更早批次已提交的 raw 可安全重试。本批只提供 raw 保存能力，不实现游标推进、映射引擎、listing 写入或 replay 执行器；`000005`/`000006` 按模型预建相关表及 `replay_run`。

维护部署：以迁移所有者（或具备父表所有权、目标 schema CREATE 与函数 EXECUTE 的专用维护角色）运行 `go run ./cmd/partition-maintenance`，必须单独配置 `CH_MAINTENANCE_DB_DSN`。由进程监督器负责失败告警与重启；覆盖告警包含 month/module/action，不输出 DSN、payload 或数据库错误详情。默认日志等级为 info，缺覆盖记录 warn。

应用角色必须独立于迁移/维护所有者，且不能继承维护角色；仅授予目标 schema USAGE、`raw_payload`/`raw_dedup` 的 SELECT/INSERT 及 `raw_payload_id_seq` USAGE。不授予 schema CREATE 或维护函数 EXECUTE。迁移撤销 PUBLIC 的 schema CREATE，若部署曾给应用角色单独授予 CREATE，也须撤销该授权。权限回收属于持久部署边界，down 不重新开放 PUBLIC CREATE。

验收：`go test -count=1 -v ./internal/kernel/db ./internal/bootstrap ./cmd/cli -run Integration`，覆盖迁移 up/down/up、完整表/索引/外键集合、UTC 跨月写入、缺分区回滚及游标保持、并发六列去重、并发建分区、停机跨月补建。受限应用角色实测使用事务内临时 NOLOGIN 角色，要求测试连接具备 CREATEROLE（否则明确 skip）；PUBLIC 权限目录断言不跳过。语义 fixture 和维护失败路径由 `go test ./internal/modules/ingestion` 覆盖。

### T3.3 原始报文落库

`ingestion.Service.SaveRaw(ctx, shopID, resource, items)`：

- 计算 `payload_sha256`；
- `INSERT ... ON CONFLICT (tenant_id, platform_id, shop_id, resource_type, external_id, payload_sha256) DO NOTHING`；
- 返回 `[]RawRef{ID, ExternalID, IsNew}`；
- 批量插入，每批 ≤ 500。

**验收**：同一批跑两次，`raw_payload` 条数不变；修改 payload 后多一条。

### T3.4 映射引擎

`ingestion.Mapping`：

```go
type Compiled struct { spec Spec; program *vm.Program; rules []CompiledField }
func Compile(specJSON []byte) (*Compiled, error)
func (c *Compiled) Apply(raw json.RawMessage) (map[string]any, []FieldError, error)
```

- JSONPath：`github.com/PaesslerAG/jsonpath`（允许新增此依赖）
- 表达式：`github.com/expr-lang/expr`（允许新增）
- 内置函数按 `docs/05-platform-sync.md` §6.3 实现，写在一个 `funcs.go` 里，注册到 expr 的 `Env`
- `Compile` 做静态校验：JSONPath 语法、expr 编译、target 字段在白名单内、`required` 与 `default` 不冲突
- `Apply` 返回：映射结果、字段级错误列表（缺失/类型错）、是否可入库

**验收**：单测覆盖 §6.3 每个函数；`Apply` 对 20 条 fixture 的结果与 golden 文件一致。

### T3.5 漂移检测

- 首次成功解析后建 `schema_baseline`（前 3 次不告警）
- 每次 run 结束对比一次（不是逐条）
- 按 `docs/05-platform-sync.md` §7.2 生成事件，24h 去重
- `critical` 事件发通知（M7 的通知模块未就绪前，先写 `notification` 表 `channel=inbox`）

**验收**：mock 平台 `MOCK_FAULT=drift`（多一个字段）→ 产生 `field_added`；删掉必填字段 → `critical` + 进隔离区。

### T3.6 规范层写入（product）

- 定义 `ingestion.TargetUpserter` 接口：`Upsert(ctx context.Context, tx *gorm.DB, resource ResourceType, records []Mapped) (UpsertStats, error)`；M3 在 `internal/modules/catalog/` 提供 `listing` 的最小实现，M4 用完整实现替换，**接口签名不变**
- 唯一键 `(tenant_id, shop_id, external_product_id)` 落 `listing`
- upsert 规则：`updated_at` 更新才覆盖；payload_sha256 相同直接跳过
- 必填缺失 → `quarantine_record`

**验收**：100 条数据入库后，`listing` 100 条；重复跑 `updated_at` 不变；3 条坏数据进隔离区且其余 97 条正常。

### T3.7 同步编排

`sync.Orchestrator`：

```
StartRun(jobID, trigger) →
  lock:sync:{shop}:{resource}（拿不到直接返回 60201）
  create sync_run(running)
  loop:
    cursor := loadCursor
    res := platform.Fetch(req)
    saveRaw(res.Items)
    apply + upsert
    update run stats
    if res.HasMore && pages < max: cursor = res.NextCursor; continue
    else break
  advanceCursor（仅当本页全部成功）
  finalize run
```

- 错误按 `docs/05-platform-sync.md` §3.1 处理
- 达到页数上限 → `status=partial` + re-enqueue 续跑
- 不可重试错误 → `dead_letter`
- 每页写一次 `sync_error`（如有）

**验收**：mock 500 条分 5 页，限 `max_pages=2` → 第一次 run `partial` 处理 200 条并自动续跑；最终 500 条全入库且无重复。

### T3.8 Worker 与调度

- `cmd/worker`：asynq server，队列 `sync`（并发 5）、`default`
- cron：读 `sync_job.cron`，用 asynq `Scheduler` 注册（启动时全量注册，job 变更时刷新）
- 任务载荷：`{"job_id":1,"run_id":0,"trigger":"cron"}`；重跑时带 `run_id` 做幂等
- 优雅退出：等待在途任务 ≤ 30s

**验收**：`make run-worker` 后定时任务按 cron 触发；kill 进程后重启不产生重复 run。

### T3.9 管理端接口

按 §6 实现。重点：
- run 列表默认按 `started_at desc`，带店铺名/平台名（join）
- 死信重放：重建一个 `trigger=retry` 的 run，只处理该条
- 漂移事件操作：`ack / resolve / ignore`，`ignore` 时把 path 写入白名单
- 映射 dry-run：返回 `{before, after, errors}`，不写库

**验收**：接口表逐条 curl 通过；dry-run 不产生任何写入（查 `raw_payload`/`listing` 条数不变）。

### T3.10 Shopee 适配器

- 实现 `Platform` 接口：签名、分页、错误映射
- `testdata/` 放脱敏 fixture：正常页、空页、401、429、字段缺失
- `httptest` 单测覆盖 5 种场景

### T3.11 Outbox 投递器

- `kernel/outbox`：`Emit(tx, event)` 与业务同事务写
- 投递器：每 500ms 批量取 `status in ('pending','failed') and available_at <= now()`，`FOR UPDATE SKIP LOCKED`
- 投递到 asynq；失败指数退避（1s/5s/30s/5m/30m），10 次后 `failed`
- 消费端幂等：按 `event_id` 去重
- 承接 ADR-011 从 M1b 延后的授权失效重试：授权变更与失效事件同 DB 事务写入，提交后仍同步 INCR；同步失败由 outbox 再尝试提升受影响用户版本。重复 INCR 只多生成缓存版本，不得恢复旧授权；覆盖故障恢复与重复事件，M1b 不提前实现投递器。

**验收**：事务回滚时事件不落库；投递失败会重试；重复投递消费端只处理一次；授权同步 INCR 故障恢复后能由 outbox 完成失效，重复事件不恢复旧权限。

## 8. 关键实现要点

1. **raw 落库必须在映射之前**，且失败不能回滚已落库的 raw。
2. **分页游标只在整页成功后推进**，否则会漏数据。
3. **`max_pages_per_run` 是必须的**，否则一个 run 跑几小时，锁续期、内存、超时全出问题。
4. **映射编译要缓存**：`Compiled` 按 `mapping_version_id` 缓存（LRU 100），不要每条记录都编译。
5. **expr 的编译错误要在发布时暴露**，不要等到运行时。
6. **漂移检测要采样**：`fields` 存全部路径，但样本值只存前 3 条，避免 `schema_baseline` 膨胀。
7. **`raw_payload` 的 GIN 索引不要建在 `payload` 上**（写入放大），只建普通 btree 索引在 `external_id`。
8. **分布式锁要续期**：处理大分页时每 10s 续一次，否则锁过期导致并发跑。
9. **`sync_run.stats` 用 jsonb 累加**，不要每页 `UPDATE` 整行（用 `jsonb_set` 或应用层累加后一次写）。
10. **死信不是垃圾桶**：必须能重放，且重放使用相同的映射版本（除非显式指定新版本）。

## 9. 验收清单

```bash
# 1. 准备：一个 mock 店铺 + 映射配置
make seed-dev          # 插入 mock 平台、店铺、100 条 fixture、mapping profile v1

# 2. 首次同步
curl -X POST localhost:8080/api/v1/admin/sync-jobs/1/run -H "Authorization: Bearer $T"
sleep 5
psql "$DSN" -c "select count(*) from raw_payload;"        # 100
psql "$DSN" -c "select count(*) from listing;"            # 100

# 3. 幂等：再跑一次
curl -X POST localhost:8080/api/v1/admin/sync-jobs/1/run -H "Authorization: Bearer $T"
sleep 5
psql "$DSN" -c "select count(*) from raw_payload;"        # 100（不变）
psql "$DSN" -c "select count(*) from listing;"            # 100（不变）

# 4. 坏数据隔离
MOCK_FAULT=missing_field make run-worker   # 重启 worker 后再触发
psql "$DSN" -c "select count(*) from quarantine_record;"  # >= 1
psql "$DSN" -c "select count(*) from listing;"            # 其余仍入库

# 5. 漂移
MOCK_FAULT=drift make run-worker
psql "$DSN" -c "select kind,path,severity from schema_drift_event;"

# 6. 映射 dry-run 不写库
before=$(psql "$DSN" -tAc "select count(*) from listing")
curl -X POST localhost:8080/api/v1/admin/mapping-versions/1/validate -H "Authorization: Bearer $T" -d '{}'
after=$(psql "$DSN" -tAc "select count(*) from listing")
test "$before" = "$after" && echo OK

# 7. 重试与死信
MOCK_FAULT=500 make run-worker   # 触发；应重试 3 次后进死信
psql "$DSN" -c "select count(*) from dead_letter;"

# 8. 分段续跑
psql "$DSN" -c "update sync_job set options='{\"max_pages_per_run\":2}'::jsonb where id=1;"
curl -X POST localhost:8080/api/v1/admin/sync-jobs/1/run -H "Authorization: Bearer $T"
psql "$DSN" -c "select status, stats from sync_run order by id desc limit 1;"  # partial, 200 条
```

| 2 | 映射正确 | `listing.title/price_cents` 与 golden 一致 |
| 3 | 幂等 | 重复跑条数不变、`updated_at` 不变 |
| 4 | 隔离 | 坏数据进隔离区，不影响其余 |
| 5 | 漂移 | 字段新增/删除各产生一条事件，critical 有通知 |
| 6 | 续跑 | `max_pages=2` 时 partial 后自动续跑，最终不重不漏 |
| 7 | 重试 | 500 错误重试 3 次；429 按 Retry-After 退避 |
| 8 | 死信 | 可单条重放成功 |
| 9 | 锁 | 并发触发同一 job，只有一个 run（另一个 60201） |
| 10 | 映射发布 | published 版本不可改，只能新建 |
| 11 | dry-run | 零写入 |
| 12 | Outbox | 事务回滚不产生事件；重复投递只消费一次 |

## 10. Gate A 评审关注点

- `connector.Platform` 接口是否够用（拿掉 refresh 会怎样？加 webhook 会怎样？）

- 游标与「整页成功才推进」的冲突：一页里有一条永久失败怎么办
- `raw_payload` 分区维护：谁来建下个月的分区（定时任务 or 迁移）
- 漂移检测的成本：每次 run 遍历全部字段是否可接受
- Outbox 的投递延迟 vs 直接发消息的取舍
