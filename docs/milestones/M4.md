## 7. 关键设计

### 7.1 归并策略（listing → SPU）

**默认不自动归并**。同步只写 `listing` 与 `listing_sku`，`spu_id` 为空。
归并方式（按优先级）：

1. **人工归并**：在后台选多个 listing → 建 SPU（或挂到已有 SPU）。
2. **编码匹配**：若平台 SKU 有商家编码且与其他 listing 相同 → 自动挂到同一 SPU。
3. **标题+品牌规则**：仅作为「建议」，不自动执行。

> 不做全自动模糊归并。误归并的代价（价格串货、库存错乱）远高于人工成本。

### 7.2 SKU 映射

- `listing_sku.external_sku_id` → `product_sku.code` 或人工绑定。
- 未绑定的 `listing_sku` 允许存在（`sku_id` 为空），列表页标记「未归并」。
- 价格：`product_sku.price_cents` 是参考价，`listing_sku.price_cents` 是平台实际价。**展示取 listing 价，分享取报价单**。

### 7.3 列表性能

- 主查询走 `product_spu` + 冗余字段（`price_min_cents/price_max_cents/sku_count/updated_at`），**不要**在列表里 join `product_sku` 聚合。
- 冗余字段在 SKU 变更时由 service 更新（同一事务）。
- 关键词搜索：标题用 `pg_trgm` GIN；编码用 btree 精确匹配。
- 平台/店铺筛选：先查 `listing` 得到 `spu_id` 集合（`EXISTS` 子查询），再查 SPU。
- 深分页：`page > 100` 时改用游标（`updated_at, id`），接口层提示。

**必须建索引**（迁移里）：
```sql
create index idx_product_spu_list on product_spu (tenant_id, status, updated_at desc) where deleted_at is null;
create index idx_product_spu_title_trgm on product_spu using gin (title gin_trgm_ops);
create index idx_listing_spu on listing (tenant_id, spu_id) where spu_id is not null;
create index idx_listing_shop on listing (tenant_id, shop_id, status, synced_at desc);
```

### 7.4 类目映射

- 平台类目同步：独立 `sync_job`（`resource=category`），落 `platform_category`。
- 自动匹配规则（按顺序，命中即止）：
  1. 手工映射已存在 → 用
  2. 同名类目（规范化后）→ 用，`confidence=0.9`
  3. 父类目已映射 → 继承，`confidence=0.6`
  4. 都不命中 → `category_id=null`，进「未匹配池」
- 商品入库时按 `platform_category → category_mapping` 反查内部类目。

M4a 本轮裁决：同步仅建立未匹配记录，精确同名同路径（0.9）与父类目规则（0.6）均只产生候选；人工 PUT 才应用映射并写 `source=manual`。商品列表的 `category_id` 同时匹配 SPU 自身类目与关联 listing 的已应用类目映射，后者通过映射配置的通用 `category_id`（平台类目 external_id，保存在 `listing.ext.category_id`）关联，不读取平台原始字段。

### 7.5 库存

- 每次同步写一条 `inventory_snapshot`（**不要** upsert，要留趋势）。
- `listing_sku.stock` 与 `product_sku.stock_cached` 是冗余的「最新值」。
- 保留 30 天，`daily cleanup` 任务删除更早的。
- 聚合到 SPU 的库存 = 所有 listing_sku 之和（展示用，可能重复计算，标注口径）。

M4a 接口口径：商品详情 `reported_stock` 为全部关联 listing_sku.stock 之和，**可能重复计算**，不是实物可售库存。快照 `available` 取映射后的 SKU `stock`；平台报告预留量时通过 SKU `ext.reserved` 映射，未报告写 0。`synced_at` 为本次 upsert 的 UTC 时间，与 raw.fetched_at 无关；被来源仲裁整组跳过的重投不重复记快照。worker leader 启动补清，随后每个 UTC 日清理一次 `synced_at < now - 30d`，失败不标完成、下次重试。

### 7.6 重放（REQ-SYNC-011）

M4b1 第一轮范围（2026-11-05）：仅交付 `000008_replay_members`、成员冻结、事务批处理及 ADR-018 §3 来源仲裁。公平调度、在线 pin、调度 grant 与 DB 代次 fence 留第二轮；本轮只在 `replay_run` 预留 `scheduling_generation`。当前 worker 使用既有 Redis 同步锁与 job 行锁，每个 outbox 事件最多提交 200 条。

M4b1 第二轮：在尚未合并的 000008 内补齐 `sync_run.scheduling_generation/ready_at`、`replay_run.ready_at`、`raw_partition_pin` 和活动 replay 唯一约束。grant 持久化在 `sync_job.options._scheduler`，包含 owner、epoch、deadline、run 身份和 sync 超车计数；正常 sync 与历史/单条 replay 共用 job 行锁仲裁。replay ready 时最多 4 个 sync 片段越过；run/outbox 的 ready 时间同事务持久化，等待中的唤醒不修改原 ready 时间。创建 sync 不再依赖 Redis 执行锁，因此 replay 持锁时仍可登记同步到达。

目标事务先锁 job，校验 grant owner/epoch/deadline 与 run.scheduling_generation，再锁/处理目标与检查点；截止时间失效导致整批回滚。正常 sync 片段最多 60 秒，replay 最多 2 秒/200 条。cancel 与处理共享 job→run 锁顺序，取消后不再写目标，checkpoint 和成员清单保留。

冻结与维护 `PartitionRetirer.Retire` 共用数据库维护锁；维护 detach/drop 必须通过该端口检查活动 pin。活跃 pin 无 TTL；成功、partial 或 cancelled 后释放活动保护，保留 pin 历史、成员、检查点作为恢复窗口，不自动清理这些证据。已 detach/drop 后恢复仍须先恢复在线 raw。管理响应含 `total/processed/stats/eta_seconds/last_committed_at`；ETA 取最近 15 分钟提交数除以墙钟时间，至少三批且覆盖 60 秒、最近五分钟有提交才返回估算，否则为 null。

创建接口在同一 REPEATABLE READ 事务中校验在线范围、去重完整 RawRef、物化成员并冻结 mapping version/checksum/spec/函数集版本。仅成功提交后返回 201；空集合直接成功且无派发事件；超 500000 条或范围包含已归档 raw 返回 60601，整个创建回滚。时间范围含头不含尾，ids 支持 `ids` 数组或闭区间 `from_raw_id/to_raw_id`，quarantine 选择当前 pending 成员。

进度接口返回 `total`、`processed`、`checkpoint_key`、`upper_key` 及六种处置计数；`processed = inserted+updated+skipped_stale+skipped_same+quarantined+failed`。每批目标、库存快照、SPU 汇总、隔离/死信、成员处置、stats、检查点及下一次派发同事务提交，不更新 `sync_cursor`。冻结后新增 raw 不加入旧 run；运行中 raw 缺失则整批回滚并保留检查点。

来源仲裁在任何目标写入前完成：完整 `(fetched_at,id)`、目录与 external_id 校验通过后才比较 `source_order=raw.id`。旧来源整组跳过；同 raw 同 checksum 跳过、换 checksum 可重解释。缺 `_ingestion`、非法时间进入 `source_metadata_unknown`；order/id 矛盾或目录多义进入 `source_identity_ambiguous`。新原因由 000008 先扩展数据库白名单。

本轮验收：`powershell -File scripts/verify.ps1 -Integration -Migration`；`TestReplayIntegrationFrozenMembersRestartAndAtomicRollback` 覆盖 500 条三批、强杀子进程恢复、stats 故障整批回滚及冻结后新 raw；`TestReplayIntegrationStaleGroupAndSameRawNewChecksum` 与 `TestReplayIntegrationUncertainSourceQuarantinesWithoutWrites` 覆盖来源仲裁；容量、归档、空集合、权限撤销另有真实数据库集成测试。

复用 M3 的映射引擎：

```
POST /replays {resource, shop_id, mapping_version_id, scope:{type:time|ids|quarantine, from, to}}
→ replay_run(running)
→ worker 分批 200 条 raw
→ Apply(新映射) → upsert listing/listing_sku → 累加 stats
→ 完成写 stats，失败进 dead_letter
```

安全：
- 单次 ≤ 50 万条；
- 重放只 upsert，不删除；
- 重放与同步任务用同一把锁（`lock:sync:{shop}:{resource}`）；
- 重放前后各打一个快照（`select count(*)`、关键字段 checksum）写进 `replay_run.stats`，便于对比。

### 7.7 单条重同步

`POST /listings/{id}/resync`：
- 调用 `platform.Fetch` 单条详情接口（若平台不支持，回退到按 ID 拉一页）
- 落 raw → 用当前 active 映射解析 → upsert
- 不动其他记录
- 若凭据失效，返回 `60401` 并提示去刷新

### 7.8 导出

- `POST /products/export` 接受 `filters` / `sort`，冻结字段版本、tenant、owner，返回 201 与 `export_id`；支持 `Idempotency-Key`，不接受对象键。
- M4b2 第一轮：新增 `000009_export_rows`。worker 首次开始在 ≤3 秒事务内物化完整白名单投影、排序键和 ordinal；重试复制已物化内容，保留生成时间。每批 ≤1000 按 ordinal keyset 流式写 CSV；执行硬预算 5 分钟。
- CSV 仅含 id、title、价格区间（分）、SKU 数、类目、状态和更新时间；不含扩展保留键或 raw。单元格以 `= + - @` 开头（包括前置空白）时加 `'`。
- 按 ADR-018 §8 使用 minio-go/v7 v7.0.83，新适配器只接导出，现有 HTTP 存储路径保留。私有键由服务端生成：`exports/{tenant}/{export_id}/attempt-{n}.csv`。
- 上传后读回校验大小、数据行数与 SHA-256；一次 attempt/status 条件 UPDATE 发布 DB 指针，同时登记 `file_object`。失败或过时代次清理对象，删除失败进 outbox；不启用桶版本管理、不复制覆盖对象。
- `GET /exports/{id}` 返回状态、attempt、row_total、row_count、时间字段；成功时返回下载 URL。下载校验 tenant 和 owner，其他租户或用户返回 404。对象逻辑寿命 24h，签名有效期为 `min(1h, 剩余寿命)`。
- 清理保留 DB 指针引用键，删除同前缀其他 attempt；每 5 分钟扫描超过 1h 的崩溃/临时残留。清理重试复用原 outbox 待办。
- 第二轮实现并发准入、pending 限额、观测阈值及其他保留期管理；本轮验收记录见 `M4b2-acceptance.md`。
