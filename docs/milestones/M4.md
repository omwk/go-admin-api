- 依赖：M3

- 分支：`feat/M4-catalog`

## 1. 目标

把 M3 落下来的 `raw_payload` 变成可查询、可归并、可分享的商品主数据，并打通「改映射 → 重放 → 数据修正」的闭环。

## 2. 范围

1. 表：`category / platform_category / category_mapping / product_spu / product_sku / product_media / inventory_snapshot`（迁移 `000007_catalog_init`）；`listing` / `listing_sku` 已在 M3 的 `000005_ingestion_init` 建好，本卡在其上做完整落库与归并
2. 商品同步落库：从 listing 到 SPU/SKU 的归并
3. 商品查询：列表（多条件 + 分页）、详情、搜索
4. 类目映射：平台类目同步 + 人工映射 + 未匹配池
5. 库存快照
6. 手工商品
7. 历史重放（`replay_run`）
8. 单条重同步
9. 商品导出（异步 CSV）

- 不做图片处理（裁剪/水印）

## 7. 关键设计

### 7.1 归并策略（listing → SPU）

**默认不自动归并**。同步只写 `listing` 与 `listing_sku`，`spu_id` 为空。
归并方式（按优先级）：

1. **人工归并**：在后台选多个 listing → 建 SPU（或挂到已有 SPU）。
2. **编码匹配**：若平台 SKU 有商家编码且与其他 listing 相同 → 自动挂到同一 SPU。
3. **标题+品牌规则**：仅作为「建议」，不自动执行。

> 不做全自动模糊归并。误归并的代价（价格串货、库存错乱）远高于人工成本。

### 7.2 SKU 映射

- `listing_sku.external_sku_id` → `product_sku.code` 或人工绑定。
- 未绑定的 `listing_sku` 允许存在（`sku_id` 为空），列表页标记「未归并」。
- 价格：`product_sku.price_cents` 是参考价，`listing_sku.price_cents` 是平台实际价。**展示取 listing 价，分享取报价单**。

### 7.3 列表性能

- 主查询走 `product_spu` + 冗余字段（`price_min_cents/price_max_cents/sku_count/updated_at`），**不要**在列表里 join `product_sku` 聚合。
- 冗余字段在 SKU 变更时由 service 更新（同一事务）。
- 关键词搜索：标题用 `pg_trgm` GIN；编码用 btree 精确匹配。
- 平台/店铺筛选：先查 `listing` 得到 `spu_id` 集合（`EXISTS` 子查询），再查 SPU。
- 深分页：`page > 100` 时改用游标（`updated_at, id`），接口层提示。

**必须建索引**（迁移里）：
```sql
create index idx_product_spu_list on product_spu (tenant_id, status, updated_at desc) where deleted_at is null;
create index idx_product_spu_title_trgm on product_spu using gin (title gin_trgm_ops);
create index idx_listing_spu on listing (tenant_id, spu_id) where spu_id is not null;
create index idx_listing_shop on listing (tenant_id, shop_id, status, synced_at desc);
```

### 7.4 类目映射

- 平台类目同步：独立 `sync_job`（`resource=category`），落 `platform_category`。
- 自动匹配规则（按顺序，命中即止）：
  1. 手工映射已存在 → 用
  2. 同名类目（规范化后）→ 用，`confidence=0.9`
  3. 父类目已映射 → 继承，`confidence=0.6`
  4. 都不命中 → `category_id=null`，进「未匹配池」
- 商品入库时按 `platform_category → category_mapping` 反查内部类目。

### 7.5 库存

- 每次同步写一条 `inventory_snapshot`（**不要** upsert，要留趋势）。
- `listing_sku.stock` 与 `product_sku.stock_cached` 是冗余的「最新值」。
- 保留 30 天，`daily cleanup` 任务删除更早的。
- 聚合到 SPU 的库存 = 所有 listing_sku 之和（展示用，可能重复计算，标注口径）。

### 7.6 重放（REQ-SYNC-011）

复用 M3 的映射引擎：

```
POST /replays {resource, shop_id, mapping_version_id, scope:{type:time|ids|quarantine, from, to}}
→ replay_run(running)
→ worker 分批 200 条 raw
→ Apply(新映射) → upsert listing/listing_sku → 累加 stats
→ 完成写 stats，失败进 dead_letter
```

安全：
- 单次 ≤ 50 万条；
- 重放只 upsert，不删除；
- 重放与同步任务用同一把锁（`lock:sync:{shop}:{resource}`）；
- 重放前后各打一个快照（`select count(*)`、关键字段 checksum）写进 `replay_run.stats`，便于对比。

### 7.7 单条重同步

`POST /listings/{id}/resync`：
- 调用 `platform.Fetch` 单条详情接口（若平台不支持，回退到按 ID 拉一页）
- 落 raw → 用当前 active 映射解析 → upsert
- 不动其他记录
- 若凭据失效，返回 `60401` 并提示去刷新

### 7.8 导出

- `POST /products/export` 创建任务，返回 `export_id`
- worker 流式写 CSV 到对象存储，分批查（keyset 分页，每批 1000）
- 进度写 `file_object.meta`
- 完成后返回 presigned URL（有效期 1 小时）

## 10. Gate A 评审关注点

- SPU 归并是否应该自动（当前选人工，确认是否接受运营成本）
- 列表冗余字段的维护一致性（双写风险）
- 库存快照的量级（10 万 SKU × 每天多次 = 是否要降采样）
- 重放的并发与锁粒度（按店铺 vs 按资源）
- 导出走对象存储的成本与清理策略
